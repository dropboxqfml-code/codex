# ACPI 메서드 연결 구문 요약 — Acpi-routing-v3

## v2 실기에서 확인한 내용

사용자 요약에서 DSDT 직접 본문 읽기 Complete, 알려진 SABI 설명자 1개, 대응 메서드 1개, 인수 3개, 본문 Parsed를 확인했습니다. v1에서 목록 미관측 때문에 읽지 않았던 DSDT를 v2가 읽은 경로가 관측됐습니다. 전체 namespace 탐색은 여전히 Partial이며, 이는 전체 펌웨어의 후보 유일성이나 다른 정의의 부재를 보장하지 않습니다. 원문 사용자 TXT는 저장소와 배포물에 포함하지 않습니다.

본문에서 Arg1==1, SizeOf(Arg2)==21, 상수 FF 반환 구문은 지원 범위에서 미관측이었습니다. 이는 호출된 보조 정의나 펌웨어 내부에도 그런 처리가 없다는 뜻이 아닙니다. 기존 판독기는 알려진 보조 호출의 인수 바이트를 읽을 뿐 그 정의 본문을 따라 읽지 않았습니다. 첫 SSDT는 Partial·설명자/메서드 0으로, 전체 SSDT나 기능 부재 판정이 아닙니다.

따라서 이번에는 수집 범위를 늘리지 않고 **관측된 후보의 반환 구문과 같은 테이블의 보조 정의 연결**을 요약합니다. FF의 의미나 배터리 명령을 확정한 변경은 아닙니다.

## 새로 표시하는 구문 사실

- 후보 본문의 알려진 명명 호출 표현식 수와 직접 Arg2를 인수로 쓴 횟수. Local·별칭·계산식·보조 인수로의 값 전달은 추론하지 않습니다.
- Return 문 수와 반환 표현식 종류: 정수 상수, 상수 Buffer, 직접 Arg2, 알려진 명명 호출, 미해결 이름, 기타. 상수 값·이름·경로·주소·원본 바이트는 내보내지 않습니다.
- 같은 테이블에서 정의가 관측된 보조 메서드의 정적 탐색 상태, 검사한 정의 수, 해석/미지원 수, 순환 구문 관측과 한계 초과 여부.
- 해석된 관측 연결 전체가 지원 범위 안일 때만 보조 정의의 상수 FF 반환 구문 여부. 이 값은 기존 후보 본문의 FF 표식을 덮지 않습니다. 보조 FF가 관측돼도 실제 응답의 원인이나 실행 분기를 입증하지 않습니다.

미해결 이름은 데이터 객체 참조인지 인수 없는 메서드 호출인지 단정하지 않습니다. 해당 수를 보고하고 연결 탐색을 Partial로 둡니다. 지원하지 않는 본문의 중간 연결·반환 표식은 폐기합니다. 순환과 여러 경로에서 재사용되는 정의를 구분하며 같은 보조 정의는 한 번만 읽습니다.

관측된 중복 보조 정의는 첫 것을 임의 선택하지 않습니다. 명시적으로 지정한 경로를 부모 범위의 다른 정의로 바꾸지 않고, 관측된 이름 객체·별칭·External 선언이 부모의 메서드를 가리는 경우도 보수적으로 처리합니다. Create*Field가 관측 메서드 이름을 가리면 해당 본문을 해석 불가로 닫습니다. ObjectType·RefOf·Store 대상처럼 이름을 참조하는 위치를 호출로 세지 않습니다. 전체 namespace가 부분 해석되거나 Field 내부를 해석하지 않은 경우까지 완전한 이름 해석을 보장하지는 않습니다.

피연산자 종류는 [고정 ACPICA 정의](https://github.com/acpica/acpica/blob/e85aa3bebaae81ed1e6d163511ac7e1eafe732cf/source/include/acopcode.h#L43)의 TermArg·SimpleName·SuperName·Target을 대조했습니다. 파일 SHA-256은 `72410dd629b6e483ad80eab513e244d951a79587784de6b842c6dddbeac1e7b2`입니다. 지원하지 않는 참조 형태는 호출로 추측하지 않고 해석 불가 또는 미확정으로 둡니다. 이는 문법 근거이며 현재 모델의 배터리 계약 근거는 아닙니다.

## 실행·수집 경계

보조 정의는 루트를 제외한 깊이 2·최대 8개 정의·루트와 검사한 고유 정의 전체의 호출 표현식 32개까지만 정적으로 읽습니다. 기존 테이블당 4MiB·전체 처리 노드 10만·구문 깊이 32·메서드 정의 4096개 제한도 유지하며 관측 이름 객체는 8192개로 제한합니다. 한계 초과를 배터리 미지원이나 분석 완료로 바꾸지 않습니다.

Windows 수집은 v2와 같은 두 API·고정 ACPI 공급자·DSDT 직접 읽기/첫 SSDT입니다. 레지스트리 캐시·다른 SSDT·새 WMI/OEM 요청·삼성 DLL·AML 평가·변수/조건 계산·실험 예약 접근·포트/장치/드라이버/물리 메모리·보안 변경·펌웨어 쓰기는 없습니다. 원본 테이블을 저장하거나 제출하지 않으며 프로그램의 네트워크 통신도 없습니다.

기존 실제 호출 요청·응답 디코더·예약·일반 앱의 하드웨어 경로·충전 제어 정책은 변경하지 않습니다. 완료된 1회 OEM 실험은 재실행하지 않고 예약 표식을 유지합니다. 실제 충전 제어는 계속 Unsupported입니다.

## 새 요약 확인

1. [프로그램 ZIP](../downloads/ATIVBatteryGuard-ACPI-METHOD-FLOW.zip) **하나만** 새 폴더에 모두 압축 해제합니다. 소스 ZIP은 실행에 필요하지 않습니다.
2. `ATIVBatteryGuard.AcpiRoutingCheck.exe`를 **일반 권한**으로 실행합니다.
3. **Acpi-routing-v3** 표시와 새 연결 구문 요약을 포함한 출력만 전달합니다. 기존 TXT·삼성 DLL·원본 ACPI는 다시 제출하지 않습니다.

이것은 이미 확인된 v2 수집에 새 구문 분석을 추가한 도구입니다. v2의 같은 출력이나 관리자 비교를 다시 요청하지 않습니다. 기존 Windows 수집 경로는 v2 실기에서 관측됐지만 **새 v3 연결 분석의 실제 결과는 아직 미관측**입니다. 자동 검증은 합성 AML과 가짜 읽기 콜백만 사용하며 [VALIDATION](VALIDATION.md)에 이번 결과를 기록합니다.
