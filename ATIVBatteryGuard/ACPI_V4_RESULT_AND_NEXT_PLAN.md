# v4 실기 결과 분석과 다음 개발 계획

**후속 구현:** 사용자의 다음 개발 지시에 따라 [v5 이름 객체·참조 관계 요약](ACPI_OBJECT_REFERENCE_UPDATE.md)을 구현합니다. 아래의 분석 전용 범위는 이 계획을 작성한 당시 기록이며 v4 반복 실행을 요청하는 내용은 아닙니다.

## 목표 달성 여부

**v4의 직접 목표인 보조 본문의 정적 구문 해석 보완은 달성됐습니다.** 사용자 출력의 DSDT에서 보조 본문 1개가 Parsed로 읽혔고 미지원 본문은 0개, 후보/보조 실패 종류와 연산은 None입니다. v3에서 보조 1개가 해석 불가였던 상태와 구분됩니다. 원문 TXT는 저장소와 배포물에 포함하지 않습니다.

| 항목 | v3 | 이번 v4 | 해석 |
| --- | --- | --- | --- |
| DSDT 본문 읽기 / 후보 본문 | Complete / Parsed | Complete / Parsed | 기존 수집·후보 구문 해석이 유지됐습니다. |
| 보조 본문 해석 / 미지원 수 | 0 / 1 | 1 / 0 | v4 확장 구문 지원의 실기 효과가 관측됐습니다. |
| 보조 본문의 확장 구문 | 미확정 | Acquire, Release | 동기화 구문의 정적 관측입니다. 실제 동기화나 AML 실행이 아닙니다. |
| 후보 Return | 1 / UnresolvedName | 1 / UnresolvedName | 이름 참조가 어떤 객체인지 아직 분류하지 못했습니다. |
| 해석한 보조 본문의 Return | 미확정 | 0 / None | 명시적 Return 구문이 없습니다. 실제 반환값 0·효과 없음·출력 데이터 미변경을 뜻하지 않습니다. |
| 보조 본문 범위의 상수 FF 반환 | 미확정 | 미관측 | 해석한 1개 본문에서 literal FF Return 구문이 미관측입니다. 실제 FF 응답의 발생 위치·의미는 미확정입니다. |
| 연결 구문 상태 / 미확정 이름 참조 | Partial / 3 | Partial / 6 | 참조 횟수이며 고유 객체 6개가 아닙니다. 성공한 보조 본문도 집계하므로 증가만으로 악화라 판단하지 않습니다. |

이번 실기에는 새로운 구문 해석 실패가 없어 실패 종류 표시가 None으로 나왔습니다. 정상 보고 경로는 관측됐지만 모든 오류 분류 분기를 실기에서 시험한 것은 아닙니다. 해당 경계의 자동 검증은 직전 384개 테스트·Python 25개 기록입니다.

## 남은 한계

현재 코드의 연결 Partial을 만드는 확인 가능한 조건은 후보와 성공한 보조 본문에서 집계한 미확정 이름 참조 6회입니다. 전체 namespace의 Partial은 별도의 탐색 한계이며 함께 유지합니다. 일부 참조를 분류하더라도 전체 펌웨어의 유일성·완전성이나 실제 실행 경로를 보장하지 않습니다.

직접 Arg2 호출 인수 0회와 이름 참조 Return, 보조 본문의 명시적 Return 없음은 **이름 객체나 공유 버퍼를 통한 전달 가능성**을 검토할 이유가 됩니다. 하지만 현재 요약은 실제 저장 대상·객체 종류·데이터 전달을 입증하지 않았으므로 공유 버퍼 방식이라고 확정하지 않습니다.

상수 FF Return 미관측은 FF를 버퍼에 대입하거나 계산·다른 정의·펌웨어 내부에서 생성하는 경우를 배제하지 못합니다. FF가 보조 밖에서 생겼다거나 배터리 보호 OFF/ON·하드웨어 미지원이라고 결론내리지 않습니다. 기존 전체 관측 연결의 보조 FF 값은 계속 미확정입니다.

첫 SSDT는 여전히 Partial·설명자/메서드 0·본문 연결 NotInspected입니다. 그 구역의 실패 None은 분석 성공이 아니라 시험하지 않은 상태와 구분해야 합니다. 나머지 SSDT와 전체 펌웨어의 기능 부재를 뜻하지 않습니다.

## 다음 개발 순서

1. **관측된 이름 정의의 종류 분류**
   - 같은 테이블에서 관측한 Buffer·단순 Name 객체·Mutex·Event·OperationRegion·지원 가능한 Field 정의를 구분합니다. 이름·경로는 임시 내부 자료로만 유지하고 보고서는 고정 종류·수만 사용합니다.
   - 중복·별칭·동적 생성·해석되지 않은 정의·명시 경로를 보수적으로 처리합니다. 분류할 수 없는 이름을 임의로 객체나 무인수 메서드로 정하지 않습니다.
   - 단순 FieldList부터 경계·크기·노드 한계를 검사하고 미지원 구문은 Partial로 닫습니다. byte 단위 재검색이나 전체 AML 실행기를 도입하지 않습니다.
2. **후보·보조 본문의 저장·반환 참조 관계 요약**
   - `Store(Arg2, Name)`과 `Return(Name)`이 같은 관측 정의를 참조하는지, 보조 본문에서 어떤 종류의 객체/필드를 Store 대상으로 쓰는지 구문 관계만 요약합니다.
   - 실제 값 전파·실행 분기·별칭 값·입출력 동일성·장치 상태는 평가하지 않습니다. 동일한 정적 이름 관계만으로 같은 데이터가 반환됐다고 보고하지 않습니다.
   - OperationRegion은 SystemIO/SystemMemory/EmbeddedControl 같은 정적 주소 공간 종류만 분류합니다. 주소·오프셋·길이·필드 이름은 출력하지 않고 실제 영역을 읽거나 쓰지 않습니다.
3. **오인식 방지와 개인정보·실행 경계 검증**
   - 알려진 객체 참조의 호출 오인 방지, 중복/가림/명시 경로, 미지원 FieldList의 중단, 실패 사실 폐기, 불변 보고서와 원문 비노출을 합성 입력으로 검증합니다.
   - 기존 두 Windows 읽기 API·DSDT/첫 SSDT·메모리/노드/시간/보조 정의 상한을 유지하고 빌드·관련 회귀·배포 검증을 수행합니다. 새 장치/드라이버/포트/물리 메모리/레지스트리 경로는 추가하지 않습니다.
4. **새 관계 요약이 구현된 뒤 결과 검토**
   - v4의 반복 실행이나 관리자 비교는 필요하지 않습니다. 새 코드가 실제로 추가 정보를 제공할 때만 새 요약을 확인합니다. 기존 TXT/DLL/EXE·원본 ACPI 재제출은 요청하지 않습니다.
   - 정적 전달 관계를 확보해도 모델별 Windows 배터리 명령과 FF 의미는 별도 근거가 필요합니다. 근거 없이 요청 바이트를 수정하거나 다른 명령·0x66·추가 OEM 시험·충전 제어를 활성화하지 않습니다.

수용 조건은 이름 객체 참조와 알려진 호출을 보수적으로 구분하고, 데이터/필드 참조의 정적 관계를 개인정보 없이 보고하며, 불완전한 부분을 미확정으로 유지하는 것입니다. 전체 Partial을 없애는 것 자체를 목표로 삼지 않습니다.

## 이번 작업 범위

이번 요청에 따라 분석과 계획만 기록했습니다. 실행 코드·정책·예약·배포 ZIP은 변경하지 않았고 새 빌드·테스트·하드웨어 실행을 수행하지 않았습니다. 384개·Python 25개·빌드 경고/오류 0개는 직전 코드의 검증 기록입니다. 실제 충전 제어는 계속 Unsupported이며 완료된 1회 OEM 실험과 예약 표식은 그대로 유지합니다.
