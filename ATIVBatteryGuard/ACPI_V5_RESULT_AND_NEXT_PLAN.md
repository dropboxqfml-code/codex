# v5 실기 결과와 다음 개발 계획 — 2026-11-05 한국 시간

## 의도한 결과의 확인

**v5의 직접 목표인 관측 이름 정의의 종류 분류와 저장·반환 참조 관계 요약은 달성됐습니다.** 사용자 출력에서 후보 3/3회와 해석한 보조 본문 3/3회의 이름 참조가 분류됐습니다. 횟수는 고유 객체 수가 아닙니다. 원문 TXT는 저장소와 배포물에 포함하지 않습니다.

| 확인 항목 | 이번 결과 | 확인 가능한 범위 |
| --- | --- | --- |
| 후보 본문의 이름 참조 | 3/3회 분류, Field | 관측된 참조들의 선언 종류가 Field입니다. 실제 실행 중 값은 확인하지 않았습니다. |
| 입력 저장 / 직접 반환 | 모두 Field, 같은 관측 정의 참조 구문 관측 | 직접 Store(Arg2, Name)의 대상과 Return(Name)이 동일한 관측 정의를 참조합니다. 실행 순서·입력 그대로 반환·수정 효과는 입증하지 않습니다. |
| 보조 본문의 이름 참조 | 3/3회 분류, Mutex·Field | 동기화 객체와 필드의 선언 종류를 관측했습니다. 실제 동기화나 영역 접근을 수행한 결과가 아닙니다. |
| 보조 본문의 Store 대상 | Field / SystemIo | I/O 주소 공간으로 선언된 필드를 Store 대상으로 쓰는 구문입니다. 포트 번호·실제 I/O·SMI 호출·충전 제어를 확인한 것은 아닙니다. |
| 후보 반환/저장 정의와 보조 본문의 직접 참조 관계 | 미확정 / 미확정 | 같은 정의를 참조하는 양성 관계가 보고되지 않았고, 부분 탐색이므로 관계 부재도 확정하지 않습니다. |
| 기존 후보 / 보조 구문 해석 | Parsed / 1개 Parsed, 미지원 0, 실패 None | v4에서 관측한 구문 해석 경로가 유지됐습니다. |

기존 Flow의 미확정 이름 참조 6회와 새 객체 분류의 3/3+3/3은 모순되지 않습니다. v5는 기존 보수적 연결 검사와 별도로 선언 종류를 분류하도록 구현했습니다. 종류를 분류했다고 실제 값·별칭·실행 중 객체의 동일성을 확인한 것은 아닙니다. 향후 보고 문구에서도 이 차이를 더 명확히 표시해야 합니다.

## 아직 확정하지 못한 내용

전체 namespace·기존 연결·새 객체 보고서는 Partial입니다. 선언 종류 6/6회를 분류해도 전체 정의 탐색이 완료되는 것은 아니며, 후보 Field가 연결된 Region의 종류나 모든 필드 관계가 해소됐다는 뜻도 아닙니다.

현재 보고서는 후보 입력/반환 Field의 주소 공간과 필드 폭을 출력하지 않습니다. 보조 Store 대상의 SystemIo를 후보 Field에도 적용하면 안 됩니다. 후보와 보조가 같은 Field를 직접 참조한다고 확인하지 못했더라도 서로 다른 Field가 같은 Region 선언에 속하거나 다른 통로로 연계될 가능성은 남습니다. 다른 Region 선언도 실제 물리 영역이 다르다는 뜻은 아닙니다.

관측된 Field 저장·반환과 보조 SystemIo 구문은 전달 통로를 구체화한 근거입니다. 그러나 실제 호출의 실행, I/O의 장치 의미, SMI 여부·번호, 펌웨어 내부 처리, FF의 생성 위치나 배터리 보호 ON/OFF를 입증하지 않습니다. 기존 FF 응답의 의미는 여전히 미확정이고 실제 충전 제어는 Unsupported입니다.

첫 SSDT는 Partial·설명자/메서드 0·연결/객체 NotInspected입니다. 분석되지 않은 영역의 None·미확정을 성공이나 기능 부재로 확대하지 않습니다.

## 다음 개발의 우선순위와 수용 조건

1. **입력/반환 Field의 선언 형태 확인**
   - 후보의 직접 Arg2 저장 대상과 직접 반환 대상 Field가 속한 관측 Region의 주소 공간 종류를 별도로 보고합니다.
   - 필드의 선언 폭이 기존 21바이트 WMI 프레임에 대응하는지 고정된 일치/불일치/미확정 분류로 비교합니다. 원시 폭·주소·오프셋·길이는 내보내지 않고 실제 영역을 접근하지 않습니다.
   - 여러 대상이나 서로 다른 폭이 관측되면 혼합·미확정 범주로 남깁니다. 일부 대상의 일치를 단일 true로 확대하지 않습니다.
   - 폭 일치는 선언 형태의 일치일 뿐 정확한 바이트 배치·런타임 변환·실행·프로토콜 의미를 보장하지 않습니다. 불일치가 나와도 입력 바이트를 자동 수정하지 않습니다.
2. **직접 Store의 입력 역할과 Region 선언 관계 요약**
   - 후보에서 Arg0·Arg1·Arg2·상수·기타 표현식 중 어떤 종류가 Field Store의 직접 원천인지 구분합니다. 값 전파·계산·별칭·분기·실행 순서는 평가하지 않습니다. 특정 Arg1 저장 구문이 존재한다고 현재 결과만으로 가정하지 않습니다.
   - 후보의 저장/반환 Field와 보조 Store Field가 동일한 관측 OperationRegion 정의에 연결되는지 비교합니다. 같은 선언과 같은 물리 주소는 별개이므로 물리 영역 동일성·겹침을 추론하지 않습니다.
   - 이 정보를 합쳐 정적 프레임 통로를 요약하되 SystemIo 구문을 SMI 실행이나 배터리 명령 지원으로 승격하지 않습니다.
3. **보고 문구와 회귀 검증 보완**
   - 참조 발생 횟수, 선언 종류 분류, 실행 중 값/관계 미확정, 전체 정의 탐색의 Partial을 분리해 보여줍니다. 지표의 숫자만 지우거나 전체 Partial을 없애는 것을 목표로 삼지 않습니다.
   - 잘못된/과도한 Field 길이, 미지원 목록·Region 해소, 중복·가림·동적 생성·부분 탐색에서의 false 확정 방지, 원문 비노출을 합성 입력으로 검증합니다.
   - 기존 두 Windows 읽기 API·DSDT/첫 SSDT·메모리/노드/시간/참조 상한과 무호출·무쓰기 경계를 유지하고 빌드·관련 테스트·배포 검증을 수행합니다.
4. **모델별 Windows 명령 계약과 대조**
   - 프레임 선언·입력 역할·전달 통로가 확인되면 기존 서비스 wsabi의 21바이트 규약 및 저장된 SABI 분석과 대조합니다. x64 Sabi3의 다른 호출자 ABI나 Linux 명령표를 그대로 대입하지 않습니다.
   - 현재 모델/BIOS에서 배터리 명령과 FF를 정의하는 별도 정적 근거가 확보되지 않으면 제어를 활성화하지 않습니다. 구조 확인만으로 FF를 OFF/ON·미지원으로 바꾸거나 새 명령을 시험하지 않습니다.

이번 단계에는 v5 반복 실행·관리자 비교·기존 TXT/DLL/EXE·원본 ACPI 재제출이 필요하지 않습니다. 후속 구현이 실제로 새 정보를 제공하고 검증됐을 때 필요한 새 요약만 확인합니다. 의미를 입증하지 못한 채 같은 진단만 반복하는 방식으로 진행하지 않습니다.

## 이번 작업 범위

사용자 요청에 따라 결과 분석과 계획만 기록했습니다. 실행 코드·정책·예약·배포 ZIP은 변경하지 않았고 새 빌드·테스트·Windows/OEM/AML 실행도 하지 않았습니다. 398개 테스트·Python 26개·빌드 경고/오류 0개는 직전 코드 검증 기록입니다. 완료된 1회 OEM 실험은 재실행하지 않고 예약 표식을 유지합니다.
