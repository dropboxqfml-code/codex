# 배터리 보호 설정 접근 후속 분석 — 2026-11-06 한국 시간

**후속:** [조회 테이블·캡슐 ACPI와 요청 범위 보강](FIRMWARE_QUERY_BOUNDARY_UPDATE.md)을 완료했습니다. 아래 당시의 프로그램·테스트 미변경 기록과 달리, 후속에서는 순수 encoder 지원 범위와 회귀 테스트를 수정했습니다. 실제 보호 설정 접근은 계속 미구현입니다.

**같은940X3G 계열의 과거 공식 원본에서 배터리 호출자를 확인했지만, 실제 보호 설정 조회는 아직 구현하지 못했습니다.** 공식 목록의 추가 원본2개와 기존에 남겨둔 간접 등록·포인터 별칭·동적 BIOS 화면 경로를 확인했습니다. 충전 제한은 `Unsupported`이며 앱·EXE·기존 ZIP은 변경하지 않습니다.

[직전 분석](CONTROL_CONTRACT_CLOSURE_REVIEW.md)에서 확인한 파일 설정과 실제 장치 재조회의 차이는 그대로 유효합니다. 삼성 EXE/DLL/UEFI/AML을 실행하거나 로드하지 않았고, 실제 장치·EC·포트·물리 메모리·펌웨어 변수·레지스트리·서비스·실험 예약 표식에 접근하지 않았습니다. 원본·서버 응답·전체 디스어셈블리는 비공개 캐시에만 보존합니다.

### 현재 계열2.0.0.78의 실제 배터리 호출자

| 새 파일 | 바이트 | SHA-256 |
| --- | ---: | --- |
| CmdServer/SUS.dll 1.0.5.7 x86 | 1,748,800 | `af60885562766d1cbc8d5886b986b9918738dae084c934e511438c7381c3628f` |
| EasySettingsCmd.dll | 1,156,416 | `3f83824c610b50a69fa3f671acbfdd9a776ddecfc6765f3a8f845a96c0bdc1b7` |

새 SUS는 비교2.0.0.89의 같은 표시 버전1.0.5.7과 실제 바이트가 다릅니다. Win7/Win8 분기 안의 위 두 파일은 각각 같은 SHA이며, 서로 다른 기존 변형의 RVA를 재사용하지 않고 검토했습니다. 반면 SOSI/SUS1.0.6.1 x86/x64는 기존 SHA와 같아 검증한 분석을 재사용했습니다.

- getter `FEC0→CC20`은16바이트 버퍼로0B를 호출하고 첫 바이트 bit3와 API 반환의 **AL만** 검사합니다. 이 gate를 통과하면 같은 버퍼의 첫 바이트만80으로 바꾸고65를 호출합니다. 전체 API 오류 검증이 아니며,65 API 결과는 검사하지 않습니다. 첫FF→소프트웨어2,01→1,그 외→0으로 분류하고 함수 자체는 정상1을 반환합니다.
- setter `FE80→CB90`은66/81 또는80을 보내지만 API 결과를 후속 helper 반환으로 덮고 정상1을 반환합니다(`CC0F`). 후속 `5FB0/62C0`의 `conf.ini` 직접 참조·`nValue` header·DoNotAsk(-2) 연결을 확인했습니다. 전체 하위 CRT/locale 그래프를 닫은 증명은 아니지만 정상 반환이 검증된 보호 상태 비교에 조건부가 아니라는 점은 확인했습니다.
- Cmd의 RTTI/vtable·IAT를 실제 바이트로 연결했습니다. enable/disable은 setter 반환 뒤 소프트웨어 캐시를 갱신하고, SupportBLEMenu는 getter 반환과 상태2 여부로 메뉴 지원을 캐시합니다. 실제 장치 재조회와 요청값의 일치를 확인하는 조건은 없습니다.
- `SetCountFile`은 로컬 INI 조건에서 getter 뒤 setter0으로 이어질 수 있습니다. 원본 앱 실행을 읽기 전용 진단으로 취급하지 않습니다.

이제 배터리 caller가 다른 비교 모델에만 있다는 한계는 좁혔습니다. **같은 계열의 과거 배포 원본에 존재했던 호출자**를 확보한 것이며 현재 Windows10에서 선택되는 DLL·P05ACJ 처리자·응답 의미·보호 설정값을 확인한 것은 아닙니다. 과거 단발에는 선행0B와 전체 응답 기록이 없어 입력/결과 동등성도 여전히 미확정입니다.

### 후속2.2.0.21과 기존2.2.0.18의 대조

SUS x86/x64·Sabi3·wsabi의 대응 파일은 기존 원본과 전체 SHA가 같습니다. ModuleSABI는 raw SHA가 달라도 `.text`는 같고 `.rdata`만 다릅니다. 같은 표시 버전을 코드 동일성의 근거로 사용하지 않고 실제 바이트를 대조했습니다.

ModuleBatteryMgr는47,936바이트/SHA-256 `c5c09c1fcc3dab074209d75859ab5e67022ba06f38d6faf61e2da28099acbfcb`로 바뀌었고 `ReInstallBatteryMgr` export가 추가됐습니다. 확인한 새 본문은 Windows 전원계획의 재가져오기·활성화·manager 레지스트리 정리로 연결됩니다. 이것을 보호 설정 조회로 해석하거나 실행하지 않았습니다.

CommandMNPowerManagement의26개 factory와 생성자→RTTI 연결도 대조했습니다. factory 바이트는 같고, 확인한 `.text` 차이는 기존 `.rdata` 주소 이동이며 분기·호출 대상 추가는 없습니다. USB·Office·Eco·Support/Default 명령 범위에서 새 배터리 보호 경로를 확보하지 못했습니다. 이 한정 대조를 패키지 전체·실제 런타임의 동작 부재로 확대하지 않습니다.

## SABI 등록 인자의 구체적 복원

고정한 SecSabiDispatch는 29,952바이트, SHA-256 `2795669f18e3fb787d908ba00e2e9da7ab7d398ee599f27aa2f068129b46f310`입니다. 다음은 이 파일의 RVA이며 장치 주소나 실행 절차가 아닙니다.

이전에는 초기화 테이블의21개 진입점과 제한된 명령 추적을 기록했습니다. 이번에는 그21개와 추가 helper2개의 본문에서 상수·스택 인자 흐름을 추적했습니다. 단순 즉시값뿐 아니라 계산된 selector 구성도 포함했습니다.

| 집계 | 결과 | 의미 |
| --- | ---: | --- |
| 검토한 초기화 진입점 / 추가 helper | 21 / 2 | 본문23개; 임의의 모든 하위 함수 분석은 아님 |
| SABI receiver를 확인한 등록 호출 위치 | 21 | 초기화 진입점21개와는 다른 집계 |

대표적으로 `BC8→C49`의 descriptor 루프와 `2108→213D`의 일반 등록, helper `ED8→1100`의78, `17E8→1A48`의67/68을 독립 검산했습니다. 기존 외부 등록10개·직접 참조6개·GUID 포함 후보34개를 새 발견으로 다시 세지 않습니다.

56개는 **정적 구문에서 복구한 후보 목록**입니다. 해석하지 못한 호출을 거친 데이터는 후보로만 보존하며, 그 호출의 메모리 변경·별칭·다른 하위 함수·외부/동적 등록을 모두 닫지 못했습니다. 실제 부팅 시 등록 성공이나 전체 런타임 테이블56개를 입증한 결과가 아닙니다. 새 배터리 handler를 찾지 못한 사실도 전체 펌웨어의 기능 부재로 확대하지 않습니다.

## 비슷한 별도 프로토콜을 SABI와 분리

`d32d4d3d-…` 프로토콜의 실제 생산자를 SecSwSmiDispatch에서 확인했습니다(SHA-256 `fc8d0f6968b18843243dd906104fba88770ccb73c8adf4a8e559bcdd08d11c9a`). 공개 interface는 allocation+8이고, method0=`2A0` / method8=`2D4`는 **1바이트 selector·24바이트 항목의 별도 테이블**을 사용합니다. UInt16 main/sub와16바이트 슬롯을 쓰는 SABI 테이블과 구분됩니다.

동일 helper 안의 이 프로토콜 호출과 뒤의 실제 SABI 호출을 분리했습니다. 가까운5843/67/68 상수나 함수 형태만으로 같은 테이블이라고 판단하지 않았습니다. 확인한 생산자 본문은 SABI로 일반 전달하는 wrapper가 아니지만, 모든 하위 callback의 전이까지 닫은 것은 아닙니다. 이 프로토콜을 배터리 대체 경로로 사용하지 않습니다.

## 지원 flag의 포인터 흐름과 객체 위치

기존 외부 소비자4개의 SABI lookup 출력11개를 추적했습니다. 검토한 caller에서 추가 전역·heap·local helper 별칭은 복구하지 못했습니다. SwSmi의 두 guard 출력은 후속 helper가 읽지 않는 stack 위치에 남으며, 다른 삼성 모듈6개의 같은 offset 호출8개는 RuntimeServices 또는 다른 GUID의 receiver로 구분했습니다. 같은 method offset만으로 새 SABI setter로 세지 않습니다.

객체 위치도 명확히 했습니다. 공개 interface는 `parent+10`이고 flags는 `interface+30..34 = parent+40..44`입니다. **parent+30은 dispatch 함수 slot**이므로 이 위치의 쓰기를 flag 변경으로 해석하면 안 됩니다.

generic setter는 여전히 caller의5바이트를 그대로 받을 수 있습니다. 알려진 마스크가 입력 snapshot의 bit3를 보존한다고 해서 현재 장치의 bit3가 불변이라는 뜻은 아닙니다. opaque method의 포인터 보존, 임의 계산 별칭·간접 쓰기·복수 인스턴스와 설치된 이미지 동일성은 미해결입니다. 새 bit3 변경 caller나 현재 장치의 flag 값을 확인한 결과가 아닙니다.

## BIOS 화면의 동적 GUID 처리

기존 HII의 vendor GUID opcode34개를 분류했습니다. 20개는03/04를 포함하는3바이트 payload이고, 나머지14개는 다른 CheckBox 내부의 동일한4바이트 payload `78 56 34 12`입니다.

새로 연결한 실제 소비자는 AMITSE입니다(567,808바이트, SHA-256 `8a353ee2a2ef589790042aa3776ef1b9aabdbb7fb681d4bb5a139e11831d0991`). `1C604`는 GUID를 stack에 조립하므로 연속16바이트 GUID 검색만으로 찾기 어렵습니다. 직접 caller `19696–196AC`는 CheckBox에 한정해 helper의 결과0A/1F를 로컬 control 필드에 저장합니다. 이 helper는 payload나 배터리 문자열 토큰77/78을 읽지 않습니다.

Setup의 GetString helper 직접 호출13개와 NewString helper 직접 호출2개도 대조했지만, 배터리 question·설정 필드·65/66으로 연결하지 못했습니다. 간접·데이터 기반 토큰과 런타임 ID는 남아 있으므로 숨은 기능 전체의 부재를 주장하지 않습니다.

같은 단순 검색의 한계를 확인하기 위해 SABI GUID의 정확한4바이트 조각도 실행 섹션에서 선별했습니다. 고유 PE229개 중 전체 GUID가 없는195개에서는 해당 조각 매치가 없었습니다. **이는 정확한 바이트 선별 결과일 뿐**, WORD/BYTE 혼합·변환·계산으로 만든 GUID나 간접 참조의 부재 증명이 아닙니다.

## 현재 OEM의 import 경계

Settings 2.2.0.18의 파일260개를 길이·해시로 다시 고정하고 PE158개의 ordinary/delay import를 검사했습니다. SUS를 정적으로 import하는 것은 EasySettingsOpenCmd x86/x64이며, 각5개는 무선 LAN 관련4개와 모델 SKU 함수1개입니다. import 이름에서 BatteryLifeExtender 함수를 관측하지 못했습니다.

이 결과는 SUS 안에 배터리 export가 있다는 사실과 현재 앱의 실제 호출을 구분하는 보조 근거입니다. ordinal·동적 바인딩·실행 시 등록/설정의 부재를 뜻하지 않으며, 현재 장치의 보호 기능 부재로 확대하지 않습니다.

## 구현 판단과 남은 조건

현재 근거에는 다음 연결이 여전히 빠져 있습니다.

1. 현재 모델에서 배터리 명령을 처리하는 handler와 선행 조건.
2. 전송 오류와 구분되는 보호 설정 응답의 의미.
3. 실제 설정을 신뢰할 수 있게 다시 읽는 방법.

이번에 복구한 목록·화면 분류·별칭 제외는 위 연결을 대신하지 못합니다. 첫FF, ACK AA, OEM의 정상 반환1/0x63, INI/UI 상태, 초기 flag도 실제 보호 상태가 아닙니다. 기존 승인 단발의 응답을 복원하거나0B/65를 재실행하지 않습니다.

실제 제어를 구현할 다음 착수 근거는 구체적인 배터리 handler/응답 계약 또는 이를 연결하는 새 모델별 제조사 자료입니다. 같은 후보 목록·GUID·첫FF를 반복 세분화해 기능 진전으로 보고하지 않습니다. 기능 접근이 미구현인 현재 상태와 하드웨어의 영구 미지원 판정도 구분합니다.
