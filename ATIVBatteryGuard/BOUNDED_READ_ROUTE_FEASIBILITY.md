# 보호 상태 조회 경로의 성립 조건 — 2026-11-07 한국 시간

**보호 모드 저장값을 읽는 정적 경로는 있습니다. 현재 노트북에서 안전하게 호출해 최신 값을 받는 계약은 아직 완성하지 못했습니다.** 이번에는 전용 삼성 getter 탐색만을 필수 조건으로 두던 기준을 수정하고, 기존 범용 읽기 경로를 제한해 사용할 가능성과 펌웨어 내부 동기화를 검토했습니다. 실제 보호 상태 조회·충전 제어 성공을 보고하는 문서가 아닙니다.

[기존 Windows 중계 연결](EC_READBACK_AND_WINDOWS_BRIDGE.md)과 [오류·신선도 분석](EC_FRESHNESS_AND_ERROR_PATHS.md)의 후속입니다. 저장된 원본을 데이터로만 읽었습니다. EC 해석은 기존 Intel 8051 호환 명령어·bank 모델을 전제로 하며 공식 칩 정의나 현재 설치 이미지 확인을 대신하지 않습니다.

## 확보된 경로와 아직 확보하지 못한 계약

| 구간 | 확인한 내용 | 아직 필요한 근거 |
| --- | --- | --- |
| Windows → WMI → 펌웨어 callback | 기존 OEM 호출자, 공유 프레임, 등록 코드의 정적 연결 | 현재 부팅의 해당 등록·gate·경로 적합성 |
| callback → EC 저장값 읽기 | 조건부 EC 모델에서 요청한 저장 바이트를 읽고 결과 한 바이트를 갱신 | 선택한 조회가 실제 처리됐고 반환값이 그 결과라는 입증 |
| 저장된 보호 모드 → 충전 정책 | 이전 분석의 80/75 비교·억제/복원 요청 | 충전기 쓰기 성공·실제 충전 변화·현재 장치 적용 |

따라서 문제를 ‘전달 경로 자체가 없다’고 표현하면 부정확합니다. 남은 핵심은 **현재 장치 적합성, 요청과 결과의 대응, 오류 처리**입니다. 전용 OEM getter는 가능한 해결책 중 하나입니다. 기존 범용 읽기를 고정된 대상에 제한하고 같은 계약을 입증하는 방식도 논리적으로 배제하지 않습니다. 이는 범용 주소 입력 UI나 실제 호출 코드를 추가할 허가가 아닙니다.

## 요청 내용 비교가 해결하는 부분

기존 일반 중계의 상위 송수신 helper는 첫 송신 반환값을 검사하지 않고 두 번째 대기를 수행합니다. 이전 작업이 그 사이 끝나면 새 요청을 게시하지 않은 채 예전 데이터를 정상으로 복사할 수 있습니다.

선택한 읽기 본문은 결과 한 바이트만 갱신하고 나머지 메시지 내용을 보존합니다. 이 성질을 이용하면 **기존 메시지에 없고, 재사용되지 않으며, 다른 작성자가 기록하지 않는 요청별 표식**의 비교로 위의 ‘새 업로드 생략’ 경로를 검출할 수 있습니다. 비재사용만으로 미관측 기존 내용과의 불일치가 보장되지는 않습니다. 이 전제와 충돌 문제를 생략해 결정적인 증명으로 쓰지 않습니다.

입력 그대로의 결과를 거부하면 업로드 후 선택한 결과 바이트가 바뀌지 않은 경우도 걸러낼 수 있습니다. 두 검사는 특정 잘못된 응답을 거부하는 근거입니다. 현재 프로그램에 표식 생성기·프레임 구성·검증기·실제 backend를 추가한 것은 아닙니다.

표식은 **EC가 생성한 완료 번호가 아니라 호스트가 넣은 내용**입니다. 다른 생산자가 표식을 남겨둔 채 결과 바이트만 바꾸는 경우까지 배제해야 합니다. 원본에는 메시지를 보존하는 명령 게시 경로와 첫 바이트만 갱신하는 다른 생산자가 있습니다. 이들이 해당 교환에 끼어들 수 있다면 잘못된 결과가 수용되는 조건부 반례가 성립하지만, 이번에 그 동시 도달이나 실제 race를 입증한 것은 아닙니다. 반대로 그런 배제가 미완료라는 이유만으로 범용 읽기의 실현 불가능을 단정하지도 않습니다. 선택한 reader가 나머지 내용을 사용하지 않는다는 사실도 현재 이미지의 다른 처리자에 그 내용을 넣어도 안전하다는 증거는 아닙니다.

## 새로 확인한 SMM 동기화의 범위

저장된 P05의 `SmmDispatcher.efi`에는 CPU 도착 계수와 leader/worker 분기, 참여 CPU 사이 장벽, 동기적인 등록 handler 호출이 있습니다. 기존 ACPI mutex나 Windows의 협력 mutex만 있었던 것은 아닙니다. 같은 handler 목록의 동기 순회와 참여 CPU에 대한 동기화는 실제 소스 근거로 인정합니다.

SMM 진입·등록 제공자·하위 분배·SABI callback의 선택 소스 연결도 대조했습니다. 초기화와 등록이 성공한다는 전제에서 같은 root/child 목록의 다음 handler는 앞선 callback이 반환한 뒤 호출됩니다. 단순한 목록 순회만으로 선택한 조회 도중 다른 sibling handler가 실행된다고 가정하지 않습니다.

다만 모든 설정 CPU의 도착을 기다리는 두 구간에는 대기 한도 소진 후 계속 진행하는 분기가 있습니다. 이후 장벽은 현재 도착 수를 기준으로 합니다. 이 코드만으로 **모든 host CPU와 모든 메시지 작성자를 교환 내내 배제한다**고 결론 내릴 수 없습니다. 미참여 CPU가 실제 Windows 코드를 실행했다거나 데이터 경합이 발생했다는 관측도 아닙니다.

참여한 보조 CPU도 항상 아무 작업 없이 멈추는 것은 아닙니다. 분배기가 유지하는 CPU별 작업 슬롯의 함수가 실행될 수 있습니다. 해당 API를 통한 EC 작성자 등록은 이번에 입증하지 못했으므로 이를 실제 충돌로 보고하지 않습니다.

또한 저장된 ACPI 메서드의 입력 저장과 최종 반환은 SMM callback 바깥입니다. SMM 내부 동기화가 이 전체 구간을 자동으로 잠그지는 않습니다. 기존 Windows DLL의 mutex 역시 참여하는 호출자 사이의 규약입니다. 실제 장치의 CPU 도착·잠금 참여·동시 실행을 관측하지 않았습니다.

WMI 응답에는 위 CPU 도착·장벽 상태가 노출되지 않습니다. 정상 WMI 반환만으로 모든 CPU의 참여를 확인할 수 없으며, host CPU 동기화 자체가 별도로 동작하는 EC의 결과 생산자를 멈추는 것도 아닙니다.

## 다음 구현의 구체적인 기준

범용 경로를 계속 검토할 경우 다음 연결을 하나의 계약으로 입증해야 합니다.

1. 현재 모델·이미지에 맞는 읽기 대상과 처리자를 고정하고 인접 쓰기 경로를 제외합니다.
2. 요청 준비부터 결과 복사까지 다른 작성자와의 관계를 확인하고, 새 게시가 생략된 경우와 다른 생산자의 결과를 구분합니다.
3. 실패·불명확·입력 echo를 실제 보호 상태로 승격하지 않고 종료합니다.
4. 모드 한 바이트의 조회와 임계값 여러 바이트의 조회를 구분합니다. 여러 요청의 성공이나 같은 Windows 잠금만으로 원자적 스냅샷이 되지는 않습니다.

저장된 모드·임계값을 확인하더라도 충전기 적용 성공은 별도입니다. 이전 분석의 설정 handler는 이미 같은 활성 모드일 때 임계값을 다시 쓰지 않으며, 일부 충전기 쓰기는 하위 성공 상태를 검사하지 않습니다. 저장값만으로 ‘80% 제한 적용됨’을 표시하지 않습니다.

같은 모델의 남은 지원 패키지 세 종류도 목록과 기존 호출자를 대조했습니다. 선택한 Support Center 호출은 파일 유무 검사·기존 창 활성화·프로그램 실행이며 보호 설정 조회 API로 연결되지 않았습니다. 미확보 패키지 내부의 기능 부재를 뜻하지 않으며, 새 배터리 단서 없이 대용량 지원 도구를 받거나 실행하지 않았습니다.

## 검증과 현재 프로그램

원본 해시·선택 분기·데이터 범위와 위의 조건부 논리를 별도로 교차 검토했습니다. 정제한 범위와 결과는 [검사 기록](reports/bounded-read-route-feasibility-audit.json)에 저장했습니다. 정적 소스 검사이며 앱 테스트나 실제 장치 관측이 아닙니다.

이번 변경은 분석 문서와 검사 기록입니다. C#/WPF·Python 개발 도구·실행 파일·기존 ZIP은 변경하지 않았고 빌드·단위 테스트는 재실행하지 않았습니다. C# 437개·빌드 경고/오류 0개는 이전 `5d77df5`, Python 88개는 이전 `e7b067a` 검증 기록입니다.

실제 제어는 계속 Unsupported입니다. 원본 실행·에뮬레이션·하드웨어/OEM 호출·기존 단발 예약 접근·드라이버/서비스/보안·펌웨어 변경은 없었습니다. 원본 바이너리·전체 디스어셈블리·물리 주소를 담은 분석 기록은 비공개로 보존하며 실행용 요청은 만들지 않았습니다. 이번 단계에서 새 프로그램 실행이나 동일 자료 재제출은 필요하지 않습니다.
