# 첫 Windows 배터리 관찰 결과와 충전 제어 검증 순서

2026-11-09 한국 시간. 기준 `37a18d5`. 사용자 관찰 TXT는 데이터로만 분석했으며, 사용자는 관찰 중 충전기를 연결하지 않았다고 확인했습니다.

## 이번 결과

| 항목 | 관측 |
| --- | --- |
| 기록 상태 | 사용자 중지 |
| 샘플 | 16개, 시작 후 5초부터 265초까지 |
| 배터리 잔량 | 첫75%, 마지막74% |
| 외부 전원 | 16개 모두 `Disconnected` |
| 충전 상태 | 16개 모두 `Discharging` |
| 품질·읽기 오류 | 모두 `Observed`, 오류 표시 없음 |
| 긴 갱신 간격 | 30초 초과 간격0개, 실제 샘플 간격10~20초 |

프로그램의 배터리 기록과 로컬 TXT 저장은 사용자 노트북에서 동작했습니다. 이번 파일에는 **AC 연결 상태의 샘플이 없으므로 충전 상한 억제·충전 재개를 평가할 기회가 없습니다.** 이 결과를 충전 제어 실패나 성공으로 판정하지 않습니다. 샘플 사이를 보간하거나 전체265초를 연속 관측 시간으로 세지 않습니다.

직전 설정 시험이 보고한 `0 / 0 / 0 → 1 / 80 / 75`, SDK7/set1·정리Complete는 그때의 저장 후보 전환 기록으로 유지합니다. 새 방전 기록은 지금도 보호 모드1이 유지되는지 재조회한 자료가 아닙니다. 재부팅·절전·그 밖의 초기화 뒤 지속성도 이 기록으로 확인하지 않았습니다.

## 충전 제어에 바로 필요한 관찰

현재 [관찰판](../downloads/ATIVBatteryGuard-BATTERY-OBSERVATION.zip)을 그대로 사용합니다. 새 프로그램·추가 설정·OEM 조회·시험 예약은 필요 없습니다.

1. 평소 사용하는 충전기를 노트북에 연결하고 Windows 배터리 표시가 AC 연결로 바뀌는지 확인합니다. 실제 연결했는데 계속 연결 안 됨으로 표시되면 그 사실을 먼저 알리고, 이를 보호 동작으로 해석하지 않습니다.
2. **새 관찰 시작**을 누르고 평소처럼 사용합니다. 시작 버튼 자체는 추가 조회를 하지 않습니다. 이미 생성된 과거 TXT를 붙여넣는 단계는 필수가 아닙니다.
3. 충전 진행과 상한 근처 상태가 기록되면 **관찰 중단 → 관찰 TXT 저장을 한 번** 누릅니다. 충전하지 않거나 잔량이80%를 넘어가더라도 설정 시험을 재실행하거나 자동으로 토글하지 않습니다. 충분한 관찰 길이는 실제 진행 속도에 따라 달라지며 이번 기능의 한 세션은 최대2시간입니다.
4. 저장 파일은 `%LOCALAPPDATA%\ATIVBatteryGuard`의 새 `battery-observation-*.txt`입니다. 이번 버전은 저장할 때마다 새 파일을 만듭니다. 같은 내용을 여러 번 저장할 필요는 없습니다.

현재 잔량이 과거 기록처럼74~75%라면, AC 연결 뒤 충전 진행과 이후 상한 근처 동작을 한 번에 살펴볼 기회가 있습니다. 이 숫자를 현재 잔량으로 가정하거나 시험을 위해 강제 방전·재부팅·반복 충전하지 않습니다.

| 기록에 나타나는 상황 | 가능한 해석과 다음 판단 |
| --- | --- |
| AC 연결·충전 중·잔량 상승 | Windows가 충전 진행을 보고함. 보호 설정의 현재값이나 상한 억제는 아직 미확인 |
| AC 연결 상태에서80% 근처까지 상승한 뒤 충전 중 아님 표시가 이어짐 | 분석된 상한 정책과 일치하는 Windows 동작 정황. 온도·충전기·배터리 조건 등 다른 원인을 배제한 단독 증거는 아님 |
| AC 연결 상태에서80%를 넘겨 계속 상승 | 관찰 기간에 기대한 상한 억제가 드러나지 않음. 현재 저장 모드 유지 여부와 적용 조건을 구분해 후속 검토하며 재설정하지 않음 |
| AC 연결이지만75% 이하에서도 충전하지 않음 | 별도 배터리 유효성·상태 조건이 있어 이 한 현상만으로 모드 오류를 단정하지 않음 |
| AC 미연결·Unknown·긴 갱신 간격 | 해당 구간에서 충전 제한 효과를 판정하지 않음 |

기존 EC 분석에서는 보호 모드·임계값을 EC의 배터리 polling 정책이 소비합니다. 모드가 활성이고 유효 잔량이 상한 이상이면 억제 요청으로, 하한 이하에서는 추가 유효성·배터리 상태 조건을 통과해야 재개 요청으로 이어집니다. 설정 뒤 앱이 setter를 반복해야 한다는 근거는 없습니다. 충전기 쓰기 요청의 소프트웨어 기록도 각 버스 쓰기의 성공이나 전기적 결과를 보증하지 않습니다.

## 다음 실제 제어 개발

보호가 켜진 상태의 AC 관찰을 먼저 보존하고, 이후 **별도 승인된1→0 해제와 같은 AC 조건의 충전 경과**를 비교합니다. [보호 해제 도구의 구체 구현안](PROTECTION_1TO0_IMPLEMENTATION_PROPOSAL.md)을 작성했습니다. 사전모드1 → 설정0최대1회 → 사후모드0의 최대3SDK안이며, 임계값·현재 충전 재개·100% 충전 성공을 추론하지 않습니다.

이 순서는 보호 모드 저장, Windows 충전 표시, 충전기의 실제 동작을 나눠 확인하기 위한 것입니다. 지금 보호를 먼저 끄거나 기존 ON 시험을 반복하면 현재 ON 상태의 동작을 비교할 기회를 잃을 수 있습니다. 새 해제 도구는 아직 구현·승인·배포하지 않았습니다. 일반 GUI의 실제 보호 조회·제어는 `Unsupported`입니다.

## 저장 UI 피드백과 이번 변경 범위

사용자는 저장 폴더를 여는 동작을 찾지 못했고 저장 완료 표시를 인식하기 어려워 여러 번 눌렀으며, 같은 위치에 TXT가 수십 개 생겼다고 보고했습니다. 관찰 카드 근처의 폴더 열기, 눈에 띄는 저장 완료·파일명 표시, 같은 기록의 불필요한 중복 저장 방지를 후속 수정 항목으로 남깁니다. 충전 제어가 우선이라는 요청에 따라 이번에는 UI나 저장 동작을 수정하지 않았습니다. 이미 생성된 파일의 삭제도 하지 않습니다.

이번 변경은 결과 분석·제어 시험의 구체 설계·정제 기록입니다. 실제 펌웨어 호출과 프로그램 변경은 없고 기존 EXE/ZIP도 보존했습니다. 빌드·C# 회귀는 반복 실행하지 않았으며 **887개 통과·두 Release 빌드0경고/0오류는 `37a18d5`의 이전 검증**입니다. 새 자료의 오프라인 CSV 정합성·샘플 집계와 문서·기존 소스 보존 검증은 이번에 수행했습니다. [정제 검토](reports/charge-effect-and-off-proposal-review.json)에 결과를 남겼습니다. 같은 TXT·진단·삼성 DLL·EXE를 다시 제출할 필요는 없습니다.
