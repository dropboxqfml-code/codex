# 현재 OEM 후속 처리와 P05ACJ 전체 볼륨 대조 — 2026-11-06 한국 시간

**후속:** [간접 등록·flag 별칭·동적 화면 감사](BATTERY_PROTECTION_ACCESS_FOLLOWUP.md)에서 남은 경로를 더 구체적으로 대조했습니다. 후속에서도 실제 보호 상태 접근은 미구현이며 실행 파일은 유지합니다.

**현재 계열 OEM의 후속 처리를 확인했지만, 실제 충전 제한을 구현할 근거는 아직 부족합니다.** 후속 helper는 팝업용 INI 설정이며 장치 보호 상태의 재조회가 아니었습니다. 저장한 P05ACJ의 나머지 볼륨과 제조사 매뉴얼도 확인했습니다. 실제 제어는 계속 `Unsupported`이고 실행 파일은 변경하지 않습니다.

이 문서는 [현재 계열 배포 원본 검토](CURRENT_MODEL_OEM_EVIDENCE_UPDATE.md)의 후속입니다. 삼성 EXE/DLL/MSI/UEFI/AML을 실행하거나 로드하지 않고, 저장 파일의 구조·기계어와 공개 제조사 문서만 데이터로 분석했습니다. 원본과 전체 디스어셈블리·서버 응답은 저장소 밖 비공개 캐시에 보존합니다.

## 1. 현재 SUS의 후속 처리는 장치 read-back이 아닌 파일 설정

Settings 2.2.0.18의 실제 파일을 고정했습니다. `SOSI`는 배포 디렉터리 이름이며 분석 대상은 그 안의 **SUS.dll 1.0.6.1**입니다. 이전 비교용 SUS 1.0.5.7/CmdServer와 혼합하지 않습니다.

| 대상 | 바이트 | SHA-256 |
| --- | ---: | --- |
| SUS 1.0.6.1 x86 | 1,741,104 | `c6a3e78ab6a4899c76e2cac5d816f8dc86a3596518bfa8a45c379e2a10b9ee95` |
| SUS 1.0.6.1 x64 | 2,365,744 | `d471164bd5a997bed4620121188f0b18d246c1532bd95f76b882d7c4a729d5ac` |

다음 RVA는 각 파일의 ImageBase 기준 상대 주소이며, 실기 메모리에 접근한 주소가 아닙니다.

| 확인한 흐름 | x64 RVA | x86 RVA | 의미 |
| --- | --- | --- | --- |
| SetBatteryLifeExtenderEnable | `10F20` | export `F150` → `C0E0` | 66 호출 뒤 파일 설정 처리로 진행 |
| 후속 읽기 / 쓰기 helper | `5EC0` / `62F0` | `57E0` / `5AF0` | 모듈 폴더의 `conf.ini` 읽기 / 쓰기 |
| setter 정상 반환1 | `10FB7` | `C159` | OEM API 결과나 장치 상태 비교에 조건부가 아님 |
| wrapper 정상 반환 `0x63` | `11D47` | `FAE4` | 별도 소프트웨어 반환값; BIOS ACK와 다름 |
| DoNotAskMe의 파일 값 -2 기록 | `1106B` | `F21A` | 다시 묻지 않기 설정과 같은 파일 경로임을 교차 확인 |

새로 확인한 핵심은 다음과 같습니다.

- x64 읽기 `5EC0`은 `basic_ifstream`, 쓰기 `62F0`은 `basic_ofstream`으로 연결됩니다. RTTI·filebuf 생성자와 파일 열기 모드 `r`/`w`까지 대조했습니다. 파일명만 보고 역할을 추정한 결과가 아닙니다.
- `[BatteryLifeExtender]` 아래 `nValue`는 팝업 카운터·다시 묻지 않기 설정입니다. setter의 -2 비교는 이 파일 값을 보존하는 조건입니다. 원하는 보호 설정과 장치에서 다시 읽은 값을 비교하는 조건이 아닙니다.
- x64의 66 호출 결과는 직후 파일 읽기 helper의 반환으로 덮입니다. 선택적 파일 쓰기의 결과도 검사하지 않은 채 정상 경로에서1을 반환합니다. x86도 같은 결론입니다. 예외·비정상 종료까지 성공한다고 주장하지 않습니다.
- 팝업 helper의 `GetSystemPowerStatus`는 잔량·AC 상태를 사용해 파일 카운터를 갱신합니다. 충전 상한 설정 재조회로 쓰이지 않습니다.

기존 getter 분석도 재확인했습니다. 기본 getter는 소프트웨어 상태2를 출력하면서 함수 자체는1을 정상 반환할 수 있습니다. 0B 첫 바이트의 bit3가 지워진 분기에서 같은11바이트 버퍼로65를 호출하고 응답 첫 바이트를 소프트웨어의0/1/2로 분류합니다. API 오류 검사가 없어 이 분류를 신뢰 가능한 보호 상태로 그대로 사용할 수 없습니다. 이 부분은 기존 사실이며 새 명령 발견으로 세지 않습니다.

과거 승인된 단발은16바이트 WMI 입력을 사용했고 선행0B가 없었습니다. 당시 저장된 응답은 첫FF까지여서 전체 데이터·echo와 현재 caller 입력의 동등성을 확정할 수 없습니다. 새 helper 분석으로 과거FF의 원인이 밝혀진 것은 아닙니다.

로더는 보고된 OS 버전에 따라 `SABI3.dll` / `WSABI.dll` / `SABI2.dll`을 선택하고 `CallBIOSInterface`를 동적으로 연결합니다(x64 로더 `BDC0`, 함수 검색 `BEEA`). 현재 Windows10에서 실제 선택·초기화된 DLL이나 이 노트북의 명령 처리 결과를 관측한 것은 아닙니다. 위 후속 helper 분석은 동적 OEM 함수·전체 CRT/locale 가상 호출의 모든 동작을 닫은 증명이 아닙니다. **확인한 setter의 정상 반환이 검증된 장치 read-back을 전제로 하지 않는다는 결론**만 유지합니다.

## 2. P05ACJ의 나머지 볼륨과 압축 섹션 확인

입력은 이전에 확보한 P05ACJ.cap **5,242,880바이트**, SHA-256 `052660c18e967f7f73b2881379066bde4b90b29192ce4292c8d29bef1ce92ab0`입니다. 이 패키지가 현재 노트북에 설치된 전체 런타임 이미지와 같은지는 미확정입니다.

| 범위 | 추출 파일 | PE 이미지 | 이번에 추가한 범위 |
| --- | ---: | ---: | --- |
| 기존 주 볼륨 FV04 | 251 | 185 | 기존 분석 유지 |
| 나머지6개 볼륨 | 232 | 46 | 새 정적 구조·후보 확인 |
| 전체7개 볼륨 | 483 | 231 | 중복을 제외한 PE 해시는229개 |

새46개 PE는 서로 다른 IA32 PEI/SEC 이미지입니다. 기존185개와도 해시가 다릅니다. PEI/SEC 명칭은 컨테이너·형식 분류이며 실제 실행을 확인한 뜻은 아닙니다.

독립 FFS 파서로 **466개 FFS**의 크기·정렬을 검사하고, 표준 type1 압축 섹션 **390개**를 별도 trusted 데이터 디코더로 해제했습니다. 해제 합계24,857,040바이트이며 **231개 PE 섹션 모두** 7-Zip 출력 파일과 해시가 일치했습니다. 인식한 섹션 트리에 크기 오류·TE·FV_IMAGE·custom GUID 처리 섹션은 없었고, 유효한 중첩 FV도 발견하지 못했습니다.

새 파일232개에는 대상 SABI 프로토콜 GUID의 정확한 바이트가 없었습니다. **새65/66 콜백·등록 경로·bit3 변경 caller는 확정하지 못했습니다.** 기존 FV04의 GUID 포함 후보34개·직접 참조6개·외부 등록10개는 종전 결과이며 새 발견으로 다시 세지 않습니다. 숫자만 같은 상수는 배터리 명령으로 연결하지 않았습니다.

볼륨 사이 **262,144바이트의 raw 구간은 불투명 데이터**로 남아 있습니다. GUID/MZ/VZ 미관측을 빈 공간이나 코드 부재의 증명으로 취급하지 않습니다. 계산·간접·동적 등록, 외부/부팅 제공 모듈, 변환된 데이터와 미인식 실행 형식은 이 구조 검사로 배제할 수 없습니다. 전체 펌웨어의 배터리 보호 기능 부재를 입증한 결과가 아닙니다.

## 3. USB 경로 대조로 확인한 분석 범위

현재 ModuleSABI.dll의 SHA-256은 `7c57ac5a6ce5727766f425c0aa7368ee75be20fdf790b84113b7e9abf2069f12`입니다. USB getter는 첫 바이트의 **bit4**를 검사한 뒤67 경로로 진행합니다(`19DA` → `19DD`의 OR EF → `19E0`의 비교, 67 호출 준비 `1A35`). 실제0B/67 호출은 통신 객체 활성 조건에도 달려 있고,0B 반환 성공 여부는 검사하지 않습니다. setter는68을 사용합니다(입력이 비0일 때 `18AB`,0일 때 `190B`).

P05ACJ의 SecSwSmiDispatch에서 bit4를 EF 마스크로 지우는 초기화와67/68 콜백 등록을 이미 확인했습니다. 이번 대조는 Windows 호출자와 펌웨어 등록의 **USB 선택자·flag 관계가 서로 맞는다는 한정된 확인**입니다. 실제 호출·응답 성공이나 USB 설정 read-back을 검증한 것은 아닙니다.

배터리 caller의 **bit3 및65/66**은 이 USB 관계와 별개입니다. USB67/68, 배터리 보정,7C 설정을 대체 배터리 명령으로 사용하지 않습니다. 초기 flag7F나 입력 snapshot을 보존하는 마스크로 현재 bit3의 값·불변성도 추정하지 않습니다.

## 4. 같은 배포 목록의 제조사 매뉴얼

Model940X3G의 두 WB 목록은 같은 `Win8.1_UserManual_Amor3 2.5.00` 항목을 가리킵니다. 목록 Version1.2.0.0과 MSI ProductVersion2.5.00은 서로 다른 필드입니다. 정상 제조사 리다이렉트로 [BASW-84558A09.ZIP](https://downloadcenter.samsung.com/content/SW/201411/20141121144036765/BASW-84558A09.ZIP)을 받아 ZIP CRC·경로를 검사하고 MSI/CAB를 데이터로만 풀었습니다.

| 대상 | 바이트 | SHA-256 |
| --- | ---: | --- |
| 매뉴얼 ZIP | 129,663,156 | `c9b52af1a2308678d069f038402ffaf898dba3d7759dc4a9f43e39f7c80069d2` |
| 영문 PDF,149쪽 | 16,417,221 | `30b3c8affebace5f8de1ca982910b0d7c3c479a4bc1674769c44e14908e80b48` |
| 국문 PDF,112쪽 | 17,297,976 | `4acdd6a9f065ad31acf2eb89d1891c579d15d9391834399ba34f3299f45c5d0f` |

영문67쪽/국문58쪽은 일반 전원 Settings와 모델·앱 버전에 따른 차이를 설명합니다. 영문58쪽/국문50쪽은 방전·재충전을 통한 **배터리 잔량 표시 보정**입니다. 위쪽수는 PDF 순서와 인쇄 쪽수가 같습니다. 영문 두 관련 페이지는 이미지도 직접 확인했습니다. 보정을 충전 상한 기능이나 실행할 시험으로 제안하지 않습니다.

전체 추출 텍스트에서 Battery Life Extender 또는80/85% 충전 상한 설명을 찾지 못했습니다.80% 검색 결과는 습도 사양이었습니다. PDF 전체 이미지 OCR은 수행하지 않았습니다. PDF 안에940X3G/930X3G 명칭이 관측된 것도 아니며, 현재 계열과의 연결은 배포 목록에서 옵니다. **공통 Windows8.1 매뉴얼의 한정 미관측은 현재 Windows10/P05ACJ의 기능 부재나 명령 의미를 증명하지 않습니다.**

## 현재 결론과 다음 구현 조건

현재 자료로는 충전 제한 제어를 안전하게 추가할 수 없습니다. 이것이 노트북 하드웨어의 영구 미지원을 확정하는 뜻은 아닙니다.

| 필요한 근거 | 현재 상태 | 구현에서의 처리 |
| --- | --- | --- |
| Windows 배터리 잔량·AC 관측 | 실제 노트북 동작 확인됨 | 상태 표시 유지 |
| WMI 전송·프레임 관측 | 과거 단발 기록 있음 | 전송 성공을 보호 적용으로 표시하지 않음 |
| 현재 모델의65/66 처리자·입력 조건·지원 flag | 미확정 | 실제 보호 조회·쓰기 연결 금지 |
| 응답의 보호 설정 의미와 신뢰할 read-back | 미확정 | 첫FF·API1·wrapper63·ACK AA·INI/UI 상태로 대체하지 않음 |
| 설정 요청 뒤 실제 보호 상태와의 일치 확인 | 미확정 | `UnsupportedChargeLimitController` 유지 |

다음 구현에는 현재 모델의 handler 또는 동등한 제조사 근거로 **명령의 의미·선행 조건·전송 실패 처리·보호 상태 응답 계약**을 연결해야 합니다. 특히 원하는 설정과 신뢰 가능한 실제 장치 재조회값을 비교할 수 있어야 합니다. 같은 첫FF 기록·메뉴 유무·수치만 반복 분석해 이 간극이 닫힌 것으로 보고하지 않습니다. 추가 정적 작업은 아직 미해결인 계산/간접 등록·bit3 writer·배터리 처리자에 연결되는 구체적 근거가 있을 때 진행합니다.

## 검증·배포·사용자 확인

이번에는 x86/x64 후속 처리의 독립 대조, 전체 FV/표준 압축 섹션의 독립 해시 대조, 매뉴얼 출처·쪽수·문맥 확인을 완료했습니다. [검사 기록](reports/control-contract-closure-audit.json)에 원본7개와 기존 ZIP2개의 길이·해시 재검산, FV 집계 대조, 변경 문서7개의 링크·문자 검사 결과를 저장했습니다. 독립 보고서 검토에서도 수정이 필요한 오류는 발견되지 않았습니다.

앱·테스트 코드·EXE·기존 ZIP은 변경하지 않았고 빌드/단위 테스트는 이번에 반복하지 않았습니다. C#435개·Python85개와 빌드 경고/오류0개는 직전 프로그램 변경의 검증 기록입니다.

기존 [프로그램 ZIP](../downloads/ATIVBatteryGuard-OEM-CALLER-EVIDENCE.zip)을 그대로 사용할 수 있습니다. 새 실행 파일이나 추가 노트북 확인 항목은 없습니다. 추가 TXT/DLL/EXE 제출·관리자 비교·OEM 호출·보정·예약 접근·드라이버/서비스/보안 변경은 요구하지 않습니다. 과거 단발 실험은 재실행하지 않으며 예약 표식도 읽거나 초기화하지 않습니다. 앱의 일반 권한·네트워크0건·실제 제어 비활성 경계를 유지합니다.
