# EC 명령 게시·선택 구간과 최소 조회 설계 — 2026-11-07 한국 시간

**정상적인 초기화·동기화 조건에서 관련 게시자를 순차화할 근거를 보강했습니다. 보호 모드 저장값만 읽는 설계의 조건은 정리했지만, 현재 노트북의 안전한 실행 계약은 아직 완성하지 못했습니다.** 실제 보호 상태 조회·충전 제어 성공을 보고하는 문서가 아닙니다.

[간섭 후보·실행 순서 분석](EC_QUERY_INTERFERENCE_REVIEW.md)의 후속입니다. 보유 펌웨어와 DLL을 데이터로만 읽었습니다. EC 해석은 기존 Intel 8051 호환 명령어·bank 모델이 전제이며 현재 설치 이미지나 실제 interrupt binding을 확인한 결과가 아닙니다.

## EC 내부에서 명령값을 바꿀 수 있는 경로

새로 연결한 대체 dispatcher poll도 같은 main scheduler의 후속 경로입니다. 현재 연결된 두 poll을 독립적인 ISR 재진입으로 취급하지 않습니다. 선택한 읽기의 종류 판정과 handler 선택 사이에 이 main-thread 경로가 스스로 끼어드는 근거는 없습니다.

지정한 포인터에 쓰는 다른 handler는 명령 슬롯도 주소 범위상 대상으로 삼을 수 있습니다. 그러나 복원한 진입에서는 **그 handler의 선택이 끝난 뒤** 쓰기가 수행됩니다. 이 능력만으로 앞선 종류 판정·선택 구간의 실제 선점 작성자라고 할 수 없습니다. 선택한 인접 주소 형성 경로들도 명령 슬롯에 도달하지 않는 범위로 분리했습니다. 직접 literal 목록의 읽기·zero clear는 기존 문맥이며, 새 자율 실행 nonzero 재게시 경로를 확보한 것은 아닙니다.

한편 다른 handler는 reader에서 사용하지 않는 입력 일부를 쓰기 데이터로 해석합니다. 따라서 ‘입력이 echo와 다르다’는 사후 검사만으로 앞선 부작용이 없었다고 판단할 수 없습니다. 명령·대상 무결성을 실행 전에 확보해야 한다는 조건은 유지합니다. 실제 다른 명령 선택이나 경합을 관측한 것은 아닙니다.

## 펌웨어 게시자의 실제 실행 문맥

| 보유 소스에서 연결한 경로 | 선택한 실행 문맥 | 이번 분류의 의미 |
| --- | --- | --- |
| SecSetupValueToEc | 동기적인 DXE 초기화 | 부팅 단계 게시를 Windows 실행 중 경쟁 작성자로 바로 세지 않음 |
| SecTouchPadDxe | Boot Services protocol notification | 초기화·알림 callback과 전송을 연결했으며 runtime SMM 게시로 분류하지 않음 |
| SecEcDxe | boot 초기화와 SMM 등록 callback을 분리 | 파일 이름만으로 boot 전용이라고 판정하지 않음 |
| SecEcSmiDispatch | SMM 초기화와 등록된 GPI event handler | 일반 SW 호출과 GPI 등록 경로를 구분 |
| SecSwSmiDispatch | 등록된 SMM callback | 실제 제공자·하위 callback·게시 helper를 연결 |
| SecSabiDispatch | 기존 SABI/WMI SMM 제공자 | 이미 연결한 일반 callback·전송 계열과 구분해 집계 |
| SecLagacySabi | SMM callback에서 기존 SABI 제공자로 전달 | 같은 하위 게시자를 별도 새 전송으로 중복 집계하지 않음 |
| Runtime | boot/SMM flash interface 게시와 virtual-address 전환 보존 | 단순 boot 미사용 코드로 제외하지 않되 현재 Windows 호출·동시 실행은 미연결 |

이는 선택한 등록·호출 관계입니다. 초기화 성공·현재 장치의 실제 호출·모든 외부 alias를 입증한 것은 아닙니다. 일부 전송 helper는 busy 상태가 해소된 뒤 메시지·명령을 게시하지만 **busy 확인은 소유권 예약과 다릅니다.** 공유 lock이나 token이 확보됐다는 의미로 해석하지 않습니다.

`Runtime`은 이름만으로 분류하지 않았습니다. entry에서 boot/SMM 초기화와 서로 다른 flash interface 게시로 이어지고, 게시된 메서드가 선택한 flash 장치의 전후 처리 hook을 통해 EC 명령을 게시하는 연결을 확인했습니다. virtual-address-change callback이 해당 hook을 포함하는 함수 포인터 표를 변환하므로 runtime까지 보존되는 경로로 남깁니다. 현재 장치의 probe 선택, OS Runtime Services·Windows 소비자에서 그 메서드까지의 호출, 실제 중첩 실행은 이번에 연결하지 못했습니다. 원본 flash 기능을 실행하거나 대체 조회로 사용하지 않았습니다.

## 정상 SMM 실행 세대의 조건부 순차화

CPU 도착 대기가 한도를 소진한다는 사실만으로 두 root handler가 동시에 실행된다고 결론 내릴 수는 없습니다. 초기화가 완료되고 관련 전역 상태가 유지되는 정상 진입에서는 atomic 선출과 고정된 선택 CPU 분기가 하나의 root 실행을 고르고 다른 참여 CPU를 worker 경로로 보냅니다. 정상적이고 고유한 CPU context와 비재진입을 전제로, 늦게 도착한 CPU가 두 번째 root를 만드는 경로는 이 선택 사슬에서 나오지 않습니다.

새 GPI/SW 제공자의 연결도 명칭만으로 가정하지 않았습니다. 실제 Base2 getter에서 얻은 서비스 테이블→root handler 등록→같은 callback 목록→child의 SW/GPI 분기→등록된 callback의 동기 호출을 연결했습니다. 초기화·등록이 성공하고 위 정상 실행 조건이 유지된다는 전제에서, 이 domain에 연결된 게시자 사이의 순서를 설명할 수 있습니다. 모든 host CPU가 정지해야만 가능한 논증은 아닙니다. 이전에 분류한 AP 작업 전체를 EC 작성자로 다시 가정하지도 않습니다.

다만 초기화·reset 경로와 관련 전역 상태의 다른 변경까지 무조건 같은 정리로 묶지는 않습니다. 실제 Windows 호출 시점의 실행 세대·context·관련 상태를 관측한 것은 아니며 WMI 응답이 그 상태를 증명하지도 않습니다. WMI 입력 저장·최종 반환은 SMM 바깥이고, 직접 port/native 접근이나 비협력 호출자를 이 순차화에 자동으로 포함하지 않습니다.

## 과거 서비스 WSABI의 협력 잠금 연결

제조사 패키지에서 확보한 과거 서비스 WSABI 원본도 현재 Settings의 세 변형과 같은 Global mutex 이름을 사용합니다. 정확한 서비스 원본은 22,920바이트, SHA-256 `564b640d62db2a4e4b56c6331e0e526bad2ac1fcf438a41a9e5241551f457b6e`입니다. 같은 크기의 다른 파일로 대체하지 않았습니다.

서비스의 선택한 일반 호출은 정상 mutex 획득 결과에서만 입력 준비로 진행하고 응답 복사 뒤 잠금을 해제합니다. 새로 확인한 것은 네 원본 사이의 협력 규약이며, 현재 process의 DLL 선택·접근 권한·실제 잠금 참여는 미관측입니다. 다른 잠금 객체를 쓰는 native나 직접 WMI/ACPI 호출자까지 같은 소유권을 갖는다는 증거는 아닙니다. 원본의 무한 대기·abandoned 소유권 처리 누락을 새 구현에 복제하지 않습니다.

## 보호 모드만 읽는 최소 설계의 판정

| 항목 | 설계 요구와 현재 판정 |
| --- | --- |
| 대상·입력 | 근거가 고정된 저장 모드 한 바이트만 후보로 삼고 임의 주소·명령 입력을 제공하지 않음. 현재 이미지 적합성은 아직 미확정 |
| 실행 전 소유권 | 입력 준비부터 결과 회수까지 협력 잠금·실제 충돌 가능한 게시자의 순서를 확보해야 함. 정상 SMM 조건부 근거와 네 WMI 원본의 규약은 보강했지만 전체 실행 계약은 미완료 |
| 응답 대응 | 업로드 생략·입력 echo·불명확 결과를 거부해야 함. 표식은 EC 완료 번호가 아니며 잘못 실행된 명령의 부작용을 되돌리지 못함 |
| 대기·정리 | UI timeout과 하위 작업 완료를 구분하고 소유권을 너무 일찍 반환하지 않아야 함. Windows mutex의 소유 thread와 해제 규칙도 유지해야 함 |
| 결과 의미 | 후보 저장 바이트를 충전기 적용 성공·전기적 충전 중단·임계값 전체의 원자적 조회로 승격하지 않음 |
| 코드 연결 | 위의 현재 모델·입력·소유권 계약이 미완료이므로 실제 호출 backend·실행용 요청을 추가하지 않음. 제어는 Unsupported 유지 |

이 설계는 저장된 모드의 제한 조회를 위한 검토 자료입니다. 전용 OEM getter만을 요구하거나 모든 작성자의 전역 부재를 요구하지 않습니다. 새 실험 승인이나 기존 단발 호출의 재사용 근거도 아닙니다. 남은 핵심은 정상 실행 조건·EC 이미지가 현재 장치에 맞는지와, runtime 보존 flash interface의 실제 OS 소비자 및 협력 규약 밖의 직접 호출자를 어떻게 다룰지입니다. 보존된 hook의 존재를 실제 경합 관측으로 바꾸지도 않습니다.

구현으로 옮길 때의 경계도 고정합니다. 현재 모델·입력·소유권 조건이 미확정이면 메서드를 호출하지 않습니다. 조건이 갖춰진 경우에도 한 작업 thread가 유한 대기로 협력 잠금을 얻어 고정 입력 준비부터 실제 하위 작업 종료·응답 회수까지 소유권을 유지해야 합니다. 비정상 획득 결과에서는 실행하지 않고 OS가 넘긴 소유권의 정리 여부를 따로 처리해야 합니다. UI의 대기 종료를 하위 작업의 종료로 간주해 잠금을 먼저 풀거나 다른 요청을 시작하지 않습니다. 이는 설계 요구이며 해당 코드·실행 경로를 이번에 추가한 것은 아닙니다.

## 검증과 산출물

새 명령-slot·대체 poll 관계, 펌웨어 게시자의 등록·실행 문맥, 서비스 WSABI와 기존 세 원본의 비교, 정상 SMM 세대의 조건부 분기를 검산·교차 검토했습니다. 새 근거와 기존 문맥의 재검산을 [검사 기록](reports/ec-command-ownership-audit.json)에 구분합니다. 기계적인 바이트·decode 검사 수는 앱 테스트나 전체 분석률이 아닙니다.

변경은 분석 문서·정제한 기록·재개 메모입니다. C#/WPF·Python 개발 도구·EXE·기존 ZIP은 변경하지 않았고 이번 빌드·단위 테스트는 미실행입니다. C# 437개·빌드 경고/오류 0개는 이전 `5d77df5`, Python 88개는 이전 `e7b067a` 기록입니다.

원본 로드·실행·에뮬레이션, 하드웨어/OEM 호출, 기존 단발 예약 접근, 드라이버·서비스·보안·펌웨어 변경은 없었습니다. 실행용 요청·표식 값·frame generator·실제 backend를 만들지 않았습니다. 원본·전체 명령어·주소와 구체적인 게시 값은 비공개로 보존합니다. 추가 노트북 시험·동일 자료 재제출은 필요하지 않습니다.
