# 충전 보호 조회의 오류·신선도 경계 — 2026-11-07 한국 시간

**후속:** [충전기 응답 조회 후보와 상태 스냅샷](CHARGER_READBACK_AND_PROJECTION.md)에서 버스 수신 word를 반환하는 별도 후보와 정책의 활동 기록이 EC 페이지에 반영되는 경로를 연결했습니다. 보호 모드의 직접 미러나 오류 보존 Windows 조회는 아직 확보하지 못했습니다. 아래는 이전 분석 시점의 기록입니다.

**첫 대기 실패를 보존하는 기존 EC 조회 경로를 찾았습니다. 다만 보호 모드 저장값을 읽는 후보와는 다른 경로입니다.** 일반 중계가 오래된 데이터를 정상으로 반환할 수 있는 조건과, 기존 Windows DLL의 협력 호출자 사이 잠금 범위도 구체화했습니다. 현재 장치에서 이 문제가 발생했다고 관측한 것은 아니며 실제 충전 제어는 미구현·Unsupported입니다.

[저장값 조회 후보와 Windows 중계 연결](EC_READBACK_AND_WINDOWS_BRIDGE.md)의 후속입니다. 보유 원본을 데이터로만 분석했습니다. EC의 명령어·메모리 해석은 기존 Intel 8051 호환 ISA와 하위 48KiB 공통/상위 16KiB bank 모델을 전제로 합니다. 실제 칩·현재 이미지·호출 안전성의 검증을 대신하지 않습니다.

## 일반 완료가 최신 응답을 보장하지 않는 이유

일반 송신 helper는 먼저 이전 작업이 끝나기를 기다립니다. 한도를 소진하면 `EFI_NOT_READY`를 반환하며 새 메시지와 명령을 게시하지 않습니다. 이 소스의 코드는 `EFI_TIMEOUT`과 구분합니다. 그런데 상위 송수신 helper는 이 반환을 검사하지 않고 다시 대기합니다.

| 순서 | 소스에서 허용되는 조건과 결과 |
| --- | --- |
| 첫 대기 | 이전 작업이 계속 진행돼 대기 한도를 소진함 |
| 송신 반환 | 실패를 반환하고 새 요청은 게시하지 않음 |
| 두 번째 대기 | 그 사이 이전 작업이 끝나면 성공할 수 있음 |
| 결과 복사 | 기존 메시지 데이터를 복사하고 정상 반환할 수 있음 |

이는 분기와 호출 순서에서 도출한 **조건부 사건 순서**입니다. 원본 코드 실행·에뮬레이션이나 실제 노트북의 발생 기록이 아닙니다. 반복해서 같은 값을 받거나 고정 echo가 맞는 것만으로 새 요청이 처리됐음을 입증할 수 없습니다.

EC 쪽에서도 저장 바이트 읽기 후보가 결과를 쓰고 분배기가 완료 표시를 지우는 순서를 연결했습니다. 선택한 읽기 본문은 **결과 한 바이트만** 갱신합니다. 중계가 복사하는 10바이트 전체가 새 상태값인 것은 아닙니다. 선택한 본문에는 요청 식별자·응답 순번·상세 상태가 없고, 완료 표시를 지우는 다른 문맥도 있어 그 표시만으로 특정 보호 조회의 완료를 증명하지 않습니다.

## 오류를 보존하는 별도 경로의 범위

별도 한 바이트 조회 helper는 첫 대기의 실패를 검사해 즉시 반환하고, 명령 게시 후 두 번째 대기의 실패도 검사합니다. 등록된 조회 callback 네 개에서 이 helper의 오류가 공통 제공자까지 유지되는 선택 경로를 연결했습니다. 모든 EC helper가 첫 오류를 잃는다는 결론은 잘못입니다.

하지만 이 경로는 정해진 EC 상태 페이지와 고정 필드를 읽습니다. 앞서 찾은 보호 모드·80/75 임계값 저장소의 범용 주소 읽기와 같은 인터페이스가 아닙니다. 그중 한 고정 비트는 EC의 생산 코드와 저장된 ACPI의 `ACEX`·전원 공급원 처리에 맞아 **AC 전원 상태** 역할을 지지합니다. 충전 제한 활성 상태나 적용 성공으로 해석하지 않습니다. 다른 페이지로 보호 모드가 복사될 가능성을 전역적으로 배제한 것은 아니며, 이번에는 그러한 연결을 확보하지 못했습니다.

오류가 보존되더라도 공통 제공자는 callback 오류를 정해진 실패 데이터로 축약하고 외부 ACK·정상 반환을 만듭니다. 상세 대기 오류를 Windows에 그대로 전달하는 계약은 아닙니다. 별도로 확인한 읽기 후 쓰기 경로는 조회 대체 수단에서 제외했습니다. 인접 쓰기 명령이나 임의 필드로 바꿔 시험하지 않습니다.

## Windows의 협력 잠금과 한계

현재 Settings 2.2.0.18의 서로 다른 WSABI 세 변형은 같은 Global 이름 mutex를 사용합니다. 일반 경로에서는 WMI 호출 전부터 응답 복사·정리까지 잠금을 유지합니다. 따라서 앞선 ACPI 분석의 ‘트리거만 잠금’은 **그 ACPI mutex의 범위**이며, 이 협력 Windows 호출자들에 전체 교환 잠금이 없다는 뜻은 아닙니다.

이름 있는 객체 생성·접근·참여가 성립하는 호출자 사이의 협력 규약입니다. 다른 WMI/ACPI 호출자·native 전송·펌웨어 접근 전체를 잠그지는 않습니다. native DLL은 다른 잠금 객체를 사용합니다. 원본 DLL에는 무한 대기와 일부 실패 경로의 잠금 해제 누락도 있어 그대로 앱에 도입하지 않습니다. 이전 사용자 제공 서비스 wsabi는 이번에 원본 바이트를 재검증하지 않았으며 같은 크기의 현재 변형으로 대체하지 않았습니다.

이 잠금은 응답 순번이나 독립 상태 비교를 추가하지 않고, 펌웨어에서 가려지는 송신 오류도 복구하지 않습니다. 앱 내부의 단일 교환 제한 역시 모든 외부 호출자를 배제하거나 현재 보호 상태를 입증하는 수단은 아닙니다.

## 다음 개발과 검증

다음 우선순위는 **오류를 보존하는 조회 경로에 보호 모드의 생산값이 연결되는지**입니다. 해당 상태 페이지의 보호 모드 반영 경로나 별도 전용 조회 생산자를 찾아야 합니다. AC 전원 비트·현재 잔량·설정 echo·완료 표시를 보호 상태로 대신하지 않습니다. 같은 실패 응답의 재분석이나 임의 명령 시험으로 빈 연결을 채우지 않습니다.

새 근거와 선택 범위는 [정적 검사 기록](reports/ec-freshness-error-paths-audit.json)에 저장했습니다. 통합 독립 검산 46개와 담당별 검산·교차 검토를 수행했습니다. 숫자는 선택한 소스 검사이며 앱 테스트 수·전체 펌웨어 분석률이 아닙니다.

앱·테스트 코드·기존 ZIP은 변경하지 않았고 빌드·단위 테스트는 재실행하지 않았습니다. C# 437개 / Python 85개 통과와 빌드 경고·오류 0개는 코드 커밋 `5d77df5`의 이전 기록입니다. 새 실행 파일이나 OEM 요청을 만들지 않았습니다. 원본 실행·에뮬레이션, 하드웨어 호출, 기존 단발 예약 접근, 드라이버·서비스·보안·펌웨어 변경은 없습니다. 원본 바이너리·전체 디스어셈블리·물리 주소·활성화 값·요청 구성은 비공개로 보존합니다. 추가 노트북 시험·자료 제출은 필요하지 않습니다.
