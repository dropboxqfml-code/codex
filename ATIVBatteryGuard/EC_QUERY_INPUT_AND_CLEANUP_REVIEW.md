# 고정 조회의 입력·완료 정리·응답 귀속 — 2026-11-07 한국 시간

후속 [공유 채널 조정·입력 수명 결과](SHARED_CHANNEL_COORDINATION_UPDATE.md)에서 FrameExchange의 동일 자원 재진입 방지를 실제 코드로 보강했고, 선택 worker의 원본/local 입력 소비가 terminal 요청 반환 전에 이뤄짐을 연결했습니다. 아래는 당시 분석·검사 기록이며 새 코드 검증은 후속 문서를 봅니다.

**명령 슬롯의 늦은 clear를 만드는 구체 작업 상태와, 고정 읽기의 주소 소비·결과 저장 관계를 좁혔습니다.** 조회를 안전하게 실패 처리하는 조건과 기존 정상 작업을 훼손하지 않는 조건도 구분했습니다. 실제 보호 모드 조회·충전 제어는 아직 제공하지 않으며 제어는 Unsupported입니다.

[이전 부팅·인계 검토](EC_READ_HANDOFF_AND_BOOT_ORDER.md)의 후속입니다. 저장된 원본을 데이터로 분석했으며 실제 EC/OEM·펌웨어 변수 호출이나 새 실기 시험은 하지 않았습니다. [고정 조회 검토안](FIXED_MODE_READ_PROPOSAL.md)은 계속 비실행 문서입니다.

## 늦은 clear의 상태 생산자

기존에 확인한 main scheduler의 완료 정리에는 여러 gate가 있습니다. 이번에는 descriptor에서 선택한 하위 작업의 시작이 성공했을 때 **active 상태와 완료 대기 상태를 함께 만드는 생산 경로**를 연결했습니다. 선택 controller 상태를 확인하는 readiness helper와 뒤의 정리 경로도 구분해, 이 특정 작업의 지연된 후처리라는 소스 근거를 얻었습니다.

여기서 active 상태와 같은 바이트의 다른 비트를 ISR이 설정한다는 사실을 혼동하지 않습니다. 작업 시작이 실패한 경우의 rollback도 성공한 active 작업으로 세지 않습니다. 이 경로를 Windows 정상 실행·부팅·flash·종료 중 어느 한 단계 전용이라고 판정하거나, 실제 조회 중 발생했다고 관측한 것은 아닙니다.

선택한 시작 staging과 알려진 완료 복사는 query mailbox와 다른 영역을 사용합니다. 이 국소 구분만으로 관련 하위 작업·간접 pointer·IRQ에서 조회 upload가 계속 소비할 입력을 훼손하지 않는지까지 입증한 것은 아닙니다. 따라서 **새 조회의 upload가 이전 작업이 계속 사용할 입력을 바꾸지 않는지**는 남은 보존 조건입니다. 선택 clear 자체가 결과 바이트를 직접 덮어쓰지 않는다는 기존 사실과도 구분합니다.

## 주소를 소비하는 때와 반환 내용을 비교하는 때

조건부 EC 해석에서 선택 reader의 helper는 두 주소 성분을 **따로 읽어** register에 보관합니다. reader는 조립한 대상에서 한 바이트를 읽고, 첫 주소 성분이 있던 message 위치를 결과로 바꿉니다. 둘째 성분과 나머지 반환 내용은 선택한 전체 helper/reader body에서 보존됩니다.

이번에는 알려진 stable-command ISR의 register 보존을 이 단계들과 연결했습니다. 그 선택 경로는 주소 조립 중간 값·carry·샘플·결과 저장 pointer에 필요한 register를 보존합니다. 이 특정 ISR이 읽기 중간 상태를 훼손한다는 우려는 좁힐 수 있습니다. 다른 ISR·외부 message writer·실제 interrupt binding·현재 이미지까지 같은 결론으로 넓히지 않습니다.

사후 내용 비교는 반환 시점의 보존 관계를 검사할 수 있습니다. 하지만 첫 주소 성분은 결과로 바뀌므로 소비 당시 값을 사후 복원할 수 없고, 둘째 성분의 최종 일치도 두 성분을 읽는 동안 계속 안정적이었다는 증거는 아닙니다. 비교만으로 선택 handler의 실행이나 EC 고유 완료 identity를 인증하지 않습니다. 입력이 바뀌었다가 복구되는 실제 actor·경쟁을 새로 찾았다는 뜻도 아닙니다. **실행 전 입력·명령 무결성은 별도 근거가 필요**합니다.

| 조건부 경우 | 선택 소스에서 구분해야 할 결과 |
| --- | --- |
| 첫 송신이 upload·게시 전에 생략됨 | 다음 대기가 성공하면 이전 mailbox가 복사될 수 있음. 신선한 내용 비교의 전제가 별도로 필요 |
| upload 뒤 reader 실행 전에 clear | 나머지 내용은 맞아도 첫 바이트가 입력 echo일 수 있음. 입력과 허용 결과 영역의 구분이 입증될 때만 echo 거부가 도움 됨 |
| reader 완료 뒤 clear | 선택 clear는 이미 생성된 샘플을 바꾸지 않음. clear 존재만으로 결과 오염을 판정하지 않음 |

이 표는 기존 송신 오류 가림·clear의 경우를 새 주소 소비 관계와 함께 분류한 것입니다. 새 요청·표식 값·프레임·실행 경로를 만들거나 실제 결과를 관측하지 않았습니다.

## WMI Field Lock과 전체 교환의 차이

보존된 두 raw DSDT는 공유 필드에 `AnyAcc, Lock, Preserve`를 선언하면서 `WM00`과 `SAWS`는 `NotSerialized`로 선언합니다. 명시적인 AML mutex는 `SAWS` 안의 trigger만 감쌉니다. `WM00`의 입력 지우기·입력 저장·마지막 응답 읽기는 그 명시적 mutex 밖입니다. 앞서 확인한 펌웨어 snapshot도 바이트별 접근입니다.

Field Lock 선언만으로 전체 메서드 교환이나 펌웨어의 일반 byte 접근까지 같은 Global Lock에 참여한다고 입증할 수 없습니다. 반대로 NotSerialized 선언만으로 실제 Windows provider가 동시에 실행하거나 race가 발생했다고 단정하지 않습니다. Windows interpreter의 실제 세부 접근·추가 직렬화·다른 호출자의 참여는 미관측입니다.

필요한 것은 입력 준비부터 응답 회수까지 관련 무결성·소유권입니다. 기존 OEM 협력 mutex는 실제 참여할 때 그 범위를 보호할 수 있는 근거이며, 유일한 가능한 해법으로 요구하지 않습니다. 앱 내부 lock이나 Field Lock 하나를 모든 호출자에 대한 보호로 확대하지 않습니다. 나중의 응답 거부가 이미 다른 명령·대상으로 실행된 부작용을 되돌리는 것도 아닙니다.

## 조회 시험안에 반영한 최소 조건

조회 자체의 무조건 성공은 요구하지 않습니다. **기존 작업의 명령·상태 전이·계속 사용할 입력을 훼손하지 않고**, 새 조회가 취소되면 입력 echo·오래된 결과를 성공으로 받지 않으며, 실제 하위 진행과 소유권을 올바르게 정리해야 합니다. UI timeout만으로 완료나 안전한 해제를 보장하지 않습니다.

고정 읽기의 사전 대상 안전성과 응답 귀속은 유지할 조건입니다. 표준 통신의 미연결 실행 영역, 전체 WMI 교환 소유권, 이전 작업의 계속되는 버퍼 의존성을 현재 근거만으로 닫지는 못했습니다. live EC 전체 해시나 모든 플랫폼 writer의 전역 부재를 대신 요구하지 않습니다. 새 backend·시험 도구·하드웨어 호출은 추가하지 않았습니다.

다음은 이 특정 deferred 작업의 계속되는 버퍼 소비와 고정 조회의 입력 준비~snapshot 경계에서 실제 참여자 규약을 우선합니다. 이미 확인한 clear·ISR·주소 helper를 다시 세거나 같은 표식 비교만 세분화해 실제 조회 성공으로 보고하지 않습니다.

문서·정제 기록만 변경했습니다. C#/WPF·Python 개발 도구·EXE·기존 ZIP은 그대로이고 이번 빌드·단위 테스트는 실행하지 않았습니다. C#437개와 빌드 경고/오류0은 이전 `5d77df5`, Python88개는 이전 `e7b067a` 기록입니다. 추가 노트북 실행·동일 자료 제출은 필요하지 않습니다.
