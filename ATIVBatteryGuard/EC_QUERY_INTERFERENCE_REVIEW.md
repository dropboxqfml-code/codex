# 보호 상태 조회의 간섭 후보와 실행 순서 — 2026-11-07 한국 시간

**이전의 간섭 후보 일부를 실제 호출 관계로 좁혔습니다. 다른 결과 작성자가 조회 도중 자율적으로 끼어든다는 근거는 이번에 확인하지 못했습니다.** 범용 읽기 후보에 유리한 범위 축소이지만 현재 노트북의 보호 상태 조회·충전 제어 성공이나 안전한 실행 계약의 완성은 아닙니다.

[경로 성립 조건](BOUNDED_READ_ROUTE_FEASIBILITY.md)의 후속입니다. 보유 P05 펌웨어를 데이터로만 읽었습니다. EC의 Intel 8051 호환 명령어·bank 모델과 실제 interrupt binding은 여전히 조건부이며, 현재 설치 이미지·실행을 확인한 분석이 아닙니다.

## EC의 다른 결과 생산자를 다시 연결한 결과

| 이전 후보 | 새로 연결한 소스 관계 | 이번에 좁힌 범위 |
| --- | --- | --- |
| 첫 결과 바이트만 바꾸는 다른 본문 | 같은 high-command 분배표의 별도 명령 handler | 선택한 읽기 명령이 유지되는 단일 분배에서 독립적인 백그라운드 작성자로 취급하지 않음 |
| 별도 완료 지우기 | 같은 EC main thread의 조건부 scheduler 후처리 | 짧은 reader를 독립적으로 선점하는 작업이 아니며, 선택한 지우기 block은 결과 바이트·tail을 바꾸지 않음 |
| 알려진 명령 ISR 형태의 코드 | 진입 jump·저장/복구·분기·pending flag 생산 연결 | 선택한 읽기 명령이 유지되는 분기에서는 다른 결과를 쓰거나 low-command 지우기를 수행하지 않음 |
| 중복 pending 알림 | 현재 명령을 다시 검사하는 scheduler 진입 | 완료 후 명령이 지워진 상태에서는 pending만으로 다른 handler를 실행하지 않음 |

따라서 다른 첫 바이트 작성자의 존재만으로 ‘EC가 자율적으로 결과를 덮어쓴다’는 반례를 세우면 부정확합니다. 별도 명령 선택, 다른 실제 진입, 또는 충돌하는 작성자의 연결이 추가로 필요합니다. ISR의 실제 하드웨어 binding, 다른 ISR·계산된 진입·외부 작성자 전체를 닫은 것은 아닙니다.

후처리 지우기에는 실제 조건과 호출 순서가 있습니다. 그 조건이 성립하고 host가 앞선 작업 scan 이후 새 명령을 게시하면 새 명령을 지울 수 있는 **조건부 취소 구간**은 남습니다. 실제 노트북의 경합 관측은 아닙니다. 이 지우기 block 자체는 다른 결과를 만들지 않습니다. 업로드 뒤 reader가 실행되지 않은 단순 취소는 입력 echo 거부 대상이며, 이미 완료된 읽기 뒤에 명령값을 다시 지우는 것은 잘못된 결과 생산자 반례가 아닙니다. 상위 함수 전체의 모든 간접 효과를 증명한 것으로 확대하지 않습니다.

## 실제 보조 CPU 작업의 역할

SMM 서비스 테이블의 출처와 AP 호출 지점, 전달 함수 포인터를 연결했습니다. 같은 함수 offset이나 GUID 문자열만으로 분류하지 않았습니다. 선택 범위는 네 모듈의 AP 호출 여섯 곳과 고정 작업 열 개입니다.

| 보유 모듈 | 연결한 작업의 역할 |
| --- | --- |
| CpuSpSMI | CPU cache·메모리 속성 register 복원 |
| PowerMgmtS3 | CPU 전력 관련 register 기록 복원 |
| DigitalThermalSensorSmm | CPU 온도 상태 수집·열 관리·local APIC 처리 |
| MicrocodeUpdate | CPU microcode 관련 register 작업 |

검토한 작업에서 EC/SABI 메시지 전송 연결은 확보하지 못했습니다. 원본의 CPU register 쓰기를 실행한 것은 아닙니다. 모든 작업의 완전한 간접 호출 폐쇄나 runtime queue 전체의 부재를 입증하지도 않습니다. 알려진 CPU 작업을 용도가 미확정인 EC 작성자로 계속 세지 않는 것이 이번 결과입니다.

## 조회 callback 자체의 호출과 입력 경계

선택한 일반 callback을 포함한 13개 함수의 직접 호출·tail 분기를 정적으로 대조했습니다. 도달 가능한 분기 양쪽을 검사했고, 이 선택 사슬에는 간접 호출이나 AP 작업 등록·다른 callback을 실행하는 pump가 없습니다. 대기 helper는 타이머를 직접 확인합니다. 이것이 모든 interrupt·다른 CPU·EC 작업을 멈춘다는 뜻은 아닙니다.

입력은 공유 프레임에서 바이트별로 복사·지워진 뒤 local stack의 모드·명령·메시지로 사용됩니다. **복사가 끝난 뒤의 공유 프레임 변경이 그 local 명령을 직접 바꾸는 경로는 선택 본문에 없습니다.** 복사 자체의 원자성, 공유 indexed I/O·EC 메시지의 독점 접근, 최종 응답 프레임 교체까지 보장한 것은 아닙니다.

타이머 대기는 정상적인 타이머 진행을 전제로 합니다. 상위 readiness 반복 횟수만으로 전체 callback의 절대 실행시간 상한을 증명할 수 없고, 앱의 timeout은 이 SMM 내부 대기를 중단시키는 계약이 아닙니다. 실제 타이머 고장이나 hang을 관측한 결과는 아닙니다.

## 남은 최소 계약

모든 CPU·모든 작성자가 전역적으로 없어야 한다는 요구는 과도합니다. 정상 지원 구성의 선택한 제한 조회에서 **명령·대상 무결성과 결과 대응을 바꾸는 간섭이 배제되거나, 안전한 순서·검출 근거를 갖추는지**가 필요합니다. 무관한 CPU 작업은 존재해도 됩니다.

구체적으로 현재 EC 분배기는 명령 종류 판정과 실제 handler 선택에서 공유 명령값을 별도로 읽습니다. 그 사이 명령값의 안정성을 입증해야 합니다. 다른 명령이 선택된 뒤 응답을 거부해도 이미 발생한 부작용을 취소하지 못하므로, **응답 귀속 검사와 실행 전 명령·대상 안전성은 별도 조건**입니다. 요청 표식과 echo 거부만으로 이 조건을 대체하지 않습니다.

다음 조사 대상은 이 공유 명령의 게시·선택 구간과 WMI 입력 복사·최종 반환 구간에서 충돌 가능한 실제 작성자의 동작 규약입니다. 이미 역할이 확인된 CPU 작업·다른 명령 handler·단순 clear를 다시 자율 덮어쓰기 근거로 세지 않습니다. 현재 이미지 적합성·실제 IRQ 선택·남은 간접 경로도 여전히 미확정입니다.

이번 변경은 분석 문서·검사 기록입니다. C#/WPF·Python 개발 도구·EXE·기존 ZIP은 변경하지 않았고 빌드·단위 테스트는 재실행하지 않았습니다. C# 437개·빌드 경고/오류 0개는 이전 `5d77df5`, Python 88개는 이전 `e7b067a` 검증 기록입니다. 실제 충전 제어는 Unsupported입니다.

원본 로드·실행·에뮬레이션, 하드웨어/OEM 호출, 기존 단발 예약 접근, 드라이버·서비스·보안·펌웨어 변경은 없었습니다. 실행용 요청·표식 값·frame generator·실제 backend도 만들지 않았습니다. 원본과 전체 명령어·주소 기록은 비공개로 보존합니다. 새 노트북 시험·동일 자료 재제출은 필요하지 않습니다.
