# 충전 보호 저장값 조회 후보와 Windows 중계 연결 — 2026-11-07 한국 시간

**80/75 충전 보호 후보의 후속으로, 저장값을 별도로 읽는 EC 코드 후보와 WMI에서 일반 EC callback으로 이어지는 소스 경로를 연결했습니다.** 기존 삼성 프로그램에서도 같은 중계 형식을 사용하는 호출자를 확인했습니다. 현재 노트북의 보호 상태나 충전 제어 성공을 관측한 것은 아니며 앱은 미구현·Unsupported를 유지합니다.

이 문서는 [80/75 충전 보호 코드 후보](EC_CHARGE_PROTECTION_CANDIDATE.md)의 후속입니다. 보유 P05ACJ와 기존 OEM 자료를 데이터로만 분석했습니다. EC 해석은 앞선 Intel 8051 호환 명령어·하위 48KiB 공통/상위 16KiB bank 모델을 전제로 하며, 공식 칩 정의나 현재 장치 이미지 확인을 대신하지 않습니다.

## 보호 상태 재조회에 가까워진 부분

내부 EC 명령 분배표에서 **지정한 저장 바이트를 읽어 응답에 넣는 경로**를 찾았습니다. 선택한 본문은 읽은 대상에 쓰지 않고 반환용 메시지를 갱신합니다. 같은 조건부 주소 모델에서는 보호 모드와 상·하한 저장값을 읽는 후보가 됩니다. 설정 요청의 입력을 그대로 돌려주는 echo와는 소스상 다른 경로입니다.

다만 이는 범용 EC 메모리 읽기이며 전용 보호 상태 조회 API가 아닙니다. 코드의 존재만으로 Windows에서 안전하게 사용할 수 있다고 판단하지 않습니다. 내부 모드 저장값, 충전기 쓰기의 실제 성공, 전기적 충전 중단은 각각 별개입니다. 이 후보를 `actualMode`나 적용 성공 표시로 연결하지 않았습니다. 인접한 쓰기 경로와도 구분했으며 요청·주소 조합·실행용 코드는 만들지 않았습니다.

특정 초기화 분기에서는 보호 모드·임계값을 포함하는 메모리 범위를 0으로 지우는 코드도 확인했습니다. 다른 분기에서는 해당 지우기를 건너뜁니다. 이 위치에서의 값만 확인한 것으로, 이후 복원·Windows 재부팅·절전 복귀·전원 차단 후 유지 여부는 미확정입니다. 모드가 이미 같은 활성 값이면 설정 handler가 임계값을 다시 쓰지 않는 점도 확인했습니다.

## WMI의 길이 차이를 설명한 근거

저장된 ACPI의 WMI 메서드에서 펌웨어 공유 프레임, 공통 분배기, 등록된 일반 EC callback까지 소스 연결을 확인했습니다. 초기화 코드는 공유 버퍼를 할당·초기화하고 ACPI의 해당 영역을 수정합니다. 별도로 보유한 같은 모델의 공개 DSDT에서도 수정된 영역 길이가 일치합니다. 공개 DSDT는 사용자의 현재 장치 관측 자료가 아니며 물리 주소를 복사하거나 접근하지 않았습니다.

| 구분 | 선택한 소스에서 확인한 길이와 범위 |
| --- | --- |
| WMI 가시 프레임 | 전체 21바이트, 그중 payload 16바이트 |
| 실제 공유 영역 | 278바이트 할당에서 17바이트 header 뒤의 261바이트 |
| callback의 입력 복사·지우기 | payload 20바이트를 다루지만 할당된 공유 영역 안에 있음 |
| 선택한 데이터 전달 | payload 앞부분의 모드·명령 및 데이터 10바이트가 WMI 가시 범위에 들어감 |
| 선택한 반환 | EC 응답 10바이트가 WMI 반환 프레임 안에 들어감 |
| 추가 4바이트 | WMI Field 밖이지만 할당 안에 있음. 선택한 입력·반환에 쓰이지 않으며 항상 0이라고 보장하지 않음 |

따라서 **20바이트와 16바이트의 차이만으로 이 경로의 할당 초과나 필요한 응답 잘림을 판단할 근거는 해소했습니다.** WMI 요청 길이를 늘리거나 모든 callback의 안전성을 인정한 것은 아닙니다. 실제 부팅의 할당·수정·등록 성공, 현재 이미지와 권한은 여전히 미검증입니다. native DLL의 다른 길이·레거시 경로와도 합치지 않습니다.

현재 계열 Settings 2.2.0.18에 포함된 `ModuleSABI.dll`에서는 동적으로 얻은 `CallBIOSInterface`를 통해 같은 중계 형식을 쓰는 실제 호출자를 찾았습니다. 선택한 기능은 항공기 모드 LED와 키보드 백라이트의 `JogMode` 조회입니다. Windows 호출자 버퍼와 펌웨어의 선택한 입력·반환 위치가 맞지만, **이 기능들의 호출을 배터리 보호 지원이나 현재 DLL 선택의 증거로 확대하지 않습니다.** 이번 선택 범위에서 새 EC 보호 모드 setter와 연결된 OEM 호출자는 확인하지 못했습니다.

## 실제 조회 구현 전에 남은 문제

일반 중계의 소프트웨어 gate는 장치 지원이나 사용자 승인 판정이 아닙니다. callback 실패에서도 공통 계층의 ACK와 정상 반환이 나올 수 있습니다. 송신 결과를 검사하지 않은 채 다음 대기를 수행하는 경로도 있어 앞선 오류가 가려지거나 오래된 데이터가 복사될 가능성을 배제하지 못했습니다. 기존 단발 응답의 첫 `FF`를 새 발견으로 재해석하지 않습니다.

또한 ACPI의 mutex는 트리거만 감쌉니다. 입력 저장부터 반환까지 전체 교환을 직렬화하지 않아 다른 호출자와의 동시 접근 안전성도 확보하지 못했습니다. 저장값을 읽는 코드 후보를 찾았더라도 현재 상태의 독립적이고 신선한 응답을 확보했다고 할 수 없는 이유입니다.

다음 작업은 **응답 신선도·오류 전달·동시 접근을 보장하는 기존 경로가 있는지** 추적하는 것입니다. 현재 노트북의 펌웨어·전송 경로 적합성과 독립적인 보호 상태 조회가 확인되기 전에는 설정 쓰기나 제어 버튼을 연결하지 않습니다. 범용 메모리 접근·새 OEM 시험·기존 단발 예약 초기화로 간극을 메우지 않습니다.

## 검증과 산출물

원본 바이트·자료 해시·ACPI checksum과 구문·길이 관계를 검산하고 담당별로 교차 검토했습니다. 통합 독립 검산은 52개 선택 단언을 통과했습니다. 각 선택 범위와 조건은 [정적 검사 기록](reports/ec-readback-windows-bridge-audit.json)에 저장했습니다. 이 숫자는 앱 단위 테스트 수나 전체 펌웨어 분석률이 아닙니다.

변경은 분석 문서와 정제한 검사 기록입니다. 앱·테스트 코드·기존 ZIP은 변경하지 않았고 새 실행 파일도 만들지 않았습니다. 이번 빌드·단위 테스트는 미실행이며 C# 437개 / Python 85개 통과와 빌드 경고·오류 0개는 코드 커밋 `5d77df5`의 이전 기록입니다. 원본 삼성 파일·전체 디스어셈블리·사용자 식별자·물리 주소·활성화 값·실행 메시지 구성은 배포하지 않습니다. 원본 실행·에뮬레이션, 하드웨어/OEM 호출, 예약 접근, 드라이버·서비스·보안·펌웨어 설정 변경은 없었습니다. 추가 노트북 시험·자료 제출은 필요하지 않습니다.
