# 보호 조회의 부팅 순서와 EC 명령 인계 — 2026-11-07 한국 시간

후속 [입력·완료 정리·응답 귀속 검토](EC_QUERY_INPUT_AND_CLEANUP_REVIEW.md)에서 late clear의 상태 생산자와 reader의 주소 소비 관계, WMI Field Lock의 범위를 구체화했습니다. 작업 보존의 최소 조건은 기존 정상 작업 비훼손과 조회의 안전한 실패·오귀속 방지이며, 두 작업의 무조건 성공을 요구하지 않습니다. 아래는 당시 소스 분석과 검사 기록입니다.

**소프트웨어 SMI fallback이 같은 정상 SMM root 안에서 변수 서비스를 호출하는 연결을 확보했습니다.** 부팅 중 중계 함수 설치의 선행 조건과, Runtime 후크·조회가 같은 준비 규약을 쓰는 관계도 좁혔습니다. 실제 보호 모드 읽기·충전 제어는 아직 제공하지 않으며 제어는 Unsupported입니다.

[이전 검토](RUNTIME_PROXY_AND_FIXED_READ_REVIEW.md)에서 정한 부팅 순서·통신 실행 영역·기존 작업 보존을 저장 원본으로 추적했습니다. 삼성 파일이나 하드웨어를 실행하지 않았습니다. [고정 조회 검토안](FIXED_MODE_READ_PROPOSAL.md)의 조건표도 이번 결과로 갱신했습니다.

## 부팅 알림의 선행 조건

원본 FV의 `NvramSmi`는 SMM/DXE 복합 모듈입니다. **DXE 의존성은 SmmBase2 제공을 요구**하며, 별도 SMM 의존성을 DXE dispatch 조건에 합치지 않습니다. CORE의 복합 모듈 열거·DXE 의존성 선택과, dispatcher 반환 뒤 실제 BDS interface를 호출하는 경로를 연결했습니다.

따라서 해당 모듈 발견·DXE 의존성 충족·비재진입 dispatch·Load/Start·알림 등록이 성공하는 정상 조건에서는, 앞서 확인한 BDS marker 게시보다 알림 등록이 선행합니다. 단순히 dispatch가 반환했다는 사실이 모든 모듈의 발견·의존성 충족·시작 성공을 뜻하지는 않습니다. marker를 제거하는 행위도 이미 queue에 들어간 알림을 취소하는 것으로 해석하지 않습니다.

실제 callback 전달과 함수 교체에는 shared buffer·Event 유지와 적절한 TPL 복귀 조건도 필요합니다. 전달은 install 반환 전에 일어나거나 이후의 TPL 하강에서 일어날 수 있으며 현재 동적 TPL·전달 성공은 관측하지 않았습니다.

이는 정상 조건에서 후속 host 중계 설치를 검토할 **소스 순서 근거**입니다. 현재 노트북에서 해당 조건·함수 포인터를 직접 관측한 것은 아닙니다. 그 미관측 하나만을 비실행 제안 검토의 절대 중단 조건으로 요구하지 않으며, 정상 성공 조건과 프로파일 가정을 함께 기록합니다. 현재 표가 반드시 특정 함수이거나 이후의 모든 writer가 배제됐다는 뜻도 아닙니다.

## 서로 다른 세 통신 경로

| 경로 | 이번에 확인한 연결 | 판정 |
| --- | --- | --- |
| Nvram의 legacy software-SMI fallback | 정확한 PCH 제공자·선택 context 비교·동기 child 호출·같은 default root·선택 private Runtime 변수 함수 | 정상 초기화·등록·버퍼·private 표 선택 성공 조건에서 연결 |
| SmmBase의 legacy Communicate | 게시된 메서드가 shared record에 인수를 저장하고 deferred job을 설치. 정상 leader가 실행한 job이 같은 legacy callback list에 buffer/size를 전달 | 해당 legacy 입력 경로 확인. Nvram fallback이나 표준 통신으로 혼합하지 않음 |
| 표준 SMM communication | 기존 typed 수신 handler 등록은 확인했으나, 표준 제공자에서 해당 GUID를 선택하는 실제 진입 연결은 미확정 | 미완료 유지 |

첫 경로에서 PCH root는 default callback으로 등록되며 정상 root의 legacy 순회가 이를 동기 호출합니다. child가 Nvram 수신자를 부르고, 그 수신자가 선택된 private Runtime 변수 함수를 호출할 때까지 같은 호출 안에 머뭅니다. 일반적인 sibling 목록 진행으로 그 중간에 다른 SABI callback이 끼어드는 구조는 아닙니다. 기존 backend가 EC 후크를 선택한다면 그 후크도 이 호출에 중첩됩니다.

private Runtime 표는 legacy/native SMST의 실제 공유 configuration 목록을 통해 게시·조회됨을 연결했습니다. 조회 실패로 이전 포인터를 유지한 경우를 성공한 private 표 선택으로 세지 않습니다. AP 작업·재진입·다른 진입·현재 설정·모든 CPU의 배제까지 입증한 것은 아닙니다.

둘째 경로는 이전에 정체가 미확정이던 leader의 특별 callback 한 사례를 설명합니다. 복원한 job은 legacy record에 입력을 queue하며 표준 GUID별 handler를 직접 선택하지 않습니다. default 순회가 같은 목록의 모든 typed handler를 호출한다는 추정으로 표준 통신의 빈 연결을 채우지 않습니다. 다른 deferred job이나 외부 제공자의 부재도 주장하지 않습니다. 이번에는 GUID·분할 상수 검색을 반복하지 않았습니다.

## 준비 대기와 실제 완료의 차이

Runtime 후크와 generic 조회의 선택 helper 여덟 쌍을 실제 callee와 함수 내부 분기 기준으로 정규화해 비교했습니다. indexed 주소 선택·같은 명령 슬롯·0일 때 준비 성공·준비 오류이면 게시 생략이라는 규약이 같습니다. timer 대기도 같은 직접 polling 구조이며 선택 본문은 callback pump가 아닙니다.

관련 게시자와 조회가 같은 초기화 완료·비재진입 SMM 순서에 속한다면, 해당 CPU의 주소 선택·데이터 접근은 그 순서 안에서 겹치지 않습니다. 후속 조회도 같은 슬롯의 준비를 먼저 기다리므로, 앞선 후크 sender에 게시 후 대기가 없다는 사실만으로 곧바로 명령 덮어쓰기를 추론할 수는 없습니다.

하지만 **준비값 0은 처리 효과 완료를 증명하는 독립 token이 아닙니다.** EC 쪽의 늦은 clear가 다음 게시를 지울 수 있는 기존 조건부 경로는 남습니다. 이전 작업과 다음 작업이 모두 보존되는 인계가 필요하며, 모든 EC 효과가 완료됐다는 요구와도 구분합니다. 정상 SMM 순서·0 대기만으로 이 조건이 해결됐다고 하지 않습니다. 실제 겹침·명령 소실을 노트북에서 관측한 것도 아닙니다.

WMI 입력 준비·snapshot·응답 회수의 소유권, 일반 중계의 첫 송신 오류 가림·응답 귀속은 별도 과제입니다. 현재 협력 DLL의 잠금과 snapshot 이후의 local 사용은 유리한 근거지만, 모든 호출자가 참여하는 원자적 교환으로 확대하지 않습니다. 사후 응답 거부나 UI timeout으로 실행 전 입력·다른 정상 작업 보존을 대체하지 않습니다.

## 구현 판단과 다음 작업

부팅 순서는 정상 성공 조건으로 구체화했고, legacy fallback의 동기 실행 영역은 연결했습니다. 현재 실제 호출 준비를 막는 핵심은 **표준 통신 분기의 미연결, EC 명령 인계에서 양쪽 작업 보존, WMI 전체 교환·응답 귀속**입니다. live host 포인터나 EC 전체 해시 미관측 하나를 절대 조건으로 반복하지 않습니다.

다음은 이 중 고정 조회의 입력·명령 인계에서 실제로 남은 예외와 응답 귀속에 집중합니다. 표준 통신은 제공자·caller·GUID별 dispatch의 구체 연결이 나올 때만 갱신하며 같은 검색·legacy 분류를 반복 성과로 세지 않습니다. 조건을 충족하기 전 실제 backend·요청 프레임·시험 도구는 추가하지 않습니다. 기존 단발 예약도 접근·재사용하지 않습니다.

이번에는 문서·정제 기록만 변경했습니다. C#/WPF·Python 개발 도구·EXE·기존 ZIP은 그대로이며 빌드·단위 테스트는 반복하지 않았습니다. C#437개와 빌드 경고/오류0은 이전 `5d77df5`, Python88개는 이전 `e7b067a` 기록입니다. 추가 노트북 실행·동일 자료 제출은 필요하지 않습니다.
