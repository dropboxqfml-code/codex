# 펌웨어 조회 경계 분석과 요청 범위 보강 — 2026-11-06 한국 시간

**배터리 보호 설정 조회는 아직 미구현입니다.** 이번에는 펌웨어 테이블의 변경·실패 응답을 더 구체적으로 확인하고, 그 결과에 따라 순수 요청 준비 코드의 허용 범위를 좁혔습니다. 새 OEM 호출이나 실제 제어 기능을 추가하지 않았습니다.

[직전 조사](BATTERY_PROTECTION_ACCESS_FOLLOWUP.md)의 같은940X3G 계열 OEM 호출자 근거는 유지합니다. 아래 결과는 저장된 P05ACJ 이미지와 공개 고정 자료의 정적 분석이며, 현재 사용자 노트북의 실행·설정 관측이 아닙니다. 원본·전체 기계어·ASL·주소·식별자는 비공개 캐시에만 둡니다.

## 테이블의 생성·변경과 응답 분기

고정 원본은 SecSabiDispatch 29,952바이트/SHA-256 `2795669f18e3fb787d908ba00e2e9da7ab7d398ee599f27aa2f068129b46f310`입니다. 아래 숫자는 이 파일 안의 RVA이며 실행 지시나 장치 주소가 아닙니다.

- 생성자 `A04`의 인자는 활성 명령 수가 아닌 **main-group capacity**입니다. 확인한 초기화는1을 전달하며, 성공하면 그룹당256개의 callback/context 슬롯을 만듭니다. 기존 descriptor 후보56개는 이 capacity나 실제 등록 개수와 다른 집계입니다.
- 등록 wrapper `948`은 기존 callback의 덮어쓰기를 허용하지 않는 경로를 사용합니다. 반면 공개 삭제 함수 `954`는 callback과 descriptor 포인터가 모두 일치하면 슬롯의 두 포인터를 지웁니다. 후보 목록을 실행 중의 불변 목록으로 볼 수 없습니다.
- lookup `8F4`는 main 정확 일치 뒤 **sub WORD를 그대로 인덱스로 사용**합니다. 확인한 이 본문에는256개 슬롯의 상한 검사·마스킹·재시도·보조 lookup이 없습니다. main5843가 있으면 미등록65도 슬롯 주소를 얻을 수 있고, 뒤의 null callback 검사에서 실패합니다.
- 공통 실패는 데이터 FF+19개0·ACK AA를 만들고 펌웨어 함수는 정상0으로 반환합니다. **이0이 Windows HRESULT/ReturnValue로 그대로 전달된다는 뜻은 아닙니다.** callback의 EFI 오류도 같은 데이터 경로로 합류하므로 첫FF·ACK·API 성공만으로 보호 상태나 원인을 고를 수 없습니다.

SecLagacySabi의 선택된81 중계 본문도 대조했습니다. 포인터 검사는 있지만 프레임의 sub 상위 바이트를 검사하거나 자르는 구문은 없고, 프레임을 위 디스패처에 전달합니다. 이는 저장 소스의 한정된 경계 확인입니다. 현재 장치의 취약점·도달 가능성·메모리 영향까지 입증한 결과가 아닙니다.

생성·등록·삭제·검색·분배와 초기화의10개 한정 본문을 검토했습니다. 초기화의 불투명한 하위 호출, 외부/보존된 포인터, 임의 계산 별칭, callback 전이, 실제 설치 이미지 동일성은 남습니다. 공개 interface에서 manager 포인터를 얻을 수 있어 테이블이 다른 별칭으로 바뀌지 않는다는 전역 증명도 하지 않습니다. 새65/66 처리자를 발견한 것은 아닙니다.

## 실제 코드 변경: 준비 가능한 명령 범위 축소

`WsabiWmiRequestEncoder.MaximumSupportedCommand`를 `0xFF`로 두어 현재 프로젝트의 지원 범위를 **0..255**로 좁혔습니다. 이전에는0..65535를 준비할 수 있었습니다.

이는 원본 wsabi의 일반 ABI가8비트라는 주장이나 허용 범위 안의 모든 명령이 안전·지원된다는 판정이 아닙니다. **wire의 명령 필드는 여전히 UInt16**이며, 현재 프로젝트가 보수적으로 준비하는 부분집합만 줄였습니다.

검사는 기존 encoder 한 곳에서 수행합니다. binder의 prepare와 raw frame wrap도 같은 encoder를 재사용하므로 별도 정책을 중복하지 않습니다. FrameExchange도 채널 호출·작업 슬롯 획득 전에 거부합니다. `0x100`, 하위 바이트가65인 `0x165`, `0xFFFF`를 낮은 번호로 잘라 전달하지 않습니다.

새 통합 회귀는 이 값들이 encoder·prepare·raw frame channel·FrameExchange를 통해 주입한 모의 transport/channel에 도달하지 않는지 확인합니다. 이전 envelope 잔류·거부 후 정상 처리도 검사하며, WMI MethodId의32비트 범위는 그대로 유지합니다. 모든 검증은 메모리의 합성 데이터와 가짜 의존성을 사용합니다.

payload16·프레임21·응답 decoder·권한·실험 정책·어댑터·앱 연결은 바꾸지 않았습니다. 원래의 단발65가 재승인되거나 예약이 초기화되는 변경도 아닙니다. 인코딩 성공은 실행 권한이나 실제 조회 결과가 아닙니다.

## 캡슐 ACPI 원본과 간접 참조의 추가 확인

기존 추출물에서 checksum과 길이가 맞는 **DSDT1개·SSDT15개**를 새로 분리했습니다. 이는 정적 템플릿 수이며 모두가 현재 장치에 로드됐다는 뜻은 아닙니다.

캡슐 DSDT는71,849바이트/SHA-256 `e65919be72fd7e7bd51ca6561a6a94754ea22c929743a04727188f4638dda7a5`입니다. 기존 공개 DSDT와 전체133바이트가 달랐지만 배터리의7개 메서드 및 WM00/WQ00의 **원시 메서드 패킷9쌍은 byte-identical**이었습니다. 독립적으로 packet 경계·길이·인수·해시를 검산했습니다. 전체 리소스·전역 입력·실제 실행 동일성의 증명은 아닙니다.

SSDT의 PNOT 외부 참조는 DSDT의 CPU 알림으로 연결됐고, Smart Connect의 ECMD는 이16개 표에서도 미해결입니다. 배터리 장치 밖의 DSM·짧은 BLC 유사 이름도 문맥을 대조했지만 새 보호 설정 경로는 확보하지 못했습니다. 이름 선별의 미관측을 전체 기능 부재로 확대하지 않습니다.

기존 GUID 포함34개 중 직접 참조가 복구되지 않았던28개에는 정확한 포인터 표현·RIP 참조·한정된 상수 주소 전파를 추가 대조했습니다. 새 typed SABI 소비자는 없었습니다. 수치상 일치를 실제 포인터로 세지 않았고, stack·분기 합류·범위 복사·불투명 helper·임의 계산과 런타임은 미해결로 남깁니다. 기존34/6 수치를 새 발견으로 다시 세지 않습니다.

공개 ACPI 원본과 trusted iasl20250404는 필요한 고정 자료를 다시 확보했습니다. 복구 자체를 새 기능 근거로 세지 않았으며, 공식 패키지를 비공개 캐시에 풀어 정적 `-d`만 사용했습니다. 시스템 설치·패키지 스크립트·AML 평가·삼성 코드 실행은 없었습니다.

## 남은 구현 조건과 배포

현재 모델에서65를 처리하는 callback과 보호 상태 응답의 의미를 연결하지 못했습니다. 추가로 좁힌 테이블·ACPI·포인터 경계와 요청 범위 제한은 그 빈칸을 대신하지 못합니다. 실제 보호 설정 조회·충전 제한은 계속 `Unsupported`이며 하드웨어의 영구 미지원을 판정하지 않습니다.

다음 실제 조회 구현은 현재 모델에 맞는 handler·선행 조건·전송 실패 처리·신뢰할 재조회 계약을 연결하는 새 근거가 있을 때 진행합니다. 같은 패킷·후보 목록·첫FF를 다시 세분화하는 작업을 실제 접근 성공으로 보고하지 않습니다. 새0B/65 시험·원본 재제출·드라이버/서비스/보안 변경은 요구하지 않습니다.

이번 제공물은 [개발 소스 ZIP](../downloads/ATIVBatteryGuard-P05ACJ-QUERY-BOUNDARY-SOURCE.zip)입니다. 실행 프로그램 교체판이 아니며 기존 프로그램을 그대로 사용할 수 있습니다. 삼성 원본·펌웨어·사용자 자료·EXE/DLL은 소스 ZIP에 넣지 않습니다. 실제 조회나 새 실행을 위해 이 파일을 받을 필요는 없습니다.
