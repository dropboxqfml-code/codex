# P05ACJ 응답 근거 반영판 — 2026-11-05

이번에는 실제 P05ACJ 이미지와 구형 OEM 배터리 호출자를 확보해 **FF가 공통 실패 응답일 수 있는 구체적 근거**를 찾았습니다. 배터리 명령이 현재 모델에서 정상 처리된 결과나 실제 충전 제한 구현은 아닙니다. 새 프로그램은 기존 배터리 표시 앱의 오프라인 결과 설명을 갱신하며 실제 제어는 Unsupported입니다.

## FF의 구체적 근거와 한계

SecSabiDispatch.efi의 RVA 0x9A0–0xA03을 확인했습니다. main/sub 명령으로 콜백을 찾고, 등록을 찾지 못하거나 콜백이 null이거나 콜백 반환값에 EFI 오류 비트가 있으면 공통 경로로 갑니다.

| 위치 | 정적 동작 |
| --- | --- |
| 0x9BD–0x9E4 | lookup 결과·콜백·EFI 오류 비트 검사 |
| 0x9E6–0x9F4 | 프레임 +5부터 데이터 20바이트를 0으로 만들고 첫 데이터 바이트를 FF로 설정 |
| 0x9F8 | 위 실패 경로와 오류 비트 없는 콜백 경로 모두 ACK를 AA로 설정 |

따라서 **AA ACK는 배터리 명령 성공의 증거가 아닙니다.** 이 이미지에는 AA + 데이터 FF 뒤 19개 0을 만드는 공통 실패 경로가 있습니다. 현재 지원하는 WMI 프레임은 21바이트/데이터16바이트이므로 비교 가능한 접두부는 FF 뒤 15개 0뿐입니다. 성공 콜백 자체가 같은 데이터를 만들 가능성도 배제하지 못하므로 패턴 일치는 특정 실패 원인·명령 미지원·보호 OFF/ON의 판정이 아닙니다.

등록 경로도 일부 연결했습니다. 같은 모듈의 RVA 0x948 wrapper는 0x81C의 main/sub 콜백 테이블 저장을 호출하고, 0x8F4는 그 테이블을 검색합니다. 0x5F3–0x642의 vtable 구성과 0x754–0x774의 인터페이스 설치를 따라가면 공개 method+0x20은 위 0x9A0 디스패처입니다. SecLagacySabi의 selector81 중계가 이 메서드로 연결됩니다. 이는 정적 레거시 중계 연결이며 현재 Windows WMI 전체 실행 경로를 검증한 것은 아닙니다. 내부 초기화 표의 21개 루틴을 대상으로 한 제한된 추적에서는65/66 연결을 관측하지 못했으나, 다른 모듈의 공개 등록 경로가 열려 있어 미등록·기능부재를 확정하지 않습니다.

이미 받은 실제 결과에는 첫 데이터 바이트 FF만 남아 있습니다. 나머지 바이트·헤더 echo를 복원할 수 없으므로 그 결과를 전체 실패 패턴 일치로 승격하지 않습니다. 현 장치가 이 모듈을 실행했는지도 입증하지 않았습니다.

## 실제 구형 OEM 호출자와 BIOS 화면 자료

구형 BatteryLifeExtender.exe의 조회 지점 4곳은 0x65와 11바이트 입력(80 + 0 열 개)을 준비합니다. RVA 0x2A6E/0x2B3E/0x2FD0 이후 첫 데이터가 1이면 80% UI, 그 외는 100% UI로 흐르며 API 반환 오류를 확인하지 않습니다. FF 전용 분기는 없습니다. 오류로 원래 입력80이 남아도 100% UI로 흐릅니다. **이 잘못된 fallback을 새 앱의 실제 보호 상태 해석으로 사용하지 않습니다.**

설정 핸들러 RVA 0x33A0–0x3433에는 0x66과 첫 바이트81/80의 분기가 있고 시작 중 설정 호출도 있습니다. 이는 다른 모델의 정적 호출 기록이며 현 장치용 실행 지시·안전성 근거가 아닙니다. 이 OEM 앱은 진단 목적으로도 실행하지 않았습니다. 기존 승인 실험과 첫11개 입력 바이트는 같지만, 구형 SABI2/3의 11바이트와 현재 WMI의 16바이트는 전송 계약이 다릅니다. 길이 차이를 현재 FF 원인으로 단정하지 않습니다.

P05ACJ Setup의 HII 문자열에는 Battery Life Cycle Extension과 80%/100% 도움말이 있습니다. 파싱한 10개 표준 IFR Forms 패키지에서는 해당 prompt/help 토큰을 사용하는 표준 question을 찾지 못했습니다. 문자열만으로 현재 노출된 BIOS 설정·활성 상태·제어 경로를 입증하지 않습니다. Smart Battery Calibration은 방전/보정 안내이며 충전 상한이 아닙니다.

SecSetupWin의 확인한 등록은 main5843/sub7C입니다. 다른 모델의 7A/E9 배터리 경로를 이 이미지에 적용하지 않습니다. 65/66 상수·등록자에 대한 제한된 정적 검색은 완전한 동적 등록 분석이 아니므로 미관측을 기능 부재로 확정하지 않습니다.

## 코드 변경

- WsabiWmiReplyResult에 별도 DispatchFailurePrefix를 추가했습니다. ValidFrame의 복사된 데이터16바이트에만 MatchesAnalyzedP05AcjPrefix / DiffersFromAnalyzedP05AcjPrefix를 계산하고 실패 프레임/거부 envelope는 NotInspected로 둡니다. 구조 검증 상태와 모든 하드웨어 권한 false는 유지합니다.
- 기존 GUI의 과거 WMI 결과 검토에서 유효한 FF 기록에 공통 실패 경로와 전체 데이터 부재의 한계를 설명합니다. 과거 parser·일회 예약·요청·OEM 실행·충전 제어 경로는 확장하지 않습니다. 새 분류는 현재 장치에서 응답을 수집하는 기능이 아닙니다.
- 새 패키지 보호 검사는 순수 응답 모델/디코더도 외부 접근 금지 범위에 포함하고, 새 분류가 없는 이전 Core DLL 혼합을 거부합니다. 빌드 메타데이터와 실행 안내도 한계를 명시합니다.

## 실행과 확인 범위

[프로그램 ZIP](../downloads/ATIVBatteryGuard-FIRMWARE-REPLY-EVIDENCE.zip) **하나만** 새 폴더에 전부 풀고 ATIVBatteryGuard.exe를 일반 권한으로 실행합니다. 소스 ZIP은 개발용이며 함께 풀 필요가 없습니다. 새 진단이나 노트북 시험·파일 재제출은 필요하지 않습니다. 원하는 경우 이미 보유한 과거 콘솔 출력만 오프라인 검토에 붙여넣어 새 설명을 볼 수 있습니다. 입력 원문은 검토 후 비우고 저장하지 않습니다.

새 배포는 미서명 개발판이며 현재 Windows GUI 실행은 클라우드에서 검증하지 못했습니다. 사용자가 선택적으로 확인할 항목은 기존 배터리 표시 유지, 기존 FF 결과의 공통 실패 경로/확정불가 설명, 실제 제어 Unsupported 유지입니다. 이것을 위한 OEM 재호출·관리자 비교·1회 예약 삭제는 하지 않습니다. 삼성 원본 DLL·EXE·펌웨어와 실험 실행 파일은 포함하지 않습니다.

## 다음 개발 수용 조건
