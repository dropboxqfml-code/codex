# 고정 조회 후보의 응답 거부 명세와 남은 보호 연결 — 2026-11-08

**응답 거부 규칙과 충돌 모델을 비실행 명세로 구체화했습니다. 실제 호출의 입력 보호는 알려진 Runtime 게시자의 순서 연결이 남아 있습니다.** [입력·응답 수명 검토](FIXED_READ_INPUT_AND_CAPTURE_REVIEW.md)의 후속이며 공개 entry 활성화·실기 시험 승인이 아닙니다. 보호 조회·충전 제어는 Unsupported입니다.

이번 결과는 새 firmware 함수 발견이 아니라 기존 source 전제, 반환되는 8개 보존 셀, 관측 가능한 거부 규칙의 합성입니다. 실제 command/address 조합·요청·응답 frame·표식 값·생성기·실제 backend는 만들지 않았습니다.

## 관련 참여자의 적용 범위

| 보존된 연결 | 적용하는 보호 근거 | 이번 안의 처리 |
| --- | --- | --- |
| 네 WSABI 원본의 선택 WMI 호출 | 정상 획득한 같은 Global 협력 mutex가 입력 준비부터 private 응답 복사까지 유지됨 | 같은 공유 host frame의 확인된 협력 경로로 분류. 현재 설치·호출 관측을 새 사실로 주장하지 않고 기존 정상 source 전제로 재사용 |
| 정상 초기화·비재진입의 같은 SMM domain에 연결된 게시자 | 해당 domain의 callback CPU 순서 | EC 전송 구간에 적용. SMM 밖 WM00 입력 저장·반환까지 보호한다고 확대하지 않음 |
| host RuntimeServices의 변수 저장→NV persistence→flash 후크→같은 indexed 게시자 | 실제 공유 자원으로 이어지는 source 연결은 있음 | boot-only나 Global mutex 참여자로 분류할 수 없음. 부팅 후 중계 교체와 관련 전송이 선택 조회와 어떻게 순서화되는지 미완료인 구체 경로로 유지 |
| Native Sabi3/driver, 이름만 있는 직접 호출자 | 선택 WMI host frame·현재 indexed 교환과의 실제 연결 미입증 | 다른 mutex 이름만으로 현재 경쟁자로 추가하지 않음. 모든 미확인 호출자 부재를 증명하도록 요구하지 않음 |

Runtime의 정상 부팅 후 legacy SMI fallback에 대해 이미 연결한 같은 root 순서 근거도 유지합니다. 이를 미연결인 모든 통신 분기나 직접 host 경로에 확대하지 않습니다. 남은 문제는 단순히 실기 가입을 관측하지 못했다는 사실이 아니라, **구체적으로 연결된 Runtime 게시자의 해당 입력·재사용 구간에 적용할 보호/순서 계약**입니다. 같은 GUID 검색·helper 재검산을 새 진전으로 세지 않습니다.

기존 worker의 inline 입력 소비·버퍼 분리와 알려진 ISR 보존도 그대로 재사용합니다. 반환 10바이트와 upload/download 30바이트, 전체 indexed 자원 수명은 앞선 검토의 구분을 유지합니다.

## 관측값으로 확정할 수 있는 거부 규칙

아래는 실제 결과 parser가 아니라 향후 명세의 판정표입니다. 실제 source/profile·command/address 무결성·관련 참여자 보호는 실행 전에 별도로 성립해야 합니다. 관측할 수 없는 `reader 실행됨`이나 `fresh임`을 입력 boolean으로 넣어 결론을 만드는 방식은 사용하지 않습니다.

| 관측 또는 조건부 경우 | 거부 규칙 / 해석 한계 |
| --- | --- |
| API/method 실패·구조/ACK 오류 | 후보값을 수용하지 않음. 이것만으로 실제 미게시나 provider 종료를 추론하지 않음 |
| 기존 공통 실패 prefix | sample이 zero여도 거부. 이미 있는 실패 표시를 재사용하며 제품 버그 발견으로 세지 않음 |
| 선택 정상 반환 형식·보존된 둘째 성분·비교 내용 불일치 | 거부. 일치 자체가 과거 입력 안정성의 증거는 아님 |
| 입력 첫 성분 그대로의 echo | 고정 profile의 입력 성분과 좁은 후보 0/1 영역이 분리된다는 기존 근거 아래 거부 |
| 후보 0/1 밖의 값 | 판정불가. 자동 OFF 변환 없음 |
| no-copy/command-only의 전체 zero 비교 내용 | 아래 nonzero 비교 영역과 불일치하므로 거부. 이 검사가 실행 전 branch 무결성을 대신하지 않음 |
| upload 생략 뒤 이전 내용과 현재 비교 내용이 불일치 | 거부. 일치할 우연은 아래 모델에 명시 |
| 다른 생산자가 현재 비교 내용을 보존하고 허용 sample만 씀 | 관측 검사만으로 통과할 수 있음. 실행 전 관련 생산자 보호·구별 근거가 필요 |
| 서로 다른 생산 구간의 혼합 복사·새 내용 replay | 관측 검사만으로 통과할 수 있음. 아래 충돌 한계의 적용 대상이 아님 |

## 비교 내용의 명시적 충돌 모델

기존 ‘fresh content’ 문구를 다음 **검토용 확률 모델**로 구체화합니다. 실제 난수 선택이나 생성기를 실행·구현한 것은 아닙니다.

- 비교에 사용하는 것은 반환되는 8개 보존 셀, 즉 64bit 공간입니다. 실제 target나 명령 값을 여기에 포함하지 않습니다.
- 전체 zero인 원소 하나를 제외한 영역에서 균등하게 한 번 선택한다고 가정합니다. 이 영역의 크기는 `2^64 - 1`입니다. no-copy가 남기는 전체 zero 형상과는 결정적으로 분리됩니다.
- 비교할 이전 8개 셀 tuple 하나는 선택 이전에 고정되고 새 선택과 독립이어야 하며, 회수는 그 단일 tuple을 일관되게 반영해야 합니다. 이전 tuple이 zero이면 우연 일치는 0, nonzero이면 정확히 `1 / (2^64 - 1)`입니다. 이는 약 `5.42 × 10^-20`이고 **0이 아닙니다**.
- 이 수치는 단발 비교 하나의 조건부 한계입니다. 여러 이전 후보·재시도·비균등/의존 선택·replay·다른 생산자의 새 내용 주입·혼합 복사를 포함하지 않습니다. 실제 엔트로피·독립성을 측정했다는 주장도 아닙니다.

이는 **한 시도에서 old 내용이 우연히 일치할 확률**이지, 수용된 결과가 틀릴 조건부 확률이나 성공 신뢰도 `1 - p`가 아닙니다. reader에 전혀 도달하지 않는 상황에서는 드문 수용 결과가 모두 충돌일 수도 있습니다.

‘우리 프로그램이 재사용하지 않았다’는 사실만으로 unknown 초기 내용과의 결정적인 불일치를 보장하지 않습니다. 해당 충돌 모델을 허용하지 않는 시험이라면 별도의 결정적인 내용 구분 근거가 필요하며, 이번 자료만으로 그것을 확보했다고 하지 않습니다. 반대로 EC 고유 완료ID나 직접 reader 실행 관측만을 유일한 해법으로 요구하지도 않습니다.

## 수용 후보의 귀속을 도출하는 조건

고정 source/profile·정상 mapper/주소 공간 대응, command/address 무결성과 관련 참여자의 입력·회수 보호를 먼저 적용합니다. 그 위에서 경우를 나눕니다.

1. 미게시 old 내용은 비교 불일치로 거부하며, 일치 예외는 위 단발 충돌 모델로 제한합니다.
2. 새 입력만 upload되고 sample이 갱신되지 않은 경우는 입력/후보 영역 분리로 거부합니다.
3. 실패·no-copy·잘못된 반환 형식은 정의한 관측 규칙으로 거부합니다.
4. 그 내용을 보존하면서 다른 허용 sample을 만드는 **관련** 대체 생산자와 혼합 회수는 별도의 source/보호 계약으로 배제하거나 구별합니다.

그 전제와 명시한 충돌 예외 안에서 수용되는 결과를 선택 reader의 저장 모드 **후보**로 연결할 수 있습니다. 처음부터 이번 reader가 실행됐다고 가정한 뒤 같은 결론을 얻는 순환논증은 아닙니다. 현재는 Runtime 관련 보호 연결이 남아 이 충분 계약 전체가 닫힌 상태가 아닙니다. 저장 후보를 충전기 적용·실제 충전 중단으로 승격하지 않습니다.

## 검증과 현재 상태

실행용 byte 없이 14개 조건부 경우와 관측 조합 256개를 검사했습니다. wrong-producer·혼합 회수·old-content 충돌이 같은 관측값으로 통과할 수 있다는 반례도 유지합니다. 이 수치는 추상 명세의 검산이며 앱 테스트·원본 실행·실기 관측 수가 아닙니다. 독립 검토와 [정제 기록](reports/fixed-read-acceptance-spec-audit.json)에 source 참조·한계를 남깁니다.

새 firmware edge·실제 race 발견은 0입니다. 검산기의 추상 boolean 차원 오기 1건을 수정한 뒤 통과했으며 제품 오류가 아닙니다. C#/프로젝트·SDK·앱·기존 EXE/ZIP은 변경하지 않아 빌드/C# 테스트는 재실행하지 않았습니다. 617개와 빌드 경고/오류 0은 62f2d2e의 이전 기록입니다.

공개 ReadSpecificationUnavailable와 Unsupported를 유지합니다. A의 호출 상한·handshake/초기화/재시도/쓰기/B fallback 0, 기존 소모 예약 접근·복원·재사용 금지도 유지합니다. 실제 하드웨어/OEM/SDK/Global 객체 접근, 삼성 원본 실행·로드·에뮬레이션, 드라이버/서비스/보안/펌웨어·클라우드 환경 변경은 없습니다. 새 노트북 시험·자료 재제출은 필요하지 않습니다.

다음 근거 확보는 위 Runtime 게시자의 부팅 후 적용 경로·선택 조회와의 순서 연결에 집중합니다. 전체 writer/IRQ·live hash·gate-open 실측을 새 절대조건으로 넓히지 않습니다. 이 입력 보호가 해결된 뒤에야 고정 요청·실제 비교 내용 생성·거부 parser·시험용 빌드를 검토할 수 있습니다.
