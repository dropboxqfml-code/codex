## 4. 완료한 기능과 검증

- 충전 제한 현재 설정 확인, 명시적인 80% 제한/제한 해제, 일반 권한 GUI와 선택 시 별도 관리자 helper.
- Windows 배터리·전원·충전 상태 표시, 약10초 주기 기록, 최대2시간 관찰, TXT 저장.
- 마우스/Tab·좌우/Home/End 그래프 표본 선택, 과거 TXT·최근10개 목록, A/B 비교.
- 기록별 최대1000자 메모, 충돌/저장 실패/닫기 취소 보존, `.ativrecord` 내보내기/불러오기.
- 0.3.1: 마지막 확인이 제한 해제면 해제 버튼, 모드1/80/75 확인이면80% 버튼만 기존 파란색으로 표시. 미확인/처리/다른 임계값은 양쪽 모두 강조하지 않음. 나머지 디자인은 유지.
- 클라우드 제품 회귀1275개·Python 배포 검사27개 통과. portable/전체net48 WPF/확인 도구 빌드 경고·오류0. [빌드 기록](reports/release-031-validation.json).
- 사용자 Windows10의0.3.1 파일 전후/GUI·합성 버튼 색 전환 검사 통과, 종료0, 오류·바인딩 오류0, 기본 배터리available/WMIcomplete. 버튼 강조 정상이라는 별도 사용자 확인도 받음. [원본 평가](reports/field-031-personal/assessment.json).
- 기존 충전 제한/해제·재시작 유지, IME 저장/닫기 취소, 빠른/20분 검사 근거 인계. 문제와 관계없는 검사를 다시 요청하지 않음.

과거 원본 도구 JSON의 `FinalReleaseApproved=false`/`ManualUserFlowsConfirmed=false`는 그 자동 도구의 실행 범위입니다. 현재 개인용 완료 판정은 위 현장 평가에 따릅니다. 원본 JSON을 고쳐 완료로 꾸미지 않습니다. 매뉴얼 동봉본의 개인용 완료 메타데이터는 같은 프로그램6파일에 대한 기존 현장 결과를 인계한 것입니다.

이 문서 정리 과정에서 기능/Windows/보안 검사를 새로 실행한 것은 아닙니다. 서명·새 Defender 검사·공개 배포 승인을 완료로 해석하지 않습니다.

## 5. 유지해야 할 조건

- 사용자는 디자인 유지와 필요한 부분만 수정하는 방식을 원합니다. 다른 모델명은 화면에 추가하지 않습니다. 펌웨어 검증용 원시 모델 문자열 `940X3G/930X3G`는 화면 문구와 별개이므로 바꾸지 않습니다.
- 읽어 확인한 장치 상태, 사용자 희망 설정, Windows 배터리 잔량을 구분합니다. 모드1만으로80%를 확정하지 않습니다. 조회 상태의 ‘마지막 확인’ 의미를 유지합니다.
- 앱 시작/배터리 갱신/getter/진단에서 OEM 쓰기를 추가하지 않습니다. 자동 재시도·부팅 적용·서비스·드라이버·시스템 정책/보안 설정 변경·런타임 네트워크 통신을 추가하지 않습니다.
- 기존 고정 프로필/공통 mutex/동작 횟수/정리 완료·불명 상태 차단/수동 승인 조건을 유지합니다. `ReadState` 최대SDK3/설정0, `Enable80` 최대SDK7/설정1, `DisableProtection` 최대SDK3/설정1입니다. 실제 하드웨어 시험이나 새 펌웨어 경로는 기존 승인 범위와 별도로 판단합니다.
- 현재는 미서명 개인용입니다. 서명 안내는 사용자 매뉴얼에만 두며 앱 UI에 추가하지 않습니다. 사용자는 필요한 파일의 SmartScreen ‘추가 정보 → 실행’을 선택할 수 있습니다. 인증서 구매·자체 인증서 신뢰 등록·보호 기능 해제를 요구하지 않습니다.
- 사용자 PC의 `%LOCALAPPDATA%\ATIVBatteryGuard`에 있는 실제 설정/기록/메모는 GitHub나 이 워크스페이스에 자동 저장되지 않습니다. 기존 자료를 삭제하거나 초기화하지 않습니다. 기본 진단에 사용자 이름/시리얼 등 고유 정보를 추가하지 않습니다.

## 6. 새 문제를 수정할 때

1. 사용 버전, 현상, 재현 순서, 정확한 오류 문구와 관련 파일을 확인합니다. 저장소/기존 보고서에서 알 수 있는 내용은 먼저 확인합니다.
2. 기존 정상 결과와 비교해 관련 ViewModel/View/저장소 또는 서비스만 조사합니다. old trial EXE/CMD를 재실행하거나 과거 패치를 다시 적용하지 않습니다.
3. 수정 후 변경 범위에 맞는 회귀/빌드/패키지 확인을 수행합니다. 문서 교체만이면 실행 파일 동일성/ZIP/해시를 확인하며 하드웨어·IME·20분 시험을 반복하지 않습니다.
4. 코드/실행 파일이 바뀌면 새 유지보수 버전/새 파일명으로 분리하고 이전0.3.1 기준을 남깁니다. 변경된 GUI에 필요한 Windows 검사만 요청하며 Linux 빌드를 실제 Windows 실행으로 표시하지 않습니다.
5. 패키징 스크립트는 특정 검증 기준에 고정돼 있습니다. 새 소스에 맞지 않는다고 검증 조건을 지우거나 예전 합격/서명 플래그를 복사하지 않습니다. [파일 색인](FILE_INDEX.md)의 패키징 구분을 따릅니다.
6. 이번 증상·수정·검사·미실행 항목을 새 문서/보고서로 기록하고 브랜치에 커밋·푸시합니다. 사용자가 받을 파일은 GitHub에서 실제 다운로드 가능한 링크로 제공합니다.

새 대화에 붙여넣을 문구는 [NEW_CHAT_START.txt](NEW_CHAT_START.txt)에 있습니다. 새 문제를 받기 전에는 현 버전을 유지하며 추가 개발을 시작하지 않습니다.
