# 보호 모드·임계값 조회와 설정 응답의 판정 계약 — 2026-11-09 한국 시간

고정7단계 원형의 후속으로 **분리된 응답 데이터만 검사하는 internal 판정기 두 개**를 구현했습니다. 하나는 모드·상한·하한 읽기 후보를 구별하고, 다른 하나는 설정1의 정상 응답 형식을 `ReceiptOnly`로 분류합니다. 실제 요청 생성·SDK 연결·새 실행 도구는 없으며 충전 제어는 Unsupported입니다.

## 이번에 확정한 차이

| 구분 | 정상 응답에서 검사할 내용 | 검사 통과의 의미 |
| --- | --- | --- |
| 모드 읽기 | 기존 엄격 형식·보존 내용, 표본0/1, 입력 첫 성분과 다름 | 조건부 저장 byte 후보. 현재 모드·충전 성공 인증은 아님 |
| 상·하한 읽기 | 같은 형식·보존 내용, 표본0..255, 입력 첫 성분과 다름 | 조건부 임계값 byte 후보. 읽기 역할·대상은 별도 연결 필요 |
| 상·하한 읽기의 표본이 입력 첫 성분과 같음 | 합법적인 저장 byte와 미갱신 입력 echo가 같은 응답이 될 수 있음 | `AmbiguousInputEcho`, 후보값 없음. 범위 오류나 기능 미지원으로 바꾸지 않음 |
| 설정1 응답 | 같은 형식·보존 내용, 첫 메시지 byte는 입력1 그대로 | `ReceiptOnly`. setter 실행·저장 변화·실제 종료는 여전히 미입증 |

기존 모드 단발 읽기는 후보0/1과 입력 첫 성분의 영역이 분리돼 있습니다. 임계값의 영역은 모든 byte이므로 그 반향 거부 규칙을 단순히 제거해 전체256값을 수용할 수 없습니다. 합법적인 값도 입력과 겹치면 보류해야 합니다. 이를 피하려고 다른 주소·명령·쓰기·재시도를 자동 선택하지 않습니다.

반대로 선택 setter는 첫 메시지 byte를 저장 상태로 바꾸는 getter가 아닙니다. 정상 처리 뒤에도 입력1을 그대로 보존하므로 읽기의 echo 거부 규칙을 setter에 적용할 수 없습니다. 같은 응답 tuple은 setter가 실행되지 않고 입력만 반영된 경우에도 가능합니다. outer ACK·정상 API 반환·보존 내용 일치를 독립적인 setter 성공 코드로 만들지 않습니다.

## 입력·검사·출력

`WsabiWmiProtectionReadReplyReview`는 사전·사후의 모드/상한/하한 **여섯 읽기 역할**만 받습니다. 기대하는 첫 성분과 보존 둘째 성분은 각각 byte 범위로 제한하고, 비교 내용은 정확한 일반 `byte[8]`의 독립 복사본으로 보유합니다. 전체zero 비교는 거부합니다. 대상 주소나 selector를 선택·해석하는 기능은 없으며, 역할은 공급자가 붙인 기대 label입니다.

`WsabiWmiProtectionSetterReplyReview`의 의미 입력은1만 허용합니다. 보존 둘째 메시지 byte와 비교8개를 별도로 받으며 동일한 크기·범위·복사 규칙을 적용합니다. 이 둘째 byte는 setter의 대상 주소가 아닙니다. 생성자는 의미와 비교 기대값만 보유하며 firmware 명령이나 전송 요청으로 인코딩하지 않습니다.

두 판정기는 기존 `WsabiWmiFrameExchangeResult`의 분리된 값만 검사합니다. 실패·취소·Busy·시간 초과·전송 실패를 구분하고, method envelope `FrameChecked`와 기존 정확한21byte/ACK 구조를 요구합니다. 이어 공통 실패 prefix, 제어2셀zero, 꼬리4셀zero, 보존 성분과 비교8개의 일치를 검사합니다. 내부 payload 복사본은 검사 뒤 지웁니다. 원문 frame·비교 내용·SDK 객체·경로·사용자 이름·고유 식별자를 결과에 넣지 않습니다.

읽기 결과는 역할·상태·선택적 byte 후보만, setter 결과는 역할·상태만 보유합니다. 모드 후보는0/1이고 임계값 후보는byte 범위입니다. 잘못된 구조·불일치·입력echo와 구분 불가에서는 후보를 남기지 않습니다. 원형의 사후1/80/75 비교는 별도 순수 전환 모델의 역할이며, 이 parser가 기대값으로 관측값을 덮어쓰지 않습니다.

## 귀속·신선도·수명에서 남는 경계

보존 내용이 맞는다고 첫 입력 소비 시점의 안정성, 새 게시, 의도한 reader 실행, 정확한 대상이나 현재 관측을 인증하지 않습니다. 같은 비교·응답에 상한/하한이라는 다른 역할을 붙이면 둘 다 형식상 맞을 수 있다는 반례도 테스트로 유지했습니다. 따라서 두 새 결과에서 `CanSupplyTransitionObservation`은 항상false이며 기존 `AcceptedCurrentRead` 또는 `SetterAcknowledged`를 자동 생성하지 않습니다.

예전 단발 명세의 조건부 `1 / (2^64 − 1)` 비교 충돌 모델은 전체7단계의 성공 신뢰도가 아닙니다. 이번 코드에는 비교 내용 생성·엔트로피·단계 간 독립성·중복 배제 기능이 없습니다. 다른 생산자의 현재 내용 주입, 혼합 복사·재생과 잘못 붙인 역할도 그 단발 모델로 배제할 수 없습니다. 기존 적용 source·입력 보호·회수 보호 전제를 유지하며 모든 writer 부재나 live 전체 hash를 새 절대조건으로 추가하지 않습니다.

구조상 정상 setter 응답도 실제 close의 증거가 아닙니다. 향후 host는 앞서 구현한 전체 owner 원형과 실제 SDK 입력·관찰자·capture의 close를 별도로 연결해야 합니다. timeout·CallCanceled·Start 예외·정리 불명에서 후속 단계를 자동 진행하거나 lease를 조기 해제하지 않습니다. 원래 A/Access1/Query65의 소모 예약을 읽거나 되돌리지 않습니다.

독립적인 setter 성공 코드를 새로 확보해야만 영원히 후속 조회가 가능하다는 조건도 두지 않습니다. 향후 구체 시험 계약은 **엄격히 수용한 receipt와 실제 close를 확인한 뒤, setter 효과는 Unknown인 상태로 독립 readback을 진행**하도록 명시할 수 있습니다. 그때는 현재 시험용 `SetterAcknowledged`를 `ReceiptOnly`와 혼동하지 않도록 단계 전이 계약을 분명하게 바꿔 검증해야 합니다. 이번 변경은 그 전이를 자동 연결하지 않았습니다.

## 재사용한 근거와 검증

[응답 위치 계약](FIXED_READ_BYTE_CONTRACT_REVIEW.md), [거부·충돌 모델](FIXED_READ_ACCEPTANCE_SPECIFICATION.md), [선택 setter와 전환](PROTECTION_TRANSITION_REVIEW.md), [오류 가림·과거 응답 경계](EC_FRESHNESS_AND_ERROR_PATHS.md)를 재사용했습니다. 저장된 setter/helper/dispatcher 선택 proof는 전체10개 메시지 byte 보존을, generic callback proof는 payload20개clear 뒤10개반환을 지지합니다. 원본을 새로 decode·검색·실행하지 않았고 두 저장 proof의 SHA256을 다시 확인했습니다. 같은 source를 새로운 독립 firmware 증거로 합산하지 않습니다.

새 회귀는 읽기15개·setter12개 그룹입니다. 여섯 읽기 역할×모든256byte, 실제 값/echo 겹침, 보존·제어·꼬리 각 셀 변조, 공통 실패의0표본, no-copyzero, method/형식/API/ACK/전송 실패, 입력 복사·불변 결과와 권한 승격 부재를 포함합니다. 반복 조합을 별도 테스트 수나 firmware 분석률로 세지 않습니다. 테스트는 실행용 header가 없는 합성 **응답**만 만들며 실제 요청·노트북 관측을 생성하지 않습니다. 최종 검증은 [정제 기록](reports/protection-reply-contracts-validation.json)에 보존합니다.

새27개를 포함해 **786통과·0실패·0skip**이며 portable와 전체 net48 참조 Release 빌드가 각각0경고·0오류입니다. 두 판정기·테스트에 대한 독립 읽기 검토에서 차단 결함은 없었습니다. 실제 Windows/.NET48 런타임·SDK/OEM·하드웨어·Global 객체 실행은0입니다.
