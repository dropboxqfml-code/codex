# 보호 모드 전환 검토와 다음 시험 설계 — 2026-11-08

**2026-11-09 한국 시간 후속:** [모드·임계값 읽기와 설정 응답 판정](PROTECTION_REPLY_CONTRACTS.md)을 internal 순수 코드로 구현했습니다. 정상 setter echo는 `ReceiptOnly`이며 실제 실행·저장 상태·close를 입증하지 않습니다. 현재 `SetterAcknowledged` 모델로 자동 연결하지 않고, 향후 receipt+actual-close 뒤 독립 readback의 전이 계약을 명시적으로 검토합니다. 실제 쓰기는 여전히0입니다.

**후속 구현:** [고정7단계 판정 모델·전체 owner 내부 원형](SEVEN_STAGE_COORDINATOR_PROTOTYPE.md)을 대역으로 검증했습니다. 새32개 포함759테스트 통과·두 Release 빌드0경고·0오류입니다. 실제 SDK adapter·설정 인코딩·새 실행 도구는 없으며, 아래 시험 설계는 실제 쓰기 승인이나 실행 결과가 아닙니다.

**Access1은 저장 모드 후보0을 반환했습니다. 다음 개발은 이 관측과 저장된 setter·정책 근거를 연결해 전환 시험의 범위를 정하는 단계입니다. 실제 설정 변경은 아직 승인·구현하지 않았으며 충전 제어는 Unsupported입니다.**

새 결과는 Elevated, 예약 Claimed, 사전 검사·SDK 준비 Ready, 입력 구성, ReplyReceived, 엄격한 응답 검증의 StoredModeCandidate0, 관련 정리 Complete를 기록했습니다. 이는 앞서 실패했던 준비 단계를 지나 고정 저장 byte의 후보를 얻은 첫 관측입니다. 원래 A·Access1·과거 Query65의 소모한 예산은 유지하며 새 실행이나 추가 예약을 만들지 않습니다.

## 후보0이 말해 주는 범위

후보0은 **그 조회에서 수용된 소프트웨어 저장값**입니다. 저장된 모델의 상위 제한 정책은 모드가 0이면 보호용 상한 분기를 건너뛰고, 모드가 0이 아니면 그 분기를 사용합니다. 따라서 이번 관측은 해당 저장 상태와 실제 노트북의 읽기 경로를 연결하는 진전입니다.

이를 현재 보호 기능 OFF, 100% 충전 설정, 충전 재개 완료로 표시하지 않습니다. 같은 source의 정상 모드 하위 정책에는 별도 flag에 따라 96/97 기준을 선택하는 분기가 있습니다. 이 숫자는 저장 source의 조건이며 현재 노트북에서 측정한 임계값이 아닙니다. 모드0은 단순히 상한에 100을 쓰는 동작이 아닙니다.

Access1은 상·하 임계값과 충전기 레지스터를 읽지 않았습니다. 관련 정리 Complete는 입력·관찰자·소유권 수명의 종료이며, 나중에도 저장값이 같다는 보장은 아닙니다. 이 값을 다음 쓰기의 확정된 직전 상태나 영속적인 actualMode로 저장하지 않습니다.

## 전환별로 달라지는 효과

다음 표는 저장된 동일 setter 본문의 조건부 source 의미입니다. 실제 노트북에서 아래 전환을 실행한 결과가 아닙니다. 입력 후보는 0/1로 제한해야 하며, setter 자체에 임의 입력값을 막는 검사가 있다는 근거는 없습니다.

| 확인한 이전 후보 → 요청 후보 | 선택 setter 본문의 효과 | 이후 확인할 내용 |
| --- | --- | --- |
| 0 → 1 | 모드를 1로 저장한 뒤 상한80·하한75를 순서대로 초기화 | 독립 조회의 모드1 및 임계값80/75. 충전기 적용과 전기적 충전 제한은 별도 |
| 1 → 0 | 모드를 0으로 저장하고 별도 소프트웨어 상태를 reset | 독립 조회의 모드0. 이 본문은 임계값을 100으로 바꾸거나 초기화하지 않음 |
| 1 → 1 | 값이 같으면 조기 반환 | 임계값80/75를 다시 설정한 것으로 해석할 수 없음 |
| 0 → 0 | 값이 같으면 조기 반환 | 모드·임계값·해당 reset을 새로 변경한 것으로 해석할 수 없음 |

상·하 정책은 이 모드와 같은 저장 셀 및 인접 임계값을 읽습니다. 별도의 배터리 polling producer와 소비자의 연결은 상대 잔량 기반의 상한 억제·하한 재개 요청을 뒷받침하며, 하한 경로에는 추가 유효성·배터리 상태 조건이 있습니다. 충전기 요청을 기록하는 소프트웨어 분기는 각 bus 쓰기의 성공을 모두 확인한 뒤에만 진행하는 구조로 입증된 것이 아닙니다. 저장값 변화와 충전기 적용 성공을 분리해야 합니다.

특히 모드1 관측만으로 현재80/75를 추론할 수 없습니다. 같은1 입력은 임계값을 고치지 않습니다. 이를 맞추려고 1→0→1을 자동 실행하는 우회도 이번 범위가 아닙니다.

## 설정 경로에서 이미 알려진 것과 아직 실행하지 않은 것

저장된 Windows 중계 callback은 정해진 upload-and-receive 분기에서 입력의 명령 성분과 메시지 성분을 EC sender로 전달합니다. 저장된 EC 명령 표는 이 setter로 연결되고 setter는 첫 메시지 성분을 모드 입력으로 읽습니다. 따라서 **정적 중계 선택·입력 위치와 모델의 setter 연결은 이미 근거가 있습니다.** 새 selector 탐색을 처음부터 반복할 단계가 아닙니다.

이 연결은 원래 OEM Windows 프로그램의 고정 설정 호출자를 새로 발견한 것이 아닙니다. Access1에서 성공한 동작도 읽기 명령 하나이며, setter의 실제 처리·상태 변화는 아직 관측하지 않았습니다. 새 쓰기 frame, 임의 주소 쓰기 API, 직접 메모리 쓰기나 실행 경로는 만들지 않습니다. 향후에는 임계값을 byte 단위로 직접 쓰는 경로보다 위 **고정 의미의 setter**만 검토해야 합니다.

setter는 입력 첫 성분을 독립적인 저장값으로 바꿔 반환하는 getter가 아닙니다. 따라서 정상 API 반환, ACK, 정상 완료, 입력0/1의 echo, 비교 내용 보존은 각각 전달·완료 검사의 일부일 수 있어도 설정 성공 판정이 될 수 없습니다. 뒤따르는 별도의 고정 읽기가 필요합니다.

## 이번 비실행 구현과 다음 연결 범위

**실행 기능 없는 고정0→1 결과 판정 모델**과 internal coordinator 원형을 구현했습니다. 과거 후보0을 현재 사전값으로 수용하지 않으며, 사전0·사후1/80/75와 ACK를 구분합니다. 위 네 전환의 source 표 전체를 실행하는 범용 계획기는 아닙니다. 순수 모델에는 dispatcher·예약·명령 생성·SDK 호출이 없고, coordinator도 실제 adapter 없이 역할·숫자·가짜 수명으로만 검증했습니다. 모델 예상값은 관측값과 다른 필드로 보존합니다.

이와 함께 다음 제어 시험안은 아래 순서로 구체화합니다.

1. **최신 사전 관측의 범위를 정합니다.** Access1의 과거0을 재사용하지 않고 시험 직전 고정 모드 읽기를 별도 예산 안에서 검토합니다. 임계값 보존·역방향 전환을 비교할 목적이면 두 임계값도 기준값으로 필요합니다.
2. **하나의 의도한 전환만 선택합니다.** 예를 들어 0→1 시험이라면 사전 모드가 이미1이거나 불명일 때 setter를 호출하지 않습니다. 불일치를 강제 토글이나 다른 명령으로 해결하지 않습니다.
3. **설정 setter 최대1회 뒤 독립 readback을 정의합니다.** 저장 모드와 두 임계값을 별도 항목으로 판정합니다. 여러 byte 조회가 하나의 원자적 snapshot이거나 read와 setter 사이가 compare-and-set이라고 주장하지 않습니다. 관측이 서로 모순되면 추가 설정 없이 판정불가입니다.
4. **종료·실패 계약을 먼저 적용합니다.** 표시 timeout이나 CallCanceled는 실제 종료가 아닙니다. 입력·관찰자·lease의 실제 종료를 확인하기 전 후속 조회를 시작하지 않으며, 종료 불명에서는 pending과 보유를 유지합니다. 기존 SDK Cancel·합성 final·watchdog·재시도 금지는 유지합니다.
5. **저장 전환과 충전 효과를 분리해 시험합니다.** readback 일치는 저장 전환에 대한 증거입니다. 이후 정상 정책이 충전기에 적용되는지와 실제 충전 억제·재개는 별도 관측 단계입니다. 잔량80%나 ‘충전 중 아님’ 하나를 성공 조건으로 삼지 않습니다.

현재 코드의 승인된 getter는 모드 한 byte만 읽습니다. 임계값을 읽는 별도의 고정 대상·엄격 응답 판정과 위 다단계 수명을 검토·검증하는 작업이 남았습니다. 이를 승인된 단발 도구에 자동 추가하거나 이미 소모한 marker를 재사용하지 않습니다.

### 단발 교환과 전환 전체의 소유권

현재 `WsabiWmiCooperativeFrameChannel`은 한 frame마다 전용 owner thread에서 gate를 획득하고, 해당 실제 호출 종료를 기다린 뒤 lease를 해제합니다. 준비된 invocation도 한 번만 실행합니다. 같은 gate 객체를 다음 frame에 전달하더라도 그 사이를 다른 협력 client가 사용할 수 있습니다. 기존 wrapper를 바깥에서 한 번 더 감싸는 중첩 owner 방식은 지원하지 않습니다.

향후 여러 단계 전환을 하나의 순서로 보호하려면 **한 번의 owner 획득부터 마지막 단계의 실제 종료·정리까지 유지하는 single-use coordinator**가 필요합니다. 고정 순서와 각 단계의 입력·출력·관찰자 수명을 인계하고, 모드/임계값 불일치·호출 실패·중단에서는 뒤 단계를 시작하지 않으며, 종료가 불명인 단계가 있으면 전체 소유권도 보유해야 합니다. 단발 객체7개를 반복 실행하는 것으로 이 계약을 대체할 수 없습니다.

이 소유권은 같은 협력 경로의 다른 Windows 요청이 단계 사이에 끼는 것을 막기 위한 것입니다. EC RAM 전체를 동결하거나 정상 firmware 정책의 실행을 멈춘다는 뜻이 아니며, 모든 writer의 부재를 새 조건으로 요구하지 않습니다. 기존 정상 플랫폼·비재진입 stream의 적용 전제는 유지합니다. 현재 internal coordinator는 가짜 역할·수명으로 검증한 원형이며 실제 SDK 연결과 새 실행 API는 없습니다.

## 향후 시험의 호출 예산을 계산하는 기준

저장된 generic reader는 한 번에 고정 byte 하나를 읽습니다. 여러 셀을 읽는 bulk getter를 확보한 것으로 가정하지 않습니다. 아래는 **새 시험의 논리적 최소 단계 수를 비교한 설계값**이며 승인된 호출 수나 새 실행 도구가 아닙니다. 실제 sample은 준비·gate·전달 결과에 따라 더 적을 수 있습니다.

| 확인할 주장 | 필요한 최소 순서 | method 상한의 설계값 |
| --- | --- | --- |
| 최신 모드만 확인 | 모드 읽기 | 1 |
| 의도한 0→1 뒤 모드1·80/75 확인 | 직전 모드 읽기 → setter1회 → 모드·상한·하한 읽기 | 5 |
| 선택한 0→1 전환 전후 모드와 임계값 변화를 비교 | 모드·상한·하한 읽기 → 모드0일 때만 setter1회 → 모드·상한·하한 읽기 | 7 |
| 의도한 1→0 뒤 모드0만 확인 | 직전 모드 읽기 → setter1회 → 모드 읽기 | 3 |

마지막3회안은 임계값 보존이나 충전 재개를 확인하지 못합니다. 다음 구체안은 **한 번의 0→1 전환 전후 비교**를7회안으로 설계합니다. 사전 모드가0일 때만 setter최대1회이며,1·Unknown·사전 실패에서는 setter0회로 중단합니다. 정상 종료·응답 검증 뒤 후속 읽기, 재시도0회 및 각 단계 중단 조건을 구체화해야 합니다. setter의 응답이 실패하거나 종료가 불명인 경우에는 다음 조회도 자동 시작하지 않고 변경 여부 Unknown으로 끝냅니다. 역방향1→0 시험은 이7회에 포함되지 않는 별도 검토·예산입니다. 기준값을 더 읽는 이유는 비교 목적이며, 0→1이80/75를 초기화한다는 source 의미를 입증하려고 모든 사전 임계값 읽기를 무조건 요구하는 것은 아닙니다. 현 단계의 실제 설정 쓰기 예산은0회입니다.

## 실패·지속성·복원에서 남은 경계

| 경계 | 현재 근거 | 제어 시험에서 지킬 판정 |
| --- | --- | --- |
| 설정 응답 실패·timeout | 전달 실패와 실제 처리 여부가 항상 같은 것은 아님 | ‘변경 안 됨’으로 단정하지 않고 Unknown. 재전송이나 역방향 쓰기를 하지 않음 |
| 후속 readback 불일치 | setter echo는 독립 상태값이 아니며 여러 조회는 시간적으로 구분됨 | 예상값으로 실제값을 덮어쓰지 않음. 추가 변경 없이 정제된 실패 결과를 보존 |
| 임계값 복원 | 0→1은80/75를 쓰고 1→0은 그 값을 되돌리지 않음 | 단순 0→1→0을 이전 전체 상태로의 rollback이라고 부르지 않음 |
| 재부팅·절전 지속 | 선택된 초기화 경로 하나는 모드·두 임계값을 포함한 RAM 범위를 clear. 다른 선택 clear 구간에는 이 영역이 포함되지 않음 | 후속 초기화 전체의 보존은 미확정. 해당 분기를 특정 재부팅·절전 원인과 동일시하지 않으며 영속 저장·자동 복원을 추가하지 않음 |
| 충전기 적용·전기적 결과 | source는 억제·재개 요청과 충전기 쓰기로 이어짐 | 모드/임계값 readback과 별도 결과로 남김. 사용자 희망값·Windows 잔량과 합치지 않음 |

역방향1회 쓰기를 향후 검토하더라도, 알려진 직전 상태·현재 관측·해당 전환의 side effect·별도 승인 범위가 먼저 정해져야 합니다. 실패를 숨기기 위한 자동 rollback, 소프트웨어 값만 복원됐다는 이유로 전체 장치 상태가 복구됐다는 판정, 임의 임계값 직접 복원은 허용할 수 없습니다.

## 이번 검토의 근거와 완료 기준

재사용한 source는 고정 P05 capsule SHA256 `052660c18e967f7f73b2881379066bde4b90b29192ce4292c8d29bef1ce92ab0`와 그 파생 EC 자료, 중계 module SHA256 `2795669f18e3fb787d908ba00e2e9da7ab7d398ee599f27aa2f068129b46f310`의 저장된 선택 분석입니다. 원본과 파생 자료를 독립된 두 firmware 증거로 세지 않습니다. 새 원본 decode·검색·실행 없이 setter·소비자·초기화·중계의 기존 근거를 Access1 관측 이후의 전환 설계에 적용했습니다.
