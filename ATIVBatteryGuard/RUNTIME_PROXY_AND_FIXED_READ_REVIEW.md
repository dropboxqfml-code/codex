# Runtime 중계와 고정 조회 준비 조건 — 2026-11-07 한국 시간

후속 [부팅 순서·EC 인계 검토](EC_READ_HANDOFF_AND_BOOT_ORDER.md)에서 정상 성공 조건의 BDS 알림 선행, legacy SW fallback의 같은 default-root 실행 영역, Runtime/조회 helper의 같은 준비 규약을 연결했습니다. 특별 callback의 선택 사례는 legacy Communicate 입력 전달이며 표준 typed 통신으로 해석하지 않습니다. 아래는 당시 분석과 검사 기록입니다.

**변수 저장 경로의 초기 선택과 부팅 후 SMM 중계 교체를 연결했고, EC 후크의 실제 효과를 좁혔습니다.** 고정 보호 모드 한 바이트 조회를 비실행 제안으로 검토할 근거는 있지만, 실제 호출 backend를 추가할 조건은 아직 충족하지 못했습니다. 실제 보호 설정 조회·충전 제어는 미구현이며 제어는 Unsupported입니다.

[이전 OS 소비자 분석](RUNTIME_VARIABLE_AND_EC_IDENTITY_REVIEW.md)의 후속입니다. 기존 제조사 원본을 데이터로 읽었으며 새 노트북 시험·자료 재제출은 요구하지 않습니다. [고정 조회 검토안](FIXED_MODE_READ_PROPOSAL.md)은 실행용 입력이나 코드가 없는 설계입니다.

## 초기 구성과 후속 함수 교체

| 새로 연결한 구간 | 확인한 사실 | 남은 한계 |
| --- | --- | --- |
| PEI 구성 생산자 → Runtime | 정확히 같은 GUID HOB의 구성 필드를 생산·소비함. 저장 원본의 초기화된 결정 바이트는 정상 성공 경로에서 flash 계열을 선택 | 현재 장치의 HOB·초기화 성공·다른 생산자는 관측하지 않음 |
| host backend 초기화의 후반부 | 할당 성공 시 주소 보정 adapter, 실패 시 직접 flash adapter를 선택. 두 adapter의 begin/end는 기존 flash 후크로 연결 | 현재 할당·probe 결과는 미관측 |
| 부팅 알림 → host SetVariable | `NvramSmi`의 알림 callback이 실제 host RuntimeServices 슬롯을 중계 함수로 교체하고 표 CRC를 다시 계산 | 실제 알림 등록·전달·다른 writer와의 순서 및 최종 target은 미확정 |
| 알림 생산자 | 게시된 BDS entry의 고정 함수 목록에서 정확히 같은 marker를 설치·제거하는 생산자를 연결 | 현재 부팅에서 실행됐다는 관측은 아님 |
| 가상주소 전환 | 해당 시점에 슬롯에 있는 함수 포인터를 변환. 초기 함수를 복원하거나 backend 종류를 새로 고르지 않음 | 성공한 실제 주소 전환과 당시 슬롯 값은 미관측 |

이전의 “별도 SMM adapter” 표현은 정정합니다. 그 주소 보정 adapter는 **host 초기화에서도 선택**되므로 표의 정체성만으로 SMM 문맥을 판정할 수 없습니다. 또한 초기 직접 host 함수가 Windows에서 계속 최종 진입점이라고 가정할 수 없습니다. 나중의 중계 교체가 성공했다면 현재 포인터의 가상주소 전환도 그 중계 함수를 대상으로 합니다.

중계 함수는 일반 host 경로에서 변수 쓰기 인수를 공유 버퍼에 담아 통신 interface 또는 별도 software-SMI fallback으로 전달합니다. SMM 쪽에는 같은 통신 GUID로 등록된 수신 handler와 private RuntimeServices 형태의 표에 인수를 전달하는 core를 연결했습니다. private 표 선택·버퍼·등록 성공은 조건이며, 원래 host 함수를 저장했다가 복원하는 구조로 해석하지 않습니다. 이 경로를 실제로 실행하거나 EFI 변수를 저장하지 않았습니다.

## SMM 안이라는 사실과 같은 순차 실행 영역이라는 증거

기존 정상 SMM root의 default 순회와 이번 통신 handler의 GUID별 등록은 구분해야 합니다. default 순회는 해당 typed record를 직접 실행하지 않습니다. **통신 제공자 → 정상 진입 → 해당 GUID를 선택하는 dispatch**의 실제 연결이 추가로 필요합니다. 같은 registry에 등록됐다는 사실만으로 이 간극을 메우지 않습니다.

기존 PE index 231개 행의 해시를 확인한 정확한 표준 통신 GUID·선택 분할 상수 검색은 기존 소비자만 찾았고 새 제공자 후보는 없었습니다. 이는 제공자가 없다는 증명이 아닙니다. 계산·변환·동적 조립·외부 구성·다른 이미지·간접 공급 가능성을 남깁니다. 별도 legacy software-SMI fallback의 등록과 같은 server core 연결은 확인했지만, 이를 표준 통신 경로 또는 다른 SWDispatch 버전의 정상 root 근거와 합치지 않습니다.

따라서 초기 직접 경로의 지속도, 모든 host 호출의 정상 SMM 순차화도 현재 장치에서 확정하지 않았습니다. 실제 경합을 관측하거나 조회가 불가능하다고 판정한 것도 아닙니다.

## guard와 실제 EC 후크 효과

플랫폼 초기화의 조건부 callback에는 저장된 Lynxpoint 참고 헤더의 `SMI_LOCK` 위치와 맞는 비트를 쓰는 경로가 있습니다. 같은 알림의 임시 게시자도 연결했습니다. 현재 policy·잠금 값·쓰기 수용 여부는 미관측이며, 이 알림을 이름이 비슷한 ReadyToLock이나 flash 잠금으로 바꾸어 부르지 않습니다. 이전 Runtime의 SMI 마스크 의도만으로 Windows 단계에서 마스크가 효과를 내거나 모든 CPU·이미 진행 중인 SMM을 배제한다고 할 수 없습니다.

조건부 EC 해석에서는 선택한 두 후크의 **전체 handler body가 같은 상태 플래그 한 비트를 각각 지우거나 설정하고 반환**합니다. 보호 모드 저장 위치와는 다르고, 이 두 body는 mailbox 입력·응답을 읽거나 쓰지 않으며 추가 호출도 없습니다. 따라서 이 구체적인 Runtime 게시자를 범용 주소 쓰기나 직접 응답 덮어쓰기 명령으로 가정하던 위험 모델은 좁힙니다. 플래그 전체 의미·모든 후속 효과까지 확정한 것은 아닙니다.

반면 host sender는 준비 대기 뒤 명령만 게시하며 처리 완료를 기다리지 않습니다. Runtime의 local flag도 EC 완료를 확인하기 전에 바뀝니다. 새 조회가 후크 명령이나 정상 상태 전이를 대신해 버릴 가능성은 별도로 해결해야 합니다. 여러 CPU가 실제 겹친다면 indexed 주소 선택·데이터 접근의 무결성도 필요합니다. 응답이 타당해 보이거나 후크가 payload를 소비하지 않는다는 사실은 다른 작업의 보존을 보장하지 않습니다. 실제 겹침을 관측한 것은 아닙니다.

## 고정 조회 검토 단계로의 판정

관측 모델·BIOS, 제조사 CAP 계보, EC 업데이트 영역·주소 관계와 여러 독립 해석 anchor를 묶어 **임시 CandidateProfile**을 만들 수 있습니다. 현재 EC 본문 전체 해시가 없다는 사실만으로 비실행 제안 검토까지 막을 필요는 없습니다. 다만 이 프로파일을 현재 이미지 동일성·제품 지원 확정으로 표시하지 않습니다.

[검토안](FIXED_MODE_READ_PROPOSAL.md)은 저장 모드 한 바이트 1회, 임의 입력 없음, 다른 정상 작업 보존, 응답 귀속·실제 완료까지 소유권 유지, 모호한 결과 거부를 조건으로 합니다. 실제 호출 준비가 미완료인 이유는 최종 host 경로·통신의 정상 실행 영역·관련 indexed 접근·작업 보존의 미연결입니다. 전체 플랫폼 writer의 부재나 현재 EC 전체 해시 하나를 절대 조건으로 요구하는 것은 아닙니다.

다음 구현 판단은 이 **남은 경로·소유권 조건을 닫을 근거**에 달려 있습니다. 우선 저장 원본의 통신 제공자와 GUID별 dispatch 연결, 실제 부팅 알림 순서를 검토합니다. 이미 확인한 adapter·GUID 개수·동일 byte/decode를 다시 성과로 세지 않습니다. 조건을 닫지 못하면 backend를 연결하지 않고 해당 미해결을 유지합니다. 현재 제안은 새 호출·실기 승인을 요청하거나 기존 단발 승인을 재사용하는 단계가 아닙니다.

## 검증과 변경 범위

원본 해시·선택 바이트·같은 바이트의 decode·GUID와 실제 receiver를 검산하고 독립 검토했습니다. [정제한 검사 기록](reports/runtime-proxy-fixed-read-audit.json)은 새 검사와 기존 문맥을 분리합니다. 주요 재검산은 구성 322개 선택 명령, 수명 31개 byte block/동일 block의 134개 decode, 잠금 관계 52개 검사, EC 효과 8개 새 단언입니다. 별도 하위 검사는 중복될 수 있고 이 수치는 앱 테스트·새 기능 수·전체 분석률이 아닙니다.

이번 변경은 문서·정제 기록뿐입니다. C#/WPF·Python 개발 도구·EXE·기존 ZIP은 변경하지 않았으며 빌드·단위 테스트는 다시 실행하지 않았습니다. C#437개·빌드 경고/오류0은 이전 `5d77df5`, Python88개는 이전 `e7b067a` 기록입니다. 삼성 원본·사용자 TXT·전체 경로·장치 식별자·실행용 주소/명령/프레임은 배포하지 않습니다. 하드웨어/OEM·기존 단발 예약 접근, 드라이버·서비스·보안·펌웨어 변경은 없습니다.

분석 중 PE 파일 경로를 셸 명령으로 잘못 전달한 실행 시도가 1건 있었습니다. OS가 `Permission denied`로 차단했으며 원본 코드는 실행되지 않았습니다. 권한 변경·재시도는 없었고 이후에는 trusted parser로 바이트만 읽었습니다. 숫자 종료 코드는 당시 출력에 보존되지 않아 추정하지 않았습니다. 이 사건을 “실행 시도 없음”으로 기록하지 않습니다.
