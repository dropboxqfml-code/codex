# 제공받은 Sabi3 x64 DLL 정적 분석 — 2026-11-01

후속 사용자 TXT에서 현재 SABI 연결 이름 NotFound를 확인했습니다. [이번 관측과 별도 WMI 전송 구조](SABI_LINK_RESULT_AND_WMI_REVIEW.md)를 함께 읽으세요. 같은 TXT나 DLL을 다시 요청하지 않습니다. 아래 초기화·메모리 접근은 제공받은 x64 해시의 정적 사실이며 실제 DLL 실행 결과가 아닙니다.

## 대상과 방법

사용자가 제공한 ZIP에서 Sabi3.dll 하나를 읽어 **28,976바이트 / PE32+ AMD64 / SHA-256 09a9714f0e11734872d60f2966edf8590ca721f0c05b2ca852a0bf20d6c006ae**를 확인했습니다. 이전 TXT의 x64 파일과 일치합니다. x86은 분석에 사용하지 않았습니다.

DLL을 로드·실행하지 않고 PE 헤더·import/export·문자열·objdump 명령어 목록을 대조했습니다. 초기화와 통신 경로를 별도로 검토하고 중요 결과를 교차 확인했습니다. 원본 DLL·ZIP·디스어셈블리는 저장소 밖에 보관하며 소스·배포에 포함하지 않습니다. 아래 RVA는 이 해시의 ImageBase 0x180000000을 기준으로 합니다.

## 확인한 핵심 차이: 호출자 버퍼는 11바이트

공개 C# 예제의 4바이트 배열은 이 DLL의 실제 메모리 접근과 맞지 않습니다. 내부 helper RVA 0x30B0은 호출자 버퍼의 +0에서 8바이트, +8에서 2바이트, +10에서 1바이트를 읽고 성공 시 같은 11바이트를 씁니다(0x313D–0x315C, 0x31E7–0x31FE).

따라서 4바이트 배열로 직접 호출하면 네이티브 범위 밖 접근이 생길 수 있습니다. 현재 앱은 이 DLL을 호출하지 않았고 이전 4바이트 코드는 가상 입력을 해석하는 순수 함수였습니다. 이번에는 **분석된 x64 DLL 규약에 맞게 길이 검사를 11바이트로 수정하고 4바이트 입력을 거부**했습니다. 다른 버전의 Sabi3까지 같은 규약이라고 가정하지 않습니다.

## 초기화·종료

- `InitBIOSInterface` RVA 0x1140은 기존 장치 경로 `\\.\SABI\SabiDrv.log`를 GENERIC_READ|GENERIC_WRITE, 공유 없음, OPEN_EXISTING으로 엽니다. `.log`라는 끝 이름을 일반 디스크 로그 생성으로 해석하지 않습니다.
- 초기화 helper는 IOCTL 0x9C412000으로 입력 없이 64 KiB 정보를 요청하고 `DiaG@`, `SwSmi@` 앵커를 찾습니다. 두 앵커가 있어야 초기화 성공으로 처리합니다. 실제 배터리 기능이나 80% 상한을 확인하는 절차는 아닙니다.
- 관측한 DLL 초기화 경로에 서비스 생성·시작이나 일반 SABI 호출 0x9C412004는 없었습니다. 드라이버 내부 동작은 제공받지 않았으므로 모든 부작용의 부재를 보장하지 않습니다.
- 실패한 초기화 뒤에도 장치 핸들이 남을 수 있습니다. 향후 caller는 실패 때도 정리해야 합니다. `UninitBIOSInterface` RVA 0x1820은 초기화 상태를 지우고 장치 핸들을 닫습니다.
- DLL 로드 경로는 CRT 초기화, 자체 프로세스/모듈 정보 및 디버그 출력을 처리합니다. 관측한 로드 경로에서 SABI 장치 열기는 없었습니다.
- manifest는 Microsoft.VC90.CRT 9.0.21022.8 amd64 의존성을 선언합니다. 실제 Windows의 SxS 정책과 런타임 해결 가능성은 별도 확인 사항입니다.

## 함수·버퍼 연결

`CallBIOSInterface` RVA 0x1800은 명령의 하위 16비트를 취해 `CallBIOSInterfaceEx(0x5843, subfunction, pointer)`로 연결합니다. Ex RVA 0x1450은 메인·서브 기능을 16비트로 받고 버퍼 포인터의 길이를 검사하지 않습니다.

| 구분 | DLL에서 관측한 구조 |
| --- | --- |
| 내부 드라이버 입력 | 26바이트: 초기화 앵커 10 + main UInt16(+10) + sub UInt16(+12) + 0(+14) + payload 11(+15) |
| 내부 드라이버 응답 | 16바이트: 앞 4바이트 + ACK 0xAA(+4) + payload 11(+5) |
| 일반 함수 통신 | 0x9C412004, METHOD_BUFFERED, FILE_ANY_ACCESS |

이는 정적으로 관측한 전송 구조이며 IOCTL을 실행하는 코드는 추가하지 않았습니다. 접근 비트만으로 읽기 전용 펌웨어 명령이라고 판단하지 않습니다. 0x65/0x66 명령이나 보호 ON/OFF가 이 BIOS에서 뜻하는 상한도 아직 검증되지 않았습니다.

## 발견한 처리상의 주의점

- `CheckSamsung`도 필요하면 초기화를 호출하며 앵커 존재만 검사합니다. 독립적인 배터리 지원 검사로 사용할 수 없습니다.
- 내부 함수는 DeviceIoControl 성공 여부와 ACK만 검사하고 BytesReturned 길이를 확인하지 않습니다. 새 순수 응답 검사기는 정확한 16바이트 반환과 ACK를 함께 요구해 짧은 응답을 거부합니다.
- `GetBiosDataFromSabi`/`GetBiosDataThroughDrvr`는 내부 오류 뒤에도 반환값을 0으로 덮는 경로가 있습니다. 0만으로 성공을 표시하지 않습니다.
- CallEx에는 이름 SABI의 mutex 무한 대기가 있고, 내부 통신 오류 시 해제 경로를 건너뜁니다. 향후 실제 호출은 GUI 스레드에서 수행하지 않고 별도 프로세스의 시간 제한·실패 후 정리를 검토해야 합니다.
- ReadIo/WriteIo 계열과 포트 I/O용 0x9C412008은 배터리 어댑터 호출 대상으로 사용하지 않습니다.

## 이번 구현과 다음 확인

11바이트 응답 해석과 새 버퍼 생성, 정확한 드라이버 응답 길이/ACK 검사를 순수 코드로 구현했습니다. 이 코드는 DLL·장치·IOCTL을 호출하지 않습니다. 미지원·OFF·ON·기타·API 오류는 계속 구분하고 실제 관측·80% 상한으로 승격하지 않습니다.

새 파일 정보 결과에는 **SABI 장치 연결 이름**을 추가했습니다. Windows `QueryDosDeviceW("SABI")`로 이름 테이블만 조회하며 매핑 문자열은 내보내지 않습니다. 장치 열기, DLL 로드, IOCTL, 서비스 변경은 하지 않습니다. 이름이 있어도 장치 접근·드라이버 버전·배터리 지원은 별도 미검증이고, 없더라도 펌웨어 기능 전체의 부재로 판단하지 않습니다.

새 앱의 **삼성 파일 정보 만들기**로 생성한 TXT에서 이 새 항목을 확인할 수 있습니다. 이번에 필요한 것은 추가 DLL이나 x86 파일이 아니라 현재 SABI 연결 이름의 관측 결과입니다. 실제 DLL 호출과 충전 제한은 계속 미지원입니다.
