# SABI 연결 이름 결과와 기존 WMI 중계 규약 검토 — 2026-11-01

## 이번 사용자 결과

사용자가 전달한 `samsung-files-20261101T132149`에서 **현재 이름 조회에서 SABI 연결을 찾지 못함**을 확인했습니다. QueryDosDevice의 오류 2/3에 해당하는 관측이며 권한 거부나 시간 초과로 보고된 결과는 아닙니다. 이 앱의 조회 시점과 이름공간에서 찾지 못한 것이므로 드라이버 미설치, 영구적인 장치 부재, 펌웨어의 배터리 기능 부재를 확정하지 않습니다.

관측된 파일 항목 9개(중복 해시 제외 8개)의 해시·버전은 직전 `samsung-files-20261101T112523`과 같습니다. x64 Sabi3.dll은 이미 제공받아 정적으로 분석한 28,976바이트 파일과 같습니다. 이 DLL의 초기화 대상은 `\\.\SABI\SabiDrv.log`이고 자체 드라이버 설치·시작 경로는 관측하지 못했습니다. 따라서 DLL 파일 존재만으로 초기화를 진행하거나 지원 가능으로 판정하지 않습니다. 원본 TXT와 삼성 바이너리는 저장소·배포물에 포함하지 않습니다.

이번 결과로 SABI 이름 조회 기능이 실제 Windows에서 실행되어 NotFound를 보고한 경로를 확인했습니다. 다른 조회 결과, GUI 전체, DLL 초기화 또는 충전 제한을 시험한 것은 아닙니다.

## 기존 자료에서 확인한 다른 전송 경로

이전에 사용자가 제공한 **서비스 폴더**의 wsabi.dll을 추가 정적 분석했습니다. 대상은 x86, 22,920바이트, SHA-256 `564b640d62db2a4e4b56c6331e0e526bad2ac1fcf438a41a9e5241551f457b6e`입니다. 이 파일은 새 Settings TXT에 나온 wsabi 변형들과 해시가 다릅니다. 아래 사실을 현재 Settings 폴더의 모든 wsabi에 적용하지 않습니다.

이 파일은 SABI 장치를 직접 여는 대신 `ROOT\WMI`의 `WmiAcpiMethod.CallSabiFunction`을 사용합니다. 이전 노트북 진단에서 `WmiAcpiVersion`, `WmiAcpiMethod`, `DataBuffer` 정의가 실제 존재함을 이미 확인했습니다. 이번 분석은 그 정의와 전달 바이트의 구조를 연결한 것이며 실제 메서드 실행이나 배터리 기능 지원 확인은 아닙니다.

| 구분 | 제공받은 Sabi3 x64 | 기존 서비스 wsabi x86 |
| --- | --- | --- |
| 전송 | SABI 장치 핸들·IOCTL | WMI의 embedded DataBuffer.Bytes |
| 호출자 payload | 11바이트 | 16바이트 |
| 전송 입력 | 내부 장치 요청 26바이트 | WMI 입력 21바이트 |
| 응답 접근 | 16바이트 | 최소 21바이트 접근; 제공자의 정확한 길이는 미확정 |
| ACK·payload | ACK +4, payload +5부터 11바이트 | ACK +4, payload +5부터 16바이트 |
| 초기화 | 기존 SABI 장치 열기·정보 요청 | COM 초기화·WMI 연결·프록시 설정 |

기존 wsabi의 WMI 입력은 `UInt16LE(0x5843) + UInt16LE(명령 하위 16비트) + 0 한 바이트 + payload 16바이트`입니다. 명령은 호출자가 제공하며 DLL에 배터리 조회·설정 번호가 고정돼 있지 않습니다. 이 구조만으로 0x65의 현재 모델 지원이나 읽기 전용 안전성을 확정하지 않습니다.

## 정적 근거와 처리 한계

아래 RVA는 위 wsabi 해시의 ImageBase `0x10000000` 기준입니다. 원본 기계어·디스어셈블리는 저장소 밖에 보관합니다.

- `InitBIOSInterface` export 0x1010 → helper 0x1270: COM/WMI 연결을 준비하며 관측한 경로에 SABI 장치 열기·IOCTL·서비스 생성/시작은 없습니다. WMI 제공자 내부의 동작까지 분석한 것은 아닙니다.
- `CallBIOSInterface` export 0x1020 → helper 0x1840: 이 x86 export는 cdecl이며 호출자 버퍼의 4개 DWORD, 총 16바이트를 사용합니다(읽기 0x1B35–0x1B89, 복사 0x1DA9–0x1DBD).
- 0x1BA8–0x1BF6: UInt8 SAFEARRAY의 요소 수를 0x15로 지정하고 21바이트 입력을 복사합니다.
- 0x1D03: 선택한 WMI 인스턴스에 `CallSabiFunction`을 실행합니다. 초기화 성공과 메서드 실행 성공은 별개입니다.
- 응답에서 +4의 0xAA와 +5부터 16바이트를 읽지만 SAFEARRAY의 형식·차원·경계·길이를 확인하지 않습니다. 이 누락을 새 구현에서 그대로 따르지 않습니다.
- 오류는 HRESULT 계열입니다. S_FALSE처럼 음수가 아닌 결과라도 인스턴스가 없어 payload를 받지 못할 수 있습니다. 무한 mutex 대기도 있어 실제 호출을 UI 스레드에 연결하지 않습니다.

## 이번 코드 반영

`Sabi3PreparationAssessment`는 정적으로 분석한 정확한 native x64 해시에 한정해 SABI 연결 이름 상태를 설명합니다. 연결 이름이 없으면 DLL·함수 이름의 존재가 이 선행 조건을 덮지 않습니다. 이름이 있더라도 접근·초기화 성공으로 승격하지 않습니다.

`WsabiWmiReplyValidator`는 기존 서비스 wsabi 규약을 위한 순수 바이트 검사입니다. 성공 코드 0, 1차원·0 기반 UInt8 배열, 0xAA ACK, 지원 길이를 확인하고 16바이트를 새 배열에 복사합니다. **정확히 21바이트만 받는 것은 현재 구현의 보수적인 지원 범위이며 실제 제공자 출력이 반드시 21바이트라는 분석 결론이 아닙니다.** 다른 길이는 추측해 해석하지 않습니다. Sabi3 x64의 11바이트/16바이트 규약과 구분합니다.

두 변경 모두 장치·WMI 메서드·삼성 DLL을 실행하지 않으며 실제 읽기·쓰기 기능을 활성화하지 않습니다.

## 다음 개발 방향

기존 SABI 장치 경로를 되살리려고 드라이버를 설치하거나 서비스를 시작하지 않습니다. 이미 확보한 WMI 스키마와 이번 전송 구조를 바탕으로 다음 실제 조회의 조건을 좁힙니다. 필요한 확인은 WMI 인스턴스·버전·활성 상태와 응답 계약, 모델별 조회 명령의 의미입니다. 동일 스키마·배터리 잔량·삼성 파일 목록을 다시 수집할 단계는 아닙니다.

실제 보호 상태 조회는 입력·응답과 모델 적합성 근거가 갖춰진 뒤 연결합니다. 실제 충전 제한은 계속 미지원입니다. 이번 변경은 분석·소스 준비이며 새 실행용 ZIP이나 사용자의 추가 실행을 요구하지 않습니다.
