# 보호 설정 저장값 전환 결과와 Windows 배터리 관찰

2026-11-09 한국 시간 수신. 기준 소스는 `039492e`입니다. 사용자가 전달한 `Protection0To1-v1` 결과를 분석하고, 설정을 다시 보내지 않는 일반 권한 GUI를 준비했습니다.

## 이번 시험에서 확인된 결과

**의도한 저장값 후보 전환이 보고됐습니다.** 도구의 사전·사후 판정은 다음과 같습니다.

| 항목 | 사전 후보 | 사후 후보 |
| --- | ---: | ---: |
| 보호 모드 | 0 | 1 |
| 상한 | 0 | 80 |
| 하한 | 0 | 75 |

전체 결과와 전이 판정은 `StoredReadbackMatchedCandidate`입니다. 여섯 읽기 단계가 모두 `CorrelatedStoredByteCandidate`로 수용됐고, 설정 응답은 `ReceiptOnly`로 수용됐습니다. 실제 종료 뒤 SDK 진입은 총 7회, 설정 SDK 진입은 1회이며 관련 정리는 `Complete`입니다. 승인된 한 번의 설정 시험이 종료됐습니다.

이 결과는 보호 설정을 저장하는 경로에 접근했다는 유의미한 진전입니다. 설정 응답 하나만 성공으로 간주한 결과가 아니라, 별도 사후 읽기에서 예상한 세 후보가 일치한 기록입니다. 다만 제출된 TXT에는 원래 응답 프레임이 없으므로 이번 분석은 도구의 보고 내용을 평가하며, 원시 응답을 독립 재검증하거나 텍스트의 진위를 인증하지 않습니다.

결과의 `고정7단계 요청 준비: None`은 준비 오류가 없다는 값입니다. `설정 효과: Unknown` 문장은 기존 도구가 설정 역할에 입장했을 때 출력하는 고정 주의 문구입니다. 이 문장은 별도 사후 읽기의 `1 / 80 / 75` 후보 일치를 취소하는 실패 판정이 아닙니다. 원래 시험 도구와 ZIP은 당시 내용으로 보존했습니다.

## 아직 구분해야 하는 범위

보고된 저장 후보는 실행 당시의 기록입니다. 지금의 보호 모드, 재부팅·절전 뒤 지속성, 충전기 내부 설정, 실제 전류와 전기적 충전 제한은 이번 TXT로 확인되지 않았습니다. 상한 80·하한 75의 후보를 현재 배터리 잔량이나 실제 충전 중단·재개 지점으로 바꿔 표시하지 않습니다.

일반 앱의 `desiredMode`와 `actualMode`, Windows 배터리 잔량은 계속 별개입니다. 실제 보호 상태의 상시 조회·충전 제어는 `Unsupported`로 유지합니다. 과거 기록 검토나 배터리 관찰로 제어 버튼을 활성화하지 않습니다.

**Protection0To1-v1 시험과 과거 Query65·A·Access1 시험은 종료·소모됐습니다.** 같은 도구를 다시 실행하거나 예약을 조회·삭제·변경·재사용하지 않습니다. 이번 후속 개발에는 추가 OEM 조회, 재설정, 끄기, 역방향 전환, 복원, 초기화 또는 handshake를 추가하지 않았습니다. 향후 새로운 펌웨어 동작은 별도 구체 범위와 명시 승인 대상입니다.

## 새 일반 권한 GUI

[ATIVBatteryGuard-BATTERY-OBSERVATION.zip](../downloads/ATIVBatteryGuard-BATTERY-OBSERVATION.zip) 하나를 새 폴더에 모두 풀고 **`ATIVBatteryGuard.exe`를 일반 권한으로 실행**합니다. 다른 ZIP이나 삼성 DLL을 합칠 필요가 없습니다. Windows 10 x64·.NET Framework 4.8 대상의 미서명 개발 빌드입니다. 이번 새 GUI의 실제 Windows 실행 검증은 아직 하지 않았습니다.

‘보호 설정 전환 기록 · 과거 결과 검토’에는 이미 보관한 `protection-0to1` TXT를 선택적으로 붙여넣을 수 있습니다. 필수 상태, 두 단계별 응답 판정 블록, 호출 수, 사전·사후 후보와 `Complete`가 모두 맞아야 일치 기록을 표시합니다. 누락·중복·순서 변경·모순·오류·Pending은 성공 기록으로 표시하지 않습니다. 붙여넣은 원문은 검토 뒤 비우며 자동 저장하지 않습니다. 앱을 처음 실행할 때 특정 사용자의 결과나 `1 / 80 / 75` 관측을 미리 넣지 않습니다.

‘Windows 배터리 상태 관찰’은 다음 순서로 사용합니다.

1. **새 관찰 시작**을 누릅니다. 첫 샘플은 다음 기존 배터리 갱신 때 기록합니다.
2. 평소처럼 사용하면서 잔량·외부 전원·Windows 충전 상태 표시를 관찰합니다.
3. **관찰 중단** 뒤 **관찰 TXT 저장**을 누릅니다. 저장은 명시적으로 누를 때만 수행합니다.
4. **정보 파일 위치 열기**에서 `%LOCALAPPDATA%\ATIVBatteryGuard`의 새 `battery-observation-*.txt`를 찾을 수 있습니다.

새 관찰을 시작하거나 관찰을 지우면 기존 메모리 기록이 비워집니다. 보관할 기록은 먼저 저장합니다. 저장하지 않고 앱을 닫은 기록은 복원하지 않습니다.

관찰은 기존 약 10초 주기의 `GetSystemPowerStatus` 조회 결과를 재사용합니다. 시작 버튼은 추가 배터리 조회를 하지 않으며 새 WMI·OEM·펌웨어 호출, 관리자 권한 또는 별도 타이머를 추가하지 않습니다. 시뮬레이션에서는 시작할 수 없고, 관찰 중 시뮬레이션을 켜면 기록을 중단합니다.

기록은 메모리에 최대 2시간·721개로 제한하고, 10초보다 짧은 간격의 중복 샘플을 추가하지 않습니다. 30초를 넘는 갱신 간격은 결측 구간으로 표시하며, 알 수 없는 상태·배터리 없음·읽기 오류 여부를 구분합니다. 경과초는 시작 이후의 상대 시간이고 샘플 사이를 보간하거나 연속 관측 시간으로 합산하지 않습니다. 전체 경로·계정·시리얼·고유 식별자·예외 원문은 관찰 기록에 넣지 않습니다.

**80% 유지나 `NotCharging` 표시가 반복돼도 충전 제한 성공을 자동 판정하지 않습니다.** 이 기록은 Windows 상태의 경과를 검토하기 위한 것이며 전류·충전기 레지스터 측정이 아닙니다. 시험을 위해 방전·재충전·재부팅을 반복할 필요가 없습니다.

## 검증과 다음 개발

새 파서 12개·관찰 모델 10개·화면 및 저장 오류 처리 11개를 포함해 **887개 통과, 실패·건너뜀 0개**입니다. Portable 및 전체 net48 참조 Release 빌드가 각각 경고·오류 0개이며 WPF/XAML도 컴파일했습니다. 첨부된 실제 TXT를 오프라인 파서에 넣어 보고된 전후 후보와 호출 수를 다시 확인했습니다. 새 GUI를 Windows에서 실행한 검증과는 구분합니다.

새 ZIP은 190478바이트, SHA-256 `dd7acffacb099fb5b08639c24909b2a45b8ef2d8981e610cead003611004dc97`입니다. 독립 검토에서 6개 항목·CRC·내부 체크섬 5개·실제 빌드 바이트·소스 151개 대조를 통과했고, 기존 ZIP 66개와 시험 코드·하드웨어 차단 코드를 보존했습니다.

최신 빌드·테스트·패키지 검증 결과와 해시는 [정제 검증 기록](reports/stored-transition-observation-validation.json)에 보관합니다. 기존 854개 통과 기록은 이전 시험 도구의 검증이며, 새 기능의 검증과 구분합니다. 배포 ZIP에는 일반 GUI 실행 파일·Core·설정과 안내·빌드 정보·체크섬만 포함하며 삼성 원본 DLL, WmiInterop, 실험 실행 파일, 펌웨어 또는 사용자 원문은 포함하지 않습니다.

다음 단계는 재설정 없이 실제 사용 중 Windows 배터리 상태의 경과를 살펴보는 것입니다. 이후 충전 효과를 평가할 때도 저장 후보·Windows 상태·충전기의 실제 동작을 구분합니다. 이 관찰만으로 미확인 상태를 성공으로 바꾸거나 상시 제어를 활성화하지 않습니다. 기존 TXT·진단·삼성 DLL·EXE의 재제출은 필요 없습니다. 추후 관찰 결과를 함께 검토할 때는 새 관찰 TXT만 사용하면 됩니다.
