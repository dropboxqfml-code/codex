# 검증 계획과 결과 구분

## 공식 지원 검토판의 현재 상태

새 제품 시작 구성은 OEM 파일 수집기와 확인 콜백을 전달하지 않습니다. 수집 명령은 비활성화되고 직접 비동기 호출도 작업 없이 반환합니다. 기존 수집 코드는 소스 이력과 회귀 검증을 위해 보관하며 현재 제품 경로에서 사용하지 않습니다.

문의문 복사는 장치 정보 조회 완료 후에만 사용할 수 있고, 조회 갱신 중의 오래된 값과 종료 후 복사를 차단합니다. 공개 장치 정보 필드만 사용하며 상세 오류와 경로를 문의문에서 제외합니다. 클립보드에 복사할 뿐 실제 문의 제출·네트워크 통신은 수행하지 않습니다.

이 변경을 포함한 전체 portable suite는 **114개 통과·실패 0개·건너뜀 0개**, 실제 WPF 빌드는 경고·오류 0개입니다. Windows에서 새 문의 복사 동작은 아직 미검증입니다. 아래 표와 수집 절차는 이전 단계의 기록입니다.


## 지금까지 확인한 상태

2026-10-31(한국 시간) 기준입니다. 이전 WMI 정의 진단판의 검증과 새 Settings 앱 파일 수집의 검증을 구분합니다.

| 검증 | 결과 | 범위 |
| --- | --- | --- |
| 이전 WMI 판 .NET Framework 4.8 x64 WPF/XAML 빌드 | 성공 | Linux에서 실제 WPF 소스와 XAML 컴파일 |
| 이전 WMI 판 .NET 8 portable suite | 78개 통과 / 실패 0개 / 건너뜀 0개 | 실제 Core·ViewModel과 WMI 정책 회귀 테스트 |
| 이전 WMI 판 노트북 창·배터리 표시 | 사용자 확인 | 62%, AC 연결 안 됨, 방전 중 |
| 이전 WMI 판 실제 클래스 정의 조회 | 사용자 TXT에서 확인 | 정확한 클래스 3개 및 메서드·입출력 정의, 보고서 오류 없음 |
| 새 Settings 앱 수집 WPF 빌드 | 성공, 경고 0개·오류 0개 | .NET Framework 4.8 x64 실제 소스·XAML 컴파일 |

| Windows 검증 스크립트 | 미실행 | Windows WPF 빌드·portable suite·90초 GUI self-test |

기존 배포본에 기록된 `149개 테스트 통과`는 과거 빌드의 기록입니다. 원본 테스트 소스는 복구되지 않았으므로 그 결과를 복원된 코드의 새 검증 결과로 사용하지 않습니다. 새 suite의 108개 결과는 기존 검사와 새 경계 검사를 이번 변경에서 다시 실행한 결과입니다.

## 자동화된 핵심 회귀 검사

- 설정 저장·재로드에서 사용자 희망 모드가 유지되는지 확인
- 손상된 JSON·유효하지 않은 값에서 안전하게 복구하고 실제 제어 지원을 활성화하지 않는지 확인
- Unsupported 어댑터가 80%·100% 및 잘못된 모드의 쓰기 요청을 모두 거부하는지 확인
- Mock 모드가 메모리 상태만 변경하고 실제 하드웨어 상태와 구분되는지 확인
- Windows 배터리 값 0%, 80%, 100%, 미제공·오류 상태가 정확히 변환되는지 확인
- 저장된 사용자 선택과 실제 장치 상태가 서로 대체되지 않는지 확인
- 삼성 WMI 진단이 정확한 허용 클래스 정의만 읽고 메서드를 실행하지 않는지 확인
- WMI 클래스 부재·접근 거부·조회 오류·중간 실패가 각각 진단 결과가 되며 실제 제어로 이어지지 않는지 확인
- 삼성 WMI 메타데이터 진단 출력에 인스턴스 값·불필요한 식별정보가 포함되지 않는지 확인
- Settings 등록 이름·게시자 확인과 허용된 전용 설치 폴더 범위를 검증
- UNC·사용자·시스템·큰 공용 폴더, 장치·ADS·상위 경로 탈출과 잘못된 DisplayIcon 입력 거부 확인
- Settings 경로 정책의 EXE·DLL 확장자, 전용 폴더 포함 관계와 안전한 거부 결과를 검증
- native 수집의 리파스 경로 거부와 깊이·개수·용량·중복 처리 한도는 코드 검토와 실제 Windows ZIP 결과로 별도 확인
- 분석 생성 취소 시 추가 설치 위치 탐색·복사 서비스가 호출되지 않는지 확인
- 유효한 InstallLocation을 찾은 경우 하위 폴더의 DisplayIcon 때문에 수집 기준 폴더가 좁아지지 않는지 확인
- 등록 미일치·제공된 경로 거부 시 대체 조회를 차단하고, 경로 정보가 모두 누락된 등록 앱에만 전용 후보 최대 6곳을 허용하는 정책 확인

Linux의 portable 테스트는 하드웨어 없이 핵심 로직을 검증하는 용도입니다. WPF 표시·Windows WMI 접근·실제 배터리 API 실행 결과를 대신하지 않습니다.

## 재실행 명령

프로젝트 루트에서 .NET 8 SDK로 실행합니다. `--report`는 테스트 수와 결과를 JSON으로 기록합니다.

```powershell
dotnet run --project tests/ATIVBatteryGuard.PortableTests.csproj -c Release -- --report reports/portable-tests.json
```

Windows 개발 환경에서는 다음 스크립트가 WPF 빌드, portable suite, GUI self-test를 순서대로 실행합니다. portable 결과의 통과 수가 0보다 크고 실패가 없는지 검사하고, GUI self-test는 90초를 넘기면 실패 처리합니다. 이 스크립트는 아직 Windows에서 실행하지 않았습니다.

```powershell
powershell -File scripts/Test-Windows.ps1
```

GUI self-test는 실제 충전 제한 성공 검증이 아닙니다.

## Windows 10 수동 확인

새 빌드가 전달된 뒤 일반 사용자 권한으로 실행합니다.

사용자가 이번에 전달할 결과는 **Settings 분석 파일 만들기 → 포함 내용 확인 → 파일 위치 열기**로 생성한 최신 `samsung-analysis-*.zip`입니다. 파일을 확보하지 못한 보고서 전용 ZIP도 조사 대상입니다. 기본 TXT 진단은 이미 전달된 결과에서 클래스 정의 조회가 확인됐습니다.

1. 창이 열리고 한국어 표시·스크롤·키보드 조작·고DPI 화면이 동작하는지 확인합니다.
2. 배터리 수치와 AC 상태를 Windows 표시와 비교합니다. 최근 확인된 62%·AC 연결 안 됨·방전 중을 고정값으로 쓰지 않고 실행 시 현재 측정값을 표시해야 합니다. 0%도 유효한 값으로 유지합니다.
3. 실제 하드웨어 상태가 미지원으로 표시되고 실제 적용 동작이 차단되는지 확인합니다.
4. 사용자 희망 모드를 저장하고 종료·재실행하여 선택값만 복원되는지 확인합니다.
5. Mock 모드가 눈에 띄게 시뮬레이션으로 표시되는지 확인합니다.
6. 읽기 전용 진단을 생성하고 로컬 파일 위치가 열리는지 확인합니다.
7. 삼성 WMI 항목에 클래스별 조회 결과가 기록되는지 확인합니다. 클래스 존재를 충전 제한 성공으로 해석하지 않습니다.
8. Settings 분석 확인 창에서 아니요를 선택해 취소되는지 확인합니다. 예를 선택하면 결과 ZIP과 파일별 정보 또는 복사 실패 이유가 생성되는지 확인합니다.
9. ZIP에 설정·로그·개인 문서가 별도로 포함되지 않았는지 확인하고, 파일 위치를 확인하지 못해도 원인을 기록한 보고서가 제공되는지 확인합니다.
10. 앱 실행만으로 서비스·자동 실행·작업 스케줄러·드라이버가 설치되거나 설정되지 않는지 확인합니다.

## 실제 충전 제한 검증

현재는 제어를 구현하지 않았으므로 실행할 성공 검증 절차가 없습니다. 잔량이 80%이거나 충전 중 아님으로 바뀐 사실은 검증 통과가 아닙니다. 모델별로 검증된 상태 read-back과 제어 경로를 확보한 장래 단계에서 별도로 설계합니다.
