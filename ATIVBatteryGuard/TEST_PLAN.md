# 검증 계획과 결과 구분

## 복구 후 검증 상태

2026-10-31(한국 시간), 복원·재구성한 실제 소스를 기준으로 다음을 확인했습니다.

| 검증 | 결과 | 범위 |
| --- | --- | --- |
| .NET Framework 4.8 x64 WPF/XAML 빌드 | 성공 | Linux에서 실제 WPF 소스와 XAML 컴파일 |
| .NET 8 portable suite | 78개 통과 / 실패 0개 / 건너뜀 0개 | 실제 Core·ViewModel 코드를 공유하는 회귀 테스트 |
| Windows 검증 스크립트 | 미실행 | Windows WPF 빌드·portable suite·90초 GUI self-test |
| 새 빌드의 Windows GUI 실행 | 미검증 | 실제 노트북에서 창과 사용자 조작 확인 필요 |
| 새 진단의 실제 WMI 접근 | 미검증 | 노트북의 클래스 존재·권한·메타데이터 결과 확인 필요 |

기존 배포본에 기록된 `149개 테스트 통과`는 과거 빌드의 기록입니다. 원본 테스트 소스는 복구되지 않았으므로 그 결과를 복원된 코드의 새 검증 결과로 사용하지 않습니다.

## 자동화된 핵심 회귀 검사

- 설정 저장·재로드에서 사용자 희망 모드가 유지되는지 확인
- 손상된 JSON·유효하지 않은 값에서 안전하게 복구하고 실제 제어 지원을 활성화하지 않는지 확인
- Unsupported 어댑터가 80%·100% 및 잘못된 모드의 쓰기 요청을 모두 거부하는지 확인
- Mock 모드가 메모리 상태만 변경하고 실제 하드웨어 상태와 구분되는지 확인
- Windows 배터리 값 0%, 80%, 100%, 미제공·오류 상태가 정확히 변환되는지 확인
- 저장된 사용자 선택과 실제 장치 상태가 서로 대체되지 않는지 확인
- 삼성 WMI 진단이 정확한 허용 클래스 정의만 읽고 메서드를 실행하지 않는지 확인
- WMI 클래스 부재·접근 거부·조회 오류·중간 실패가 각각 진단 결과가 되며 실제 제어로 이어지지 않는지 확인
- 새 삼성 WMI 메타데이터 진단 출력에 인스턴스 값·불필요한 식별정보가 포함되지 않는지 확인

Linux의 portable 테스트는 하드웨어 없이 핵심 로직을 검증하는 용도입니다. WPF 표시·Windows WMI 접근·실제 배터리 API 실행 결과를 대신하지 않습니다.

## 재실행 명령

프로젝트 루트에서 .NET 8 SDK로 실행합니다. `--report`는 테스트 수와 결과를 JSON으로 기록합니다.

```powershell
dotnet run --project tests/ATIVBatteryGuard.PortableTests.csproj -c Release -- --report reports/portable-tests.json
```

Windows 개발 환경에서는 다음 스크립트가 WPF 빌드, portable suite, GUI self-test를 순서대로 실행합니다. portable 결과의 통과 수가 0보다 크고 실패가 없는지 검사하고, GUI self-test는 90초를 넘기면 실패 처리합니다. 이 스크립트는 아직 Windows에서 실행하지 않았습니다.

```powershell
powershell -File scripts/Test-Windows.ps1
```

GUI self-test는 실제 충전 제한 성공 검증이 아닙니다.

## Windows 10 수동 확인

새 빌드가 전달된 뒤 일반 사용자 권한으로 실행합니다.

사용자가 이번에 전달할 결과는 **진단 파일 만들기 → 진단 파일 위치 열기**로 생성한 최신 `diagnostics-*.txt`입니다. 삼성 EXE·DLL 분석 ZIP은 다시 수집하지 않아도 됩니다.

1. 창이 열리고 한국어 표시·스크롤·키보드 조작·고DPI 화면이 동작하는지 확인합니다.
2. 배터리 수치와 AC 상태를 Windows 표시와 비교합니다. 현재 노트북의 0%는 기대 가능한 실제 상태입니다.
3. 실제 하드웨어 상태가 미지원으로 표시되고 실제 적용 동작이 차단되는지 확인합니다.
4. 사용자 희망 모드를 저장하고 종료·재실행하여 선택값만 복원되는지 확인합니다.
5. Mock 모드가 눈에 띄게 시뮬레이션으로 표시되는지 확인합니다.
6. 읽기 전용 진단을 생성하고 로컬 파일 위치가 열리는지 확인합니다.
7. 삼성 WMI 항목에 클래스별 조회 결과가 기록되는지 확인합니다. 클래스 존재를 충전 제한 성공으로 해석하지 않습니다.
8. 앱 실행만으로 서비스·자동 실행·작업 스케줄러·드라이버가 설치되거나 설정되지 않는지 확인합니다.

## 실제 충전 제한 검증

현재는 제어를 구현하지 않았으므로 실행할 성공 검증 절차가 없습니다. 잔량이 80%이거나 충전 중 아님으로 바뀐 사실은 검증 통과가 아닙니다. 모델별로 검증된 상태 read-back과 제어 경로를 확보한 장래 단계에서 별도로 설계합니다.
