# 1회 후보 응답 수신과 오프라인 검토 — 2026-11-04

## 실제 수신 결과

사용자가 전달한 Query65-locator-v2 결과는 다음과 같습니다. 원본 TXT는 저장소나 배포물에 넣지 않습니다.

| 항목 | 관측값 |
| --- | --- |
| 토큰 / 준비 | Elevated / Complete / Ready |
| 결과 / 요청 | ResponseReceived / 요청됨 |
| 메서드 응답 / 프레임 | FrameChecked / ValidFrame |
| 후보 표식 | FF |

이는 단순 요청 플래그보다 강한 근거입니다. 현재 구현에서 이 조합은 비동기 Completed.Status=0과 정확히 한 출력 객체, 고정 outData/Bytes 구조, 정확한21바이트 UInt8 배열과 ACK(+4)=0xAA를 통과해야 나옵니다. 따라서 **WMI 응답 수신과 프레임의 구조 검증은 성공**했습니다.

FF는 payload 첫 바이트(+5)가0xFF였다는 분류입니다. 전체 응답이FF였다는 뜻은 아니며 응답의 헤더/명령 echo는 현재 검증 항목이 아닙니다. 배터리 명령 지원, 보호 OFF/ON, 충전 상한이나 부작용 부재까지 입증하지 않습니다. 실제 충전 제어는 계속 Unsupported입니다.

## 공개 구현과의 대조

- [samsung-hotkeys 고정 소스](https://github.com/akastormseeker/samsung-hotkeys/blob/0d3947eea0003dd8e9372c36925c0fd0a8fd28d3/SamsungHotkeys/Controls/SamsungBIOSInterface.cs#L88)는 Sabi3.dll의 응답 첫 바이트FF에 미지원 디버그 문구를 남기고 false를 반환합니다. 다른 실패/OFF 후보도 같은 bool로 합치므로 재사용하지 않습니다. SHA-256은 기존 기록과 같은 `fa3e2ee228d3f4012bfa259c06437ee0de2f7187fcc64518a8dac6b60ad54c68`입니다.
- [Linux v6.12의 직접 SABI 경로](https://github.com/torvalds/linux/blob/v6.12/drivers/platform/x86/samsung-laptop.c#L425)는 ACK가AA여도 interface data 첫 바이트FF를 알 수 없는 명령으로 설명하며 오류를 반환합니다. [배터리 함수](https://github.com/torvalds/linux/blob/v6.12/drivers/platform/x86/samsung-laptop.c#L700)는 상위 실패를 먼저 전달하고0/1만 받아들입니다. SHA-256은 `42593bb4c71de22756a3d051ba79d8ad0ba3964e652872d627c2384e0d791063`입니다.

이 둘은 각각 삼성 DLL과 직접 포트/메모리 경로이며 현재 모델의 Windows WMI 계약은 아닙니다. 이번 FF를 OFF 또는 하드웨어 미지원으로 확정할 근거가 되지 않습니다. 기존11바이트 Sabi3 해석기의 FF 판정도 WMI16바이트 payload에 적용하지 않습니다. 명령 echo 규약을 추가 확보하지 못했으므로 decoder의 수락 규칙은 유지합니다. 공개 소스는 정적으로 읽었으며 실행하지 않았습니다.

## 승인된 요청 완료

이번 실제 요청으로 기존 [최대1회 승인](WMI_ONE_SHOT_QUERY_APPROVAL.md)은 사용됐습니다. 구현 흐름상 기존 v1 표식의 영속 예약을 확보한 뒤 요청했으며, 현재 파일의 존재 여부를 별도로 조회한 것은 아닙니다. **실험 재실행·예약 표식 삭제/초기화·다른 계정이나 경로 우회·추가 후보·0x66 설정 명령은 수행하지 않습니다.** 개발 계속 요청을 추가 하드웨어 실험 승인으로 넓히지 않습니다.

기존 실험 backend/정책/예약/디코더는 보존하며 완료 기록이 있는 동안 패키저가 새 OEM 실험 EXE 배포를 거부하도록 닫았습니다. 기존 다운로드는 과거 기록이며 재실행하지 않습니다. 다른 검증된 계약을 확보하기 전 실제 제어를 활성화하지 않습니다.

## 이번 프로그램 개발

새 일반 앱에 **과거 WMI 실험 결과 검토**를 추가했습니다. 원하는 경우 이미 받은 콘솔 출력을 붙여넣고 검토할 수 있습니다. 새 실험이나 자료 재제출은 필요하지 않습니다. 앱은 일반 권한으로 실행하며 실험 EXE나 삼성 DLL은 포함하지 않습니다.

- Core 파서는 고정 수정판·범위·필수 필드와 상태 조합을 검사합니다. 전체8192자·64행·행당512자 제한과 숫자 enum/누락/중복/알 수 없는 수정판/모순 상태 거부를 적용합니다. CRLF/LF와 시작 BOM은 허용합니다.
- 검토 객체는 고정 상태·표식·요청 여부만 보관합니다. 원문·경로·계정·예외는 결과에 보관하지 않으며 검토 뒤 입력창도 비웁니다. 검토 결과는 파일·설정·로그로 저장하지 않습니다.
- 입력 변경·검토 실패는 이전 성공을 제거합니다. 같은 빈 입력의 바인딩 반향은 판정을 유지하고 명시적 지우기는 초기화합니다. 종료 후 새 명령은 실행하지 않습니다.
- 텍스트의 진위나 현재 장치와의 일치를 증명하지 않습니다. ValidFrame과FF/0/1/Other가 있어도 보호 상태는 알 수 없음으로 남고 하드웨어 capability는 false입니다.
- 새 검토 기능은 장치/WMI/OEM/예약에 접근하지 않습니다. 기존 Windows 배터리 표시와 읽기 전용 진단은 유지하며 물리 제어는 Unsupported 그대로입니다.

[새 일반 앱·소스](../downloads/README.md)의 RESULT-REVIEW ZIP 전체를 새 폴더에 압축 해제한 뒤 **ATIVBatteryGuard.exe를 일반 권한으로 실행**합니다. 기존 실험 파일은 다시 실행하지 않습니다. 추가 노트북 시험 결과를 제출할 필요는 없습니다.

## 남은 개발 조건

통신 경로와 형식의 실기 확인은 확보했습니다. 남은 핵심은 현재 모델·BIOS의 Windows 배터리 명령 의미와 응답 해석 근거입니다. 이번 FF를 값 보정이나 다른 명령 탐색으로 덮지 않으며 추가 읽기/쓰기 실험에는 검토 가능한 별도 범위와 근거가 필요합니다. 저장된 분석과 공개 자료로 가능한 정적 개발을 우선합니다.

자동 검증은 합성 결과와 가상 서비스·임시 파일만 사용합니다. 새 GUI의 실제 Windows 표시/붙여넣기 동작은 아직 미검증이며 클라우드에서 Windows/OEM/펌웨어를 실행하지 않았습니다. 정확한 수치는 [VALIDATION](VALIDATION.md)에 기록합니다.

이번 전체342개와 Python 검증19개가 통과했고 여섯 프로젝트 및 테스트 프로젝트 빌드는 경고·오류0개입니다. 사용자 제출 텍스트를 새 파서로 직접 검증한 결과도 ValidatedFrameMeaningUnknown/FF이며 하드웨어 권한은 false였습니다. 이는 과거 텍스트의 검토이고 새 하드웨어 실행은 아닙니다.
