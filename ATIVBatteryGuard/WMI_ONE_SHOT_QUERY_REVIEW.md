# 다음 단계 검토서: 한정된 OEM 조회 후보 실험 — 미승인·미구현

2026-11-03 기준입니다. 이 문서는 사용자가 검토할 구체적인 범위 변경 제안입니다. 아래 OEM 호출 코드·실험용 EXE는 아직 만들지 않았고 실제 메서드를 실행하지 않았습니다. 메인 앱은 계속 Unsupported입니다.

## 왜 이 경계를 검토하는가

현재 노트북에서 WMI 클래스 GUID 후보·메서드 존재·WindowsMethodId1·입출력 DataBuffer·Bytes UInt8[]를 확인했습니다. 메모리용 요청/응답 처리와 비동기 통합 경로도 구현·검증했습니다. 남은 핵심은 모델별 배터리 명령 의미·안전성·실제 응답 계약입니다.

추가 공개 자료를 조사했지만 현재940X3G/930X3G·BIOSP05ACJ의 Windows WMI 조회 계약은 새로 확정하지 못했습니다. 이에 조회 후보를 실제로 한 번 시험하는 범위로 바꿀지 명시적으로 검토합니다. 공개 함수 이름이 Get이라고 해서 이 노트북에서 안전한 읽기라고 보장하지 않습니다.

사용자의 앞선 제한은 삼성 DLL 초기화·OEM 명령 실행을 제외했습니다. [AGENTS.md](AGENTS.md)의 지침도 “커널/펌웨어 제어 코드 추가 작업은 사용자에게 별도의 명시적 승인을 받은 뒤 안전성과 모델 적합성이 입증된 범위에서만 진행한다”입니다. 이번 제안은 **모델별 검증이 끝나지 않은 후보에 대해 별도 실험을 허용할지 묻는 범위 변경**입니다. 일반적인 개발 계속 지시나 과거의 속성 읽기 관리자 비교 승인을 이 실험 승인으로 취급하지 않습니다.

## 검토 대상과 근거의 한계

| 항목 | 근거 | 아직 확인되지 않은 전이 |
| --- | --- | --- |
| 후보 명령0x65 | 공개 samsung-hotkeys의 GetBLEStatus와 Linux SABI3 조회 후보 | 이 모델의 Windows WMI에서 같은 의미인지 |
| 첫 입력 바이트0x80 | 공개 GetBLEEnabled는 80 00 00 00을 Sabi3.dll에 전달 | WMI payload16의 나머지를0으로 채우는 것이 맞는지 |
| WMI 프레임 | 특정 서비스 wsabi의 magic0x5843+command+예약0+payload16 | 해당 배터리 후보의 정확한 입력 계약인지 |
| 응답 지원 범위 | 현재 디코더의 정확한21바이트·ACK0xAA | 실제 제공자 길이·후보 응답의 의미 |

후보 입력을 기존 순수 인코더 형식으로 표현하면 다음21바이트입니다. **검토용 자료이며 실행 지시가 아닙니다.**

43 58 65 00 00 80 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00

Windows의 WmiMethodId1과 프레임 내부 명령0x65는 별개로 유지합니다. 0x80은 기능 입력값 후보이며 80%라는 수치가 아닙니다. 이 바이트열은 검증되지 않은 경로 간 전이 가설을 포함하므로 그대로 제품 기능으로 채택하지 않습니다.

## 제안하는 도구의 정확한 범위

- 메인 앱과 분리된 asInvoker 도구 하나를 만들고 사용자가 같은 계정으로 수동 관리자 실행을 한 번 하는 범위입니다. 자동 UAC·runas·다른 계정 로그인은 구현하지 않습니다. 현재 토큰을 확인할 수 없거나 Elevated가 아니면 OEM 호출 없이 종료합니다.
- 로컬 ROOT\WMI의 고정 클래스·메서드·입출력 정의를 검증합니다. 메서드 인스턴스 전체 조회가 완료되고 정확히 한 행이며 Active=True일 때만 진행합니다. 권한 거부·오류·시간 초과·여러 행·불완전 조회에서는 중단합니다. 인스턴스 이름/경로를 추측하거나 서로 다른 클래스의 행을 자동 연결하지 않습니다.
- 해당 고정 인스턴스의 CallSabiFunction에 위 후보 요청을 최대1회 전달합니다. COM 오류도 시도1회로 계산합니다. 자동 재시도·주기 실행·다른 명령 탐색은 없습니다.
- 삼성 DLL 로드·초기화, SABI 장치 열기·IOCTL·포트 I/O, Linux 코드 실행, unlock, 드라이버/서비스/ACL/보안 설정 변경은 구현하지 않습니다. 설정 후보0x66과 다른 OEM 명령은 포함하지 않습니다.
- 부모는 작업자를10초로 제한하고 종료·정리합니다. 시간 초과는 결과 불명으로 남기며 재시도하지 않습니다. **프로세스 종료가 이미 시작된 제공자/펌웨어 동작의 중단·취소·원상 복구를 보장하지는 않습니다.**
- 프로그램 실행 중 네트워크 통신은 없고 출력은 고정된 상태값만 표시합니다. 사용자 이름·SID·시리얼·인스턴스 이름·경로·실제 GUID·원문 오류·전체 응답 바이트는 출력하거나 저장하지 않습니다.

이 도구가 쓰기 명령을 구현하지 않는다는 사실과 펌웨어 부작용의 부재는 다릅니다. **현재 모델의 후보 의미가 검증되지 않았으므로 예상하지 못한 펌웨어 동작 가능성을 배제할 수 없습니다.** 쓰기·충전 제한 구현은 이번 제안에 포함하지 않습니다.

## 결과를 어떻게 제한해 해석하는가

API 실패·컨테이너/필드 누락·배열 형식·차원·길이·ACK를 기존 통합 계층으로 구분합니다. 정확한 지원 구조를 통과해도 응답의 첫 payload 바이트는 후보 표식0/1/FF/Other로만 구분하고 원문 payload는 내보내지 않습니다. 0/1/FF를 곧바로 실제 보호 OFF/ON/미지원으로 판정하지 않습니다.

어떤 결과에서도 메인 앱의 actualMode나 실제 하드웨어 지원을 갱신하지 않으며 제어 버튼을 활성화하지 않습니다. 잔량80%·충전 중 아님·WMI Active·version16·메서드 호출 성공만으로 충전 제한 성공을 표시하지 않습니다.

이전 TXT·삼성 DLL/EXE·파일 목록·일반/관리자 속성 비교는 다시 요구하지 않습니다. 이 실험이 승인되더라도 결과 해석과 이후 쓰기 구현은 별도 단계입니다.

## 이번에 추가 확인한 공개 자료

[voria/samsung-tools README](https://github.com/voria/samsung-tools/blob/10fd47c8048e87b7c07930fccc4d258c35d68e63/README.md)와 Python31개를 정적으로 대조했습니다. Linux 도구이며 읽은 범위에는 현재 모델의 BLE/Windows WMI 명령 계약이 없었습니다. [전원 관리 backend](https://github.com/voria/samsung-tools/blob/10fd47c8048e87b7c07930fccc4d258c35d68e63/backends/system/powermanagement.py)도 현재 계약의 근거가 아닙니다. SHA-256은 각각 b0c4723f385c7ce2f925231a2ba65f001d56fc0288f98a16c0f43dbd9842ae47, bb2a22b2f801c988c68ef8b0fac2b7e09e4ae64fb414cea2b3b2943ab25bcc2b입니다.

추가로 [samsung-hotkeys 설정창](https://github.com/akastormseeker/samsung-hotkeys/blob/0d3947eea0003dd8e9372c36925c0fd0a8fd28d3/SamsungHotkeys/SettingsWindow.xaml.cs#L35)은 GetBLEEnabled의 bool을 그대로 표시합니다. [해당 함수](https://github.com/akastormseeker/samsung-hotkeys/blob/0d3947eea0003dd8e9372c36925c0fd0a8fd28d3/SamsungHotkeys/Controls/SamsungBIOSInterface.cs#L88)는 FF와OFF를 같은 false로 접으므로 현재 상태 모델로 재사용하지 않습니다. 소스의 GetBIOSStatus0x0B/BLE비트 주석은 실행 callsite가 없어 새로운 조회 명령 근거로 취급하지 않았습니다. 설정창/BIOSInterface SHA-256은 각각 6ee9ad2e59454c562acf466dc8024406832d748d12413149619737e34c81eb5c, fa3e2ee228d3f4012bfa259c06437ee0de2f7187fcc64518a8dac6b60ad54c68입니다. 이슈2·3은 다른 Chronos7 모델의 설치·백라이트 문제이며 현재 모델 BLE 검증으로 확대하지 않습니다.

ACPI 테이블을 복사해 _WDG/WMxx 선언만 확인하는 방법도 검토했습니다. Windows 기본 API의 읽기 범위지만 선언·인수 수만으로 배터리 opcode·실제 응답 계약은 밝혀지지 않아 새 진단을 즉시 추가하지 않았습니다. [공식 GetSystemFirmwareTable](https://github.com/MicrosoftDocs/sdk-api/blob/656e9656bfaef34dd29cd7ee9e1146aec17e924c/sdk-api-src/content/sysinfoapi/nf-sysinfoapi-getsystemfirmwaretable.md#L153)은 중복 signature 테이블 중 첫 것만 반환하는 제한도 설명합니다. 이 검토에서 펌웨어 테이블·AML·OEM 코드를 실행하지 않았습니다.

## 현재 완료된 것과 승인 뒤 작업

현재 완료한 것은 추가 정적 조사, 후보 바이트·권한·횟수·출력·중단 조건·위험을 명시한 이 검토서입니다. OEM 실행 구현과 실기 시도는 미승인·미구현·미실행입니다. 기존 실제 충전 제어는 계속 Unsupported입니다.

명시적 범위 변경 승인을 받으면 이 제한에 맞는 별도 도구를 구현하고, 무호출 조건·최대1회·고정 명령 외 거부·취소/시간 초과·개인정보 제한·해석 차단을 먼저 자동 검증한 뒤 검토 가능한 소스와 다운로드 프로그램을 제공합니다. 과거297개 테스트와 빌드 경고/오류0개는 이전 코드의 검증 기록이며 이번 문서 변경에서 다시 실행한 결과가 아닙니다.
