# Image Monitor 0.5.0-alpha.1

Windows에서 공개 검색 결과를 감시하고 본문 이미지를 수집하는 프로그램입니다.

`RUN_AUTO_COLLECT.cmd`는 기존 감시 기록에서 게시글 한 건을 자동 저장하는 실행기입니다.
이미 본문 확인을 마친 저장 대상이 있으면 그 글을 사용합니다. 대상이 없으면 아직 열지 않은
글을 최대 세 건 확인합니다. 저장 가능한 본문 이미지가 한두 장인 글을 찾으면 전용 Chrome을
열어 다시 대조한 뒤 실제 우클릭으로 저장하고 파일을 검증합니다. 전용 Chrome 창을 앞에 두세요.
게시글마다 누르던 **저장 시작** 버튼은 이 실행기에서 생략됩니다. 한 글을 저장하거나
이번 범위에서 대상을 찾지 못하면 결과 TXT를 열고 종료합니다. 주기적인 목록 확인은
`RUN_MONITOR.cmd`에서 시작할 수 있습니다.

`RUN_MONITOR_RESUME.cmd`는 이전 감시에서 남겨 둔 본문 확인 한 건을 이어서 처리하고
결과 TXT를 엽니다. 종료 시간에 맞춰 감시 창을 지켜볼 필요가 없습니다. 남은 차례가 없으면
바로 종료하고, 대기 시간이 60초를 넘으면 다음에 확인할 수 있는 시각을 표시합니다.
이미지는 기존 저장 절차에서 별도로 저장합니다.

`RUN_MONITOR.cmd`로 감시 화면을 다시 열면, 지난 목록 검사에서 본문 확인 차례가 남아 있는지
표시합니다. **감시 시작**을 누르면 저장된 대기 시간이 지난 뒤 미확인 글 한 건을 먼저 확인하고
목록 감시로 돌아갑니다. 이어갈 기록이 없으면 목록부터 확인합니다.

`CHECK_WATCH_IMAGES.cmd`는 최근 게시글 저장 시험에서 마지막으로 완료한 파일을 디스크에서 다시 확인합니다.
프로그램을 다시 실행한 뒤에도 저장 당시 기록과 현재 파일이 일치하는지 확인할 수 있습니다.
결과 TXT에는 확인한 파일명과 형식, 크기, 해상도가 표시됩니다. 이 확인은 브라우저를 열거나 파일을 다시 저장할 필요가 없습니다.

`RUN_WATCH_IMAGES.cmd`는 이전 상세 검사 기록을 읽고, 필요하면 같은 목록에서 새 글을 최대 세 건까지
확인합니다. 본문 이미지가 0장인 글, 저장 대상 이미지가 3장 이상인 글, 삭제된 글은 건너뛰고
다음 후보를 확인합니다. 첨부 목록에만 있는 파일은 저장 대상에서 제외합니다.
저장 조건을 충족한 본문 이미지가 한두 장인 글을 찾으면 전용 Chrome에 그 글을 열고 다시 대조합니다.
**저장 시작**을 한 번 누르면 기존 우클릭 저장 절차로 파일을 저장하고 검증합니다.

`RUN_WATCH_DETAIL.cmd`는 SQLite에서 최근 목록 검사와 후보의 주소를 대조하고, 그때 처음 발견한
글 중 아직 본문을 열지 않은 한 건을 Chrome으로 확인합니다. 결과 TXT에 작성 시각 판정과
본문 이미지 수를 기록합니다. 이 시험에서 목록을 다시 읽거나 이미지를 저장할 필요는 없습니다.

목록 시험은 최신 두 페이지를 검증한 뒤 과거 완료 지점에 도달하지 못했을 때 최근 후보와
미확인 구간을 함께 기록합니다. 광고·공지·설문으로 식별한 행은 작성자 칸 수가 달라도 제외할 수 있습니다.
일반 글은 작성자 칸 하나와 표시 이름을 확인하며, 표 전체의 작성자 칸 수도 각 행에서 센 합계와 대조합니다.
목록 시험 결과는 페이지별 검증 상태와, 기록에서 확인한 경우 작성자 칸이 없거나 여러 개인 행의 종류와 개수를 표시합니다.
`CHECK_LAST_LIST.cmd`는 감시 DB에서 최근 목록 구조 실패 한 건을 읽고 결과 TXT를 엽니다.
기록이 남아 있는 범위에서 페이지별 목록 상태, 행 수, 검증을 통과하지 못한 항목을 표시합니다.
감시 화면에서도 최근 실패 기록을 펼쳐 볼 수 있습니다.

정기 감시 중에는 알려진 목록에서 작성 정보나 보조 표의 행이 늦게 나타나는 경우 같은 문서를
한 번 더 읽습니다. 두 번째 페이지의 구조만 검증에 실패하면, 첫 페이지에서 독립적으로
검증된 후보는 기록하고 감시를 멈춥니다. 이전 완료 지점과 미확인 구간은 보존합니다.
`RUN_MONITOR.cmd`에서 **감시 시작**을 누르면 목록과 미시도 후보 본문을 번갈아 읽습니다.
최근 두 페이지의 글과 이동 경로가 검증되면 이전 목록과의 겹침을 끝까지 확인하지 못한
경우에도 후보 한 건을 확인할 수 있습니다. 화면에는 목록 부분 확인과 전체 확인을 따로
표시하며 이전 완료 지점과 누락 구간을 보존합니다. 작업 간격은 기본 60초입니다.

감시를 중지하면 작업 현황을 갱신합니다. 저장할 후보가 있으면 **후보 1건 저장**을 누르고
열린 전용 Chrome에서 **저장 시작**을 누릅니다. Chrome을 앞에 두면 기존 Windows 우클릭
저장·파일 검증 절차를 수행합니다. 저장이 끝나면 감시 화면의 완료 수와 미리보기를 갱신합니다.
서버 대기 중에는 남은 시간을 표시합니다.

0.4는 단일 갤러리의 수집 단계를 연결하는 버전입니다. 기존 v1~v23은 각 Windows 시험 ZIP의
번호입니다. 원 설계안과 대조한 기능별 결과, 다음 버전의 범위와 완료 기준은
[개발 단계와 버전 계획](docs/development-roadmap.ko.md)에 정리했습니다.

## v23까지의 개발·검증 이력

Windows에서 공개 게시글의 본문 이미지를 실제 우클릭과 브라우저의 네이티브 저장 창으로
저장하는 별도 프로젝트입니다. 기존 Image Duplicate Finder는 그대로 유지합니다.
초기에는 **예제 게시글 하나의 Chrome 저장과 재개**를 사용자 환경에서 완료했습니다.
사용자 v13 결과에서 목록 기준점과 새 후보 6개 기록, v14 결과에서 기존 후보 두 개의 작성
시각·본문 관찰을 확인했습니다. v15에서 한 후보의 JPEG·PNG 두 파일을 저장·검증·확정했고,
v16에서 기존 두 파일과 메타데이터 보존·이전 브라우저 종료·미해결 표시 해제를 확인했습니다.
v16은 이미 종료된 브라우저를 확인한 결과이며 사용자 PC에서 새 CDP 재연결 종료를 실행한
증거는 아닙니다.

원 설계와 현재 구현·사용자 인수 범위의 차이는 [프로젝트 검토](docs/project-review.md)에
정리했습니다. 목록 발견부터 상세 확인·저장까지 계속 이어지는 전체 자동 수집은 아직 완료되지 않았습니다.

v17은 **목록 감시를 시작·일시정지·중지하는 로컬 상태 화면**을 추가했습니다. 사용자 결과에서
두 주기 실행·새 후보 3개 기록·정상 종료를 확인했습니다. 검토한 검색 범위의 목록을
주기적으로 읽어 새 후보를 기록하며 이미지 자동 저장은 연결하지 않습니다.
기존 시험 기록과 분리한 `목록 감시` 범위의 첫 시작은 지금부터의 기준점을 만들고,
이후 실행은 그 범위의 기준점과 후보를 이어갑니다. 장시간 실행·일시정지/재개 수동 조작·
재시작 후 보존은 이번 사용자 결과의 검증 범위에 포함하지 않습니다.

v18에서는 같은 화면의 정지 상태에서 기존 후보 두 개의 내용을 읽고 정상 종료한 사용자
결과를 확인했습니다. 두 후보 모두 기준점 이후 작성 시각과 로딩된 본문 이미지 1개를 보고했습니다.
새 목록을 읽거나 기준점을 초기화하지 않으며 작성 시각의 기준점 비교와 본문 이미지 개수를
익명 결과 표에 표시합니다. 확인을 마쳐도 목록 감시를 자동으로 재개하지 않습니다.

v19의 별도 `RUN_MONITOR_SAVE.cmd`는 이 `목록 감시` 범위의 완료 상세 관찰에서 후보 하나를
고정해 기존 Chrome 네이티브 저장 작업자에 연결합니다. 전용 Chrome에서 `저장 시작`을 누른 뒤
그 창을 앞에 유지해야 합니다. 사용자 결과에서 JPEG 한 개의 저장·검증·확정과 브라우저 정상
종료·미해결 표시 해제를 확인했습니다. 이전 후보 시험의 선택·저장 위치와 분리하며 모든 후보의
이미지 자동 저장과 다중 갤러리 설정은 아직 없습니다.

v20은 `RUN_MONITOR.cmd`의 같은 로컬 화면에 **저장 결과**를 추가합니다. 화면을 열면 정지
상태에서 기존 완료 파일을 한 번 검증하고, 감시 제어 아래의 저장 결과 영역에 미리보기와 형식·
크기·해상도를 표시합니다. 아래로 스크롤해야 보일 수 있습니다. 이번 확인에는 감시 시작·후보
내용 확인·네이티브 저장을 다시 실행할 필요가 없습니다. 현재 Windows 세션에 저장한 한 고정
후보의 결과를 읽는 기능이며 원본 사이트 접속·이미지 재저장·자동 복구는 하지 않습니다.

v20 사용자 TXT에서는 기존 JPEG 한 개의 재검증과 미리보기 캐시 준비·정상 종료를
확인했습니다. 브라우저의 실제 이미지 표시나 육안 확인을 입증한 결과와는 구분합니다.

v21의 `RUN_MONITOR_BATCH.cmd`는 이미 상세 확인한 `목록 감시` 후보를 이어 처리합니다.
기존 v19 완료 파일을 읽기 전용으로 재검증해 새 저장 이력에 등록하고 재저장하지 않으며,
새 네이티브 시도는 한 실행에 최대 두 번으로 제한합니다. 후보별 출력은 별도
`ImageMonitorBatch`에 분리합니다. 사용자 v21 결과에서 이전 완료 한 건의 등록·재저장 건너뜀과
다른 후보 한 건의 새 JPEG 저장·검증·확정·정상 종료를 확인했습니다. 새 후보 두 건을 한 실행에서
저장한 근거는 아니며 정기 감시가 새 후보를 계속 저장하는 전체 자동화와 구분합니다.

v22는 **기존 완료 파일과 배치 완료 파일을 같은 저장 결과 화면에서 열람하는 연결**을
추가했습니다. 사용자 TXT와 `두 장 모두 보임` 답변으로 두 파일의 검증·미리보기 준비,
실제 화면 표시와 정상 종료를 확인했습니다. 완료 원장에 등록된 기존 파일은 중복해서
추가하지 않으며 서로 다른 게시글의 같은 `001.jpg`도 `저장 묶음 1`·`저장 묶음 2`로 구분합니다.
v19와 v21에서 저장한 서로 다른 JPEG 두 장이 검증됐고 생략된 파일이나 오류는 없었습니다.
화면을 열면 정지 상태에서 로컬 검증만 수행하며 목록·상세 탐색이나 네이티브 저장은 시작하지 않습니다.

v23은 같은 화면에 **기존 후보와 저장 작업을 구분하는 작업 현황**을 추가했습니다.
발견 DB·배치 원장과 완료 파일 근거를 읽어 내용 미확인·저장 가능·계획됨·진행 중·완료·
저장 불가·확인 필요를 나눠 표시합니다. 사용자 Windows 결과에서 **내용 미확인 1개·
저장 완료 2건**, 기존 JPEG 두 장의 검증·미리보기 준비와 정상 종료를 확인했습니다.
시작 시 작업 현황과 기존 이미지 두 장을 로컬에서 다시 확인합니다.
`작업 현황 새로 확인`도 기록·선택·이미지 파일을 보존하는 읽기 전용 동작입니다.

`완료 상태 다시 확인`은 같은 Windows 세션의 미완료 저장 한 건에 대해 이미 저장된 파일과
작업 정체성·필요한 완료 근거가 모두 맞는 경우에만 활성화하는 명시적 종료 확인입니다.
이번 사용자 결과에서는 정리 대상이 없어 버튼 비활성 상태가 확인됐습니다. 정리 대상이 있을
때의 실행과 완료 처리는 자동화 시험에서 검증했습니다.

Windows 실행 절차와 결과 확인은 ZIP 안의 [짧은 TXT 안내](WINDOWS_TEST_GUIDE.txt)에
하나로 정리합니다. 기본 저장 시험과 게시글 저장·재개 명령도 유지합니다.
개발용 패키징은 `python scripts/build_windows_bundle.py`이며 패키지 버전에 맞는 ZIP을 생성합니다.

## 현재 구현

- 본문 `.write_div` 안의 로딩·decode가 완료된 일반 이미지 수집과 디시콘·광고·댓글·영상 제외.
- 유일한 게시글 헤더에서 제목·작성자·공개 부분 IP·Asia/Seoul 작성 시각 추출.
- 확인한 본문/첨부 엔드포인트의 공통 `no`로 원본명 대응과 안정적 작업 키 산출.
  순서·파일명·다른 속성으로 대응을 추측하지 않습니다.
- SQLite 발견·불변 관찰 결과·작업 선점·재시도 정책·파일 슬롯·최초 폴더 계획 보존.
- [검색 목록과 주기 감시](docs/list-watch.md): 검토한 검색 구조·번호/링크 일치·행 분류,
  최신 기준점·겹친 구간·미확인 구간과 별도 SQLite의 영구 후보 기록.
  기존 두 주기 시험과 새 로컬 감시 화면 모두 이미지 작업을 생성하지 않습니다.
- 시작 전에는 정지한 로컬 상태 화면에서 시작·일시정지·재개·중지·종료를 선택합니다.
  60~300초 간격은 정지 상태에서만 변경·보존하며 앞 관찰이 끝난 뒤의 최소 대기를 지킵니다.
  headless Chrome으로 목록과 미시도 후보의 본문을 번갈아 읽으므로 그동안 다른 작업을 계속할 수 있습니다.
  구간 누락·구조 오류·접근 차단은 검토 대기로 멈추며 기준점을 자동 초기화하지 않습니다.
- 정지 상태의 `후보 내용 확인`은 같은 `목록 감시` 범위에 보존한 미시도 후보를 한 번에 최대
  두 개 확인합니다. headless Chrome으로 본문을 읽으며 다른 작업을 계속할 수 있습니다.
  앞 확인 종료 후 최소 60초·같은 DB의 공통 대기·서버 대기를 지키고 목록 감시와 동시에
  탐색하지 않습니다. 시도 시작을 먼저 영구 기록하므로 중단·실패도 자동 재시도하지 않습니다.
  확인 수와 대기 수·완료 수, 익명 행의 시각 판정·본문 이미지 개수를 표시하며 이미지 작업과
  네이티브 저장은 시작하지 않습니다.
- 기존 감시 DB의 미시도 후보를 최대 두 개 읽어 정확한 작성 시각과 최초 기준 시각을 대조하고,
  헤더·본문·이미지 개수 등 제한된 구조를 보고합니다. 목록을 다시 읽거나 기준점을 초기화하지
  않으며, 결과는 DB v5의 별도 상세 시도 기록으로 보존합니다. 이 읽기 전용 단계의 날짜 판정만으로
  저장 승인과 이미지 작업 등록을 허용하지 않습니다.
- 완료된 상세 관찰과 현재 본문이 일치하는 후보 하나에만 명시적인 `CandidateSavePermit`을 적용합니다.
  본문 이미지가 없는 후보는 건너뛰고 로딩된 이미지 1~2개·기준점 이후 작성 시각을 확인한 대상을
  고정합니다. 별도 네이티브 DB와 출력 루트에서 기존 저장 작업자를 사용하며 발견 DB의 이미지
  작업은 0개로 유지합니다. 다시 실행해도 같은 선택과 완료 파일을 유지합니다.
- `monitor-save-test`는 `목록 감시` 범위에만 묶인 완료 관찰에서 선택을 고정하고 별도
  `monitor-save-selection.json`과 `ImageMonitorMonitorSave` 출력 루트를 사용합니다.
  이전 `검색 감시 시험`의 선택·저장 파일은 유지하며 범위가 다른 관찰을 섞지 않습니다.
  목록·상세 확인을 반복하지 않고 전용 Chrome의 현재 헤더·이미지 집합을 허가와 다시 대조합니다.
  로컬 감시 화면의 백그라운드 작업에 네이티브 저장을 넣지 않고 별도 실행기의 주 스레드에서 처리합니다.
- `monitor-save-batch`는 기존 완료 상세 관찰만 사용하고 별도 `monitor-save-ledger.sqlite`
  스키마 1에 후보별 진행 상태를 기록합니다. 기존 `watch.sqlite`의 스키마 5와 단일 저장 선택은
  유지합니다. 이전 완료 파일을 재검증해 등록한 뒤 새 후보마다 UUID 작업 루트와 세션을 고정하며
  작업자 호출 전에 `started`를 커밋합니다. 중단·검토 상태는 자동 재시도하지 않습니다.
  서비스 대기·접근 차단과 탐색 진행 여부가 불명확한 상태는 현재 버전의 목록·상세·저장 진입점에
  함께 적용합니다. 삭제된 후보는 입력 전·빈 네이티브 DB·브라우저 종료·보류 없음이 입증된
  404/410에만 해당 후보를 소진하고 다음 후보로 넘어갑니다.
- 로컬 화면의 저장 결과는 현재 세션의 기존 DB·완료 저널·파일·메타데이터를 읽기 전용으로
  대조합니다. 배치 루트를 지정하면 원장의 완료 목록을 고정해 모든 완료 건의 원본 관찰·허가와
  파일을 검증하고, 이력에 등록한 이전 단일 저장은 한 번만 포함합니다. 익명 저장 묶음으로 같은
  파일명을 구분하며 검증 후 파일 정보 최대 20개를 표시합니다. Pillow와 배타적 해시 검증을
  통과한 JPEG·PNG·WEBP·GIF·BMP 원본 바이트만 파일당 16MiB·전체 32MiB 이내에서 메모리에
  보관합니다. TIFF나 미리보기 한도를 넘는 표시 항목은 검증된 정보만 보여주며 20개를 넘는
  완료 파일도 검증 수와 생략 수에 반영합니다. 정지 상태의 `저장 결과 새로 확인`으로 다시 읽을 수
  있습니다. 미해결 네이티브 저장이나 일치하지 않는 근거가 있으면 파일을 표시하지 않습니다.
  열람은 목록·상세 탐색·네이티브 저장·원장 변경을 수행하지 않으며 새 이미지 수집·재인코딩·
  파일 변경도 없습니다. 전체 과거 저장 폴더를 임의로 탐색하는 기능은 아닙니다.
- 작업 현황은 같은 감시 범위의 기존 후보·상세 기록·배치 원장·네이티브 완료 근거를 읽기
  전용으로 대조합니다. 완료 작업에 해당하는 후보를 중복 집계하지 않고 아직 내용 확인을
  시도하지 않은 후보와 구분하며 익명 기록은 최대 20개 표시합니다. 기존 접근 차단·탐색 미확정·
  검토 상태와 서버 대기를 유지하고 현황 새로 확인으로 감시나 네트워크 제어를 풀지 않습니다.
- 명시적인 `완료 상태 다시 확인` 요청은 활성화 근거를 다시 읽은 뒤 기존
  `monitor-batch-finish`를 소유한 별도 프로세스의 주 스레드에서 한 번 실행합니다. 실행 경로는
  PID·생성 시각·프로필·세션·미해결 표시의 정체성과 파일·보고서를 다시 대조하고 전용 브라우저의
  부재 또는 정상 종료를 확인한 뒤에만 표시를 해제하고 원장을 완료 처리합니다. 새 네이티브 입력·
  다운로드·부분 파일 재시도는 없습니다. 시작 전 중지는 실행을 막으며 시작 후 중지·종료는
  프로세스를 강제 종료하지 않고 기존 완료 확인과 정리가 끝날 때까지 기다립니다.
- 기존 후보의 저장 완료 보고서·고정 원본 관찰·완료 작업·확정 저널·파일 해시·Pillow 결과와
  메타데이터를 읽기 전용으로 대조하는 `candidate-finish`를 추가합니다. 전용 브라우저가 남아
  있으면 정확한 PID·생성 시각·프로필·세션·디버깅 포트 소유권을 확인한 뒤 정상 종료만 요청하고,
  전체 프로필 종료를 확인해야 세션 공통 미해결 표시를 정리합니다. 이미지 재저장·작업 재대기·
  이미지와 메타데이터 덮어쓰기는 없습니다.
- 전용 프로필·Windows 세션 공통 잠금·미해결 저장 표시와 전경/창 소유권 보호.
- 이미지 사이의 전경 이탈 시 선점 전 일시정지, 새 사용자 클릭과 게시글 재검사 후 재개.
- 입력 전 중단이 기록·원본 관찰·빈 임시 폴더·브라우저 종료로 입증된 v9 실패의 개별 재개.
- 저장 직전에 정확한 이미지 `currentSrc`, 본문 소속, 게시글 URL과 예상 헤더 재검사.
- 실제 우클릭 → UIA 메뉴 Invoke → Windows Save As에 고유 staging 경로 입력.
- Chrome의 소유한 백그라운드 다운로드 목록에서 정확한 원본 URL·저장 경로와 완료 상태 확인.
- 배타적 파일 읽기와 Pillow 전체 프레임 검증으로 형식·크기·SHA-256 산출.
- 최종 파일 덮어쓰기 거부, 확정 저널, DB 완료 처리와 원자적 `metadata.json` 기록.
  확정 도중 중단된 작업은 네이티브 저장을 반복하지 않고 로컬 파일과 저널로 복구합니다.

기본 `save-post`의 실사이트 저장 대상은 사용자 v7/v8 관찰로 검증한 일반 갤러리 `comic_new6`의
게시글 `7036949` 한 개로 제한합니다. v15의 별도 후보 시험은 완료된 v14 관찰에서 만든 불변
허가와 현재 본문 재검사를 모두 통과한 한 게시글만 연결합니다. 전역 `site_verified` 대상이나
다른 게시글·마이너·미니 갤러리의 저장 프로필을 넓히지 않습니다.
v9 사용자 TXT에서 실제 WEBP 한 개의 저장·검증·최종 확정을 확인했습니다.
두 번째 이미지는 첫 조작 전 전경 보호 검사에서 중단됐습니다. v10 사용자 결과에서 해당 작업의
입력 전 재개와 나머지 세 파일의 저장·검증·확정을 확인해 이 게시글의 전체 저장 인수 시험을
통과했습니다. 기존 `001.webp`는 다시 저장하지 않았으며 완료 4개·미해결 0개로 종료했습니다.
이 저장 결과는 검증한 게시글 하나에 한정합니다. 별도의 v12 목록 관찰은 일반 갤러리
`comic_new6`의 `ai` 제목+내용 검색 두 페이지에서 게시글 40개와 실제 다음 페이지 이동을
확인했습니다. 목록 구조 검증은 다른 검색 범위의 본문 분석이나 이미지 자동 저장을 허용하지 않습니다.
v13의 새 후보 6개 발견은 목록 발견 연결의 사용자 인수 결과이며 상세 작성 시각 필터·본문 분석·
새 글 이미지 저장을 입증하지 않습니다. v14 결과에서는 두 후보의 기준점 이후 작성 시각과
본문 이미지 0개/2개를 확인했습니다. 이미지 두 개와 첨부 한 개의 원본명 대응은 `ambiguous`여서
원본명은 null로 유지합니다. v15 사용자 결과에서 후보의 `001.jpg`와 `002.png`가 모두 검증·
확정되고 완료 2개·미완료 0개인 것을 확인했습니다. 전체 결과는 마지막 Chrome 종료 확인 실패로
`candidate_save_manual_review`였으며 미해결 표시가 남았습니다. 창이 사라진 사실만으로 프로세스
종료나 표시 해제를 단정하지 않습니다. 이후 v16에서 기존 파일 두 개의 재검증과 보존,
이전 브라우저 종료와 미해결 표시 해제를 확인해 이 고정 후보의 완료 연결을 마쳤습니다.
`close_attempted`가 false였으므로 새 종료 방식의 사용자 실행으로 해석하지 않습니다.
Edge와 Chrome의 기본 합성 이미지 저장은 Windows CI와 사용자 보고에서 성공했으며,
이번 통합 작업자의 완료 판독은 Chrome만 지원합니다.

원본 공개 첨부명·저장 창 제안명·최종 저장명은 메타데이터에 별도로 보존합니다.
저장 경로는 `감시이름/실제ID/날짜/작성자/글번호/001.실제확장자` 형태입니다.
금지 문자·예약 이름·이름 충돌·루트 이탈·심볼릭 링크와 경로 길이를 검사하며,
공개 IP는 화면에 보이는 표시값만 사용합니다.

## 실행과 개발

TXT 안내의 Windows 실행기는 uv·관리형 Python 3.12.14·잠금 의존성을 준비합니다.
개발자는 이 디렉터리에서 실행합니다.

```powershell
uv sync --locked --extra windows
uv run --locked --extra windows image-monitor save-post --work-root C:/IMPost --browser chrome
uv run --locked --extra windows image-monitor watch-test --work-root C:/IMWatch --browser chrome
uv run --locked --extra windows image-monitor monitor --work-root C:/IMWatch
uv run --locked --extra windows image-monitor monitor --work-root C:/IMWatch --save-root C:/IMMonitorSave
uv run --locked --extra windows image-monitor monitor --work-root C:/IMWatch --save-root C:/IMMonitorSave --batch-root C:/IMMonitorBatch
uv run --locked --extra windows image-monitor candidate-test --work-root C:/IMWatch --browser chrome
uv run --locked --extra windows image-monitor candidate-save-test --watch-root C:/IMWatch --work-root C:/IMCandidateSave --browser chrome
uv run --locked --extra windows image-monitor candidate-finish --watch-root C:/IMWatch --work-root C:/IMCandidateSave
uv run --locked --extra windows image-monitor monitor-save-test --watch-root C:/IMWatch --work-root C:/IMMonitorSave --browser chrome
uv run --locked --extra windows image-monitor monitor-finish --watch-root C:/IMWatch --work-root C:/IMMonitorSave
uv run --locked --extra windows image-monitor monitor-save-batch --watch-root C:/IMWatch --legacy-root C:/IMMonitorSave --work-root C:/IMMonitorBatch
uv run --locked --extra windows image-monitor monitor-batch-finish --watch-root C:/IMWatch --legacy-root C:/IMMonitorSave --work-root C:/IMMonitorBatch
uv run --locked pytest -q
uv run --locked ruff check .
uv run --locked ruff format --check .
```

Linux에서는 로컬 정책·검증·대기열·DOM fixture 시험을 실행할 수 있습니다.
실제 Windows UI 시험과 모의 시험의 결과는 [검증 기록](docs/validation.md)에 구분합니다.
`monitor`는 같은 `ImageMonitorWatch/watch.sqlite` 안에 별도 이름 `목록 감시`의 상태를 만듭니다.
처음 시작할 때 이 범위의 새 기준점을 만들며 기존 `검색 감시 시험`의 오래된 완료 지점을
가져오거나 초기화하지 않습니다. 화면을 열기만 해서는 사이트에 접속하지 않습니다.
시작·대기·중지 상태와 새 후보 수를 로컬 화면에서 확인하고 종료하면 결과 TXT를 엽니다.
일시정지·중지는 진행 중인 탐색을 즉시 강제 종료하지 않고 안전한 종료가 끝날 때까지 기다립니다.
`RUN_MONITOR.cmd`는 기존 `ImageMonitorMonitorSave`와 `ImageMonitorBatch`를 열람 루트로
전달합니다. 화면은 열자마자 정지 상태에서 작업 현황과 저장 결과의 로컬 검증을 한 번
시작합니다. 결과 TXT에는 작업 상태별 수와 익명 행·대기 사유·완료 확인 가능 여부를 포함합니다.
이번 Windows 확인의 조작 절차는 TXT 안내 한 곳에만 둡니다. 개발용 `monitor --save-root`는 선택 옵션으로 생략하면 기존
감시 화면만 열고 저장 결과 검증은 시작하지 않습니다. 추가 옵션 `--batch-root`는 `--save-root`를
함께 지정해야 하며 생략하면 기존 단일 저장 결과만 검증합니다.
기존 감시 후보의 내용만 확인하려면 `RUN_MONITOR.cmd`를 열고 정지 상태에서 `후보 내용 확인`을
한 번 누릅니다. 완료 후 정지 상태가 되면 `프로그램 종료`를 눌러 자동으로 열린 결과 TXT를
전달하면 됩니다. 이 동작은 새 목록 탐색·기준점 초기화·이미지 저장·목록 감시 자동 재개를
시작하지 않습니다. 최초 기준점이나 미시도 후보가 없으면 새 후보를 임의로 만들지 않습니다.
`candidate-test`는 같은 작업 루트의 기존 감시 DB와 최초 기준점·후보를 요구합니다. DB v5로
추가 마이그레이션한 상태는 이전 v13 실행 파일에서 거부되므로 버전이 다른 실행기를 섞지 않습니다.
`candidate-save-test`는 같은 발견 루트와 별도의 저장 루트를
요구하며, Windows 실행기는 각각 `ImageMonitorWatch`와 `ImageMonitorCandidateSave`를 사용합니다.
선택은 발견 루트의 `candidate-save-selection.json`에 고정합니다. 후보 시험에는 기존 v9용
`--resume-preinput`을 적용하지 않습니다. `candidate-finish`도 같은 두 루트와 고정 선택을 사용하며
완료된 파일의 읽기 전용 확인과 종료 정리만 수행합니다. 새 브라우저·게시글 탐색·네이티브 입력은 없습니다.

`monitor-save-test`는 같은 발견 루트에서 `목록 감시`의 완료 관찰을 사용합니다. Windows 실행기
`RUN_MONITOR_SAVE.cmd`는 별도 `%LOCALAPPDATA%/ImageMonitorMonitorSave`를 출력 루트로
사용하고 발견 루트의 `monitor-save-selection.json`에 한 후보를 고정합니다. 기본 사용자 시험은
이 실행기를 더블클릭한 뒤 열린 전용 Chrome에서 `저장 시작`을 한 번 누르는 절차입니다.
저장이 끝날 때까지 그 창을 앞에 두면 결과 TXT 하나가 자동으로 열립니다. 목록 감시나 후보 내용
확인을 다시 실행할 필요가 없습니다. `monitor-finish`와 `RUN_MONITOR_FINISH.cmd`는 완료 파일의
근거와 종료 상태만 확인하는 별도 지원용 경로이며 기본 시험에 추가 실행을 요구하지 않습니다.

`RUN_MONITOR_BATCH.cmd`는 같은 발견 루트와 기존 `ImageMonitorMonitorSave`, 새
`ImageMonitorBatch`를 전달합니다. 이전 완료 파일은 재검증 뒤 건너뛰고 아직 시도하지 않은
완료 상세 관찰만 새 Chrome에서 `저장 시작`을 누르는 대상입니다. 저장이 끝날 때까지 그 창을
앞에 유지하면 결과 TXT가 자동으로 열립니다. v21 사용자 결과에서는 남은 한 후보의 저장이
완료됐으며 v23 현황·열람 확인에는 이 실행기를 다시 실행할 필요가 없습니다.
지원용 `RUN_MONITOR_BATCH_FINISH.cmd`는 완료 근거와 정확한 이전 브라우저 종료만 재확인하며
새 입력·재다운로드를 하지 않습니다. 미해결 작업이 다른 Windows 세션에 속하면 처리하지 않습니다.

기존 `RUN_MONITOR_SAVE.cmd`는 이전 한 후보에 고정된 동작을 유지합니다. v20의 저장 결과
화면은 이전 완료 파일만 읽었으며 v22에서는 배치 루트를 함께 지정해 새 완료 파일도 검증합니다.

중단 뒤 자동으로 재저장하거나 보류 상태를 초기화하지 않습니다. 명시적인 입력 전 재개는
브라우저 종료와 로컬 기록을 대조해 검증한 실패 작업 하나만 다시 대기열에 넣고,
이미 저장한 파일·확정 기록·재시도 이력을 유지합니다. 입력이 시작됐거나 근거가 불명확한
보류 작업은 검토 상태를 유지합니다. v16의 명시적 완료 확인은 이미 완료된 후보의 모든 로컬
근거와 전용 프로필 종료가 확인된 경우에만 표시를 정리하며 이전 작업자 보고서는 보존합니다.
사용자 절차는 위 TXT 안내를 따릅니다.

직접 HTTP 이미지 저장·응답 바이트 추출·`download.save_as`·스크린샷·재인코딩은 사용하지 않습니다.
알려진 원본 해시 비교는 합성 fixture 시험에만 사용하며 실제 게시글에서는 저장 파일의 해시를 기록합니다.
남은 작업은 다른 게시글의 본문 구조 검증·장시간 감시 및 재시작 보존의 사용자 인수·누락 구간 재탐색·
상세 시각 필터의 다른 분기 인수와 발견부터 저장까지 이어지는 전체 자동 수집·다중 갤러리 설정·전체 저장 이력 열람·
네이티브 저장의 긴급 중단 UI·용량 관리,
일반 재시도와 보류 작업 수동 처리, 화면 잠금·다중 모니터·배율의 추가 인수 시험,
Pillow 단일 디코딩 호출의 프로세스 격리입니다.
