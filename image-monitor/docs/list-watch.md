# 검색 목록과 주기 감시 — 개발 단계

사용자 v10 시험에서 검증한 게시글 하나의 이미지 4개 저장과 재개를 완료했습니다.
별도의 사용자 v12 읽기 전용 관찰로 일반 갤러리 `comic_new6`의 `ai` 제목+내용 검색
두 페이지 구조를 확인했습니다. v13 사용자 시험에서는 이 범위의 최초 기준점과 다음 주기의
새 후보 6개 기록을 확인했습니다. v14 사용자 결과에서는 기존 후보 두 개의 작성 시각과 본문을
확인했습니다. v15의 한 후보 저장과 v16의 재검증·완료 정리까지 사용자 인수를 마쳤습니다.
v17은 별도 범위에서 시작·일시정지·재개·중지할 수 있는 주기적 목록 발견을 연결했습니다.
사용자 결과에서 두 주기·새 후보 3개와 정상 종료를 확인했습니다. v18에서는 같은 화면의 정지
상태에서 기존 후보 두 개의 작성 시각·본문 이미지 관찰과 정상 종료를 확인했습니다. 이 읽기
전용 연결과 별도로 v19에서는 `목록 감시`의 완료 관찰에 묶인 한 후보의 JPEG 저장·검증·확정과
정상 종료를 사용자 환경에서 확인했습니다. v20은 같은 로컬 화면에서 기존 완료 파일을 검증하고
표시합니다. 정기 목록 감시가 이미지 작업자나 모든 새 후보의 자동 저장을 실행하지는 않습니다.

## 읽기 전용 관찰과 사용자 v12 근거

목록 검사는 다운로드를 허용하지 않는 전용 headless Chrome으로 최신 첫 페이지를 읽습니다.
같은 검색 범위의 실제 인접 링크가 유일하게 확인되면 두 번째 페이지까지 정상 탐색하며,
과거 검색 구간이나 세 번째 페이지로 넘어가지 않습니다. 이미지 저장·대기열 기록·네이티브
저장 창 조작은 없으며 두 번째 관찰이 실패해도 첫 관찰을 보고서에 남깁니다.
사용자 실행 절차는 ZIP 안의 `WINDOWS_TEST_GUIDE.txt` 하나로 정리합니다.

사용자 v11에서는 `.gall_list` 두 개가 함께 잡혀 `ambiguous_list`로 중단됐습니다.
v12는 자신의 tbody에 직접 속한 `.ub-content` 행이나 명시적 빈 목록 구조를 가진 테이블을
후보로 삼고, 후보가 정확히 하나일 때만 읽도록 수정했습니다. 순서나 표시 여부로 복수
후보의 동률을 깨지 않으며 중첩 테이블의 행도 다른 테이블의 것으로 세지 않습니다.

사용자 v12 TXT에서 Chrome 155.0.8059.84의 두 번 탐색이 모두 HTTP 200으로 끝나고
브라우저가 종료된 것을 확인했습니다. 이미지 저장과 DB 쓰기는 없었습니다.
두 페이지 모두 다음 구조였습니다.

- 선택된 목록은 id 속성이 없는 TABLE로 `.ub-content` 22행과 번호·제목·작성자·날짜 필드가 각각 22개였습니다.
- 부가 목록은 id 속성이 있는 TABLE로 일반 테이블 행 19개가 있었지만 `.ub-content`와 작성자 필드는 없었습니다.
- 페이지마다 일반 게시글 20개와 제외 행 2개가 있었으며, 제외 사유는 첫 행 `non_numeric`, 둘째 행 `pinned`였습니다.
- 두 페이지의 일반 게시글은 총 40개로 중복 없이 글번호 내림차순이었고 제목·작성자·표시 시각이 모두 있었습니다.
- 페이지마다 유효한 이동 후보 17개가 관찰됐고 `javascript:` 링크 16개는 거부됐습니다.
  첫 페이지에서 실제 관찰한 같은 검색 범위의 다음 페이지 링크로 두 번째 페이지를 읽었습니다.

이 결과는 목록 선택과 두 페이지 이동의 근거입니다. v12의 `non_numeric` 행이 안전한 제외
행이라는 근거는 부족하므로 이 보고서만으로 감시 기준점을 만들지 않습니다. `inspected_unverified`는
관찰 보고서 생성 상태이며, 행이 완전하거나 이미지 저장이 허용됐다는 뜻이 아닙니다.
원문 제목·작성자·글번호·커서·해시·로컬 경로·사용자 로그는 이 문서에 옮기지 않습니다.

## v13의 구조 검증과 행 분류

목록의 `site_verified`는 검토한 검색 구조에만 적용합니다. 범위는 추가 필터가 없는
`normal / comic_new6 / ai / search_subject_memo`이며, 새 관찰에서 유일한 본문 테이블과
부가 테이블의 소유 관계·행과 필드 수·일반 게시글의 필수 값을 다시 대조합니다.
실사이트의 행 수를 항상 22개로 고정하지는 않습니다. 다른 검색 범위나 구조가 달라진 페이지는
미검증 상태로 남습니다. 본문의 기존 `site_verified`와 목록의 구조 검증은 별개입니다.

번호가 정확히 `설문`이고 제목 링크와 행이 직접 소유한 전체 링크가 동일한 `javascript:`
링크 하나일 때만 새 관찰에서 `survey`로 분류합니다. 링크를 실행하거나 코드 내용으로
의미를 추측하지 않습니다. 정확한 공지·광고 표시와 이 설문 근거는 안전한 제외로 취급하지만,
알 수 없는 비숫자·필드 충돌·번호/링크 불일치·모호한 행은 `rows_complete: false`로 남깁니다.
구조가 검증됐어도 행이 불완전하면 기준점을 만들거나 완료 지점을 전진하지 않습니다.

표시 시각이 `13:00`처럼 보이면 원문 그대로 기록하며 날짜나 시간대를 추정하지 않습니다.
공유 보고서는 쿠키·인증 헤더·로컬 경로를 제외하고 실제 과거 커서를 해시로 표시합니다.
기존 v12 공유기의 쿼리 유형 진단은 `search_pos`의 `empty` 같은 분류값까지 해시해 버렸습니다.
따라서 해당 진단의 해시를 실제 커서 값이나 과거 검색 구간이 있었다는 증거로 해석하지 않습니다.
v13은 지정한 진단 위치의 허용된 분류값만 원문 분류로 보존하며 실제 커서는 계속 해시로 가립니다.

## v17 로컬 상태 화면과 주기적 목록 발견

`monitor`는 로컬 상태 화면을 열고 정지 상태에서 기다립니다. 화면을 열기만 해서는 사이트
요청이나 감시가 시작되지 않으며 사용자가 시작을 선택해야 합니다. 시작·일시정지·재개·중지·
종료를 제공하고 현재 상태·최근 확인·다음 확인·새 후보 수와 검토 사유를 표시합니다.
사용자 실행 절차는 ZIP 안의 TXT 하나로 제공합니다.

0.4.0-beta.2부터 감시를 시작할 때 같은 감시 범위에서 직전에 끝난 목록 검사와 본문 확인
기록을 대조합니다. 목록 검사와 브라우저 종료가 확인됐고 아직 본문을 확인할 차례라면,
저장된 대기 시간이 지난 뒤 미시도 글 한 건을 확인합니다. 이 근거가 없는 이전 버전의
기록에서는 목록부터 확인합니다. 발견한 후보와 기존 파일은 그대로 사용할 수 있습니다.

`monitor-resume-once --work-root <감시 폴더>`는 이 감시의 남은 본문 확인 차례를 한 번 실행하고
종료합니다. 자동 확인할 차례가 없거나 이미 다른 작업이 처리했으면 목록을 새로 요청하지 않습니다.
일반 감시와 같은 대기 시각을 따르며, 남은 대기가 60초를 넘으면 결과에 다음 시각을 남깁니다.
결과 TXT의 `monitor_resume_completed`는 본문을 확인한 경우입니다. 글이 삭제돼 서버가
404 또는 410을 반환하면 `monitor_resume_unavailable`로 기록하고 그 글의 확인을 마칩니다.
같은 기록으로 다시 실행하면 `monitor_resume_no_slot`이 표시됩니다.

검증한 검색 범위는 추가 필터가 없는 `normal / comic_new6 / ai / search_subject_memo`이며
브라우저는 headless Chrome입니다. 동일한 `watch.sqlite`를 쓰지만 감시 이름이 `목록 감시`인
새 범위를 사용합니다. 기존 `검색 감시 시험`의 후보 6개·상세 관찰·고정 저장 허가와 기존
이미지는 유지하며, 예전 시험의 오래된 완료 지점을 새 감시에 가져오지 않습니다.

새 범위의 최초 유효 시작은 지금부터의 기준점을 기록하고 기존 글을 후보로 추가하지 않습니다.
이후 중지·화면 종료·프로그램 재시작은 이 범위의 기존 기준점과 후보를 유지합니다. 구간 상한이나
겹침 부족·알 수 없는 행·구조 변경 때문에 완료할 수 없으면 후보와 미확인 근거를 남기고 검토
대기로 멈춥니다. 화면에는 기준점 초기화·과거 수집·누락 구간 자동 재탐색 기능이 없습니다.

확인마다 최신 첫 페이지에서 시작해 실제로 관찰한 같은 검색 범위의 유일한 인접 링크만 따라
최대 두 페이지를 읽습니다. 각 확인은 기존 한 주기 관찰과 같은 기준점·행 완전성·정확한 겹침
규칙으로 커밋하고 자신의 headless 브라우저를 안전하게 닫습니다. 일시정지·중지는 두 번째
페이지 탐색 전에 중단 여부를 확인합니다. 이미 실행 중인 페이지 탐색은 즉시 강제 중단하지
않으므로 화면은 종료가 끝날 때까지 일시정지 중·중지 중 상태를 표시할 수 있습니다.

간격은 정지 상태에서만 60~300초로 설정해 로컬 JSON에 보존합니다. 앞 확인 종료 후의
설정 간격·이미 커밋한 실행 가능 시각·같은 DB의 서비스 공통 대기 중 가장 늦은 시각을 지킵니다.
간격을 늘렸을 때도 이전 종료 시각부터 새 간격을 적용하며 이미 보존한 대기를 줄이지 않습니다.
429·503의 서버 대기는 `Retry-After`에 따라 기다립니다. 다른 전송 오류·불완전한 탐색이나
401·403·404·410 차단은 자동 반복으로 넘기지 않고 검토 대기로 멈춥니다. 최소 여유 공간
256MiB 조건을 확인하며 부족한 디스크에 관찰을 계속 쌓지 않습니다.

앱이 열린 동안 별도 목적의 프로세스 잠금을 유지해 같은 감시 화면의 중복 실행을 막습니다.
탐색·자격 확인·커밋에는 기존 검색 범위의 네트워크 잠금을 공유하고 대기 중에는 놓습니다.
따라서 이전 후보 상세·네이티브 저장 명령이 대기 틈에 같은 보호를 사용할 수 있으며 요청을
동시에 시작하지 않습니다. 기존 잠금의 키 형식은 유지합니다. UI 요청 스레드는 상태와 제어만
다루고 작업 스레드가 자신의 SQLite 연결과 Playwright 수명을 관리합니다.

화면 서버는 `127.0.0.1`의 임의 포트와 비밀 경로를 사용합니다. Host·Origin·제어 헤더와
요청 크기를 확인하고 CORS를 열지 않습니다. CSP와 `textContent`로 로컬 화면을 구성하며
비밀 URL·쿠키·원문 제목·작성자·커서·로컬 원본 경로를 상태 로그에 넣지 않습니다.
종료는 진행 중인 작업과 소유 브라우저의 안전한 종료를 기다린 뒤 앱과 결과 TXT로 마칩니다.
v17 자동화와 사용자 두 주기 결과는 [검증 기록](validation.md)에 남겼습니다. 사용자 환경의
장시간 감시·일시정지/재개 수동 조작·재시작 후 보존은 아직 인수하지 않았습니다.

## v18 정지한 화면에서 기존 후보 내용 확인

`RUN_MONITOR.cmd`의 같은 로컬 화면에서 정지 상태일 때 `후보 내용 확인`을 선택합니다.
이 기능은 현재 `목록 감시` 범위의 영구 후보와 기존 최초 기준점을 사용합니다. 한 번 누를 때
아직 상세 시도가 없는 후보를 최대 두 개 확인하며, 목록을 새로 읽거나 다른 감시 범위의 후보를
가져오거나 기준점을 초기화하지 않습니다. 기준점·미시도 후보가 없으면 새 탐색을 시작하지
않습니다. 기존 `검색 감시 시험`의 후보·상세·고정 저장 허가·저장 파일은 유지합니다.

확인은 전용 headless Chrome에서 진행하므로 사용자는 다른 작업을 계속할 수 있습니다.
목록 감시와 같은 작업자·네트워크 잠금을 사용해 동시에 탐색하지 않으며 앞 확인 종료 후
최소 60초·기존 서비스 공통 대기·`Retry-After`를 지킵니다. 시도 시작은 탐색 전에 DB에
기록하고 완료·실패·중단 기록이 있는 후보를 자동 재시도하지 않습니다. 중지·종료는 진행 중인
확인과 소유 브라우저의 안전한 종료를 기다리며 확인을 마친 뒤 목록 감시를 자동 재개하지 않습니다.

로컬 화면과 종료 TXT에는 상세 대기·완료·실패 수, 익명 행의 작성 시각 비교와 수집 대상 본문
이미지 개수를 표시합니다. 원문 제목·작성자·글번호·URL·이미지 경로는 이 표에 표시하지 않습니다.
시각 판정은 `at_or_after_baseline`·`before_baseline`·`unknown`으로 구분하며 기준점 이후라고
해서 저장을 승인하지 않습니다. 이미지 작업 등록·네이티브 저장·다운로드는 실행하지 않습니다.
세부 시각·본문 검사와 차단 처리는 아래 기존 후보 확인과 같은 규칙을 사용합니다.

사용자 확인은 압축을 풀고 `RUN_MONITOR.cmd`를 연 뒤 `후보 내용 확인`을 한 번 선택하면 됩니다.
정지 상태로 돌아오면 `프로그램 종료`를 눌러 자동으로 열린 TXT를 전달합니다. 절차는 ZIP 안의
TXT 하나에 정리하며 별도 명령 입력이나 새 목록 감시 실행은 요구하지 않습니다.

## 두 주기로 제한한 목록 감시

`watch-test`는 Windows의 전용 headless 브라우저에서 최대 두 주기만 실행하고 종료합니다.
첫 유효 관찰은 최신 1페이지의 정확한 게시글 ID로 `new` 기준점을 만들고 기존 글을 후보로
등록하지 않습니다. 기준점이 이미 있으면 각 주기는 최신 1페이지에서 다시 시작해 실제로
관찰한 같은 검색 범위의 인접 링크만 따라 최대 두 페이지를 읽습니다.

다음 주기는 앞 관찰이 끝난 뒤 최소 60초가 지난 시각부터 가능합니다. 고정 시각을 맞추기
위해 밀린 관찰을 연속 실행하지 않습니다. 다음 실행 가능 시각은 DB에 남으므로 재실행으로
대기를 건너뛰지 않습니다. 동일 DB·검색 범위의 OS 잠금을 자격 확인부터 탐색과 커밋까지
유지하고, 경쟁 실행은 새 탐색을 시작하지 않습니다. 프로세스가 종료되면 OS가 잠금을 해제합니다.
탐색 전과 종료 처리에서 서비스 대기를 먼저 보존해 취소 후 즉시 재탐색하는 것을 막습니다.
저장된 종료 시각·대기 시각·간격이 없거나 모순되면 탐색을 시작하지 않습니다.

429·503은 `Retry-After`와 최소 간격 중 늦은 시각을 감시 상태와 같은 DB의 서비스 공통
대기에 보존합니다. 401·403·404·410은 수동 검토가 필요한 차단 상태로 남기며 자동 해제하지
않습니다. 네트워크 오류·구조 오류·불완전한 구간도 상태와 근거를 기록하고 시험을 중단합니다.
이 실행기는 무한 반복 스케줄러가 아닙니다.

## 정확한 완료 지점과 미확인 구간

`watch_planner.plan_scan`은 합성 fixture 또는 명시적으로 허용한 위 실사이트 구조만 처리합니다.
브라우저를 실행하거나 이미지를 저장하지 않으며 다음 규칙을 적용합니다.

- 이전 완료 지점의 정확한 ID를 다시 찾고 한 페이지를 더 겹쳐 읽어야 구간을 완료합니다.
  최대 글번호만으로 완료를 선언하지 않으며, 실사이트에서는 링크가 없다는 이유로 마지막 페이지로 판정하지 않습니다.
- 상한 전에 기준점에 도달하지 못하거나 추가 겹침이 부족하면 발견 후보·관찰·후속 커서와 미확인 사유를 보존합니다.
  마지막 완료 기준점은 유지합니다. 두 페이지를 읽었다는 사실만으로 전체 구간 확인을 선언하지 않습니다.
- 행의 정체성·필수 필드·내림차순·페이지 이동이 불명확하면 기준점을 전진하지 않습니다.
  `search_pos` 변경만으로 다음 과거 구간임을 확정하지 않습니다.
- 새로 보인 목록 행은 실행 이후 작성됐다는 증거가 아닙니다. 후보의 `requires_published_at_filter`와
  최초 기준 시각을 보존합니다. 아래 상세 시험의 시각 비교를 통과하더라도 본문 구조 검증과
  이미지 저장 작업자 연결이 별도로 필요합니다.

실사이트에서 끝을 입증하는 규칙과 미확인 구간 자동 재탐색은 아직 연결하지 않았습니다.

## 기존 후보의 상세 시각과 본문 확인

`candidate-test`는 v13이 사용한 같은 작업 루트의 `watch.sqlite`를 열고 이미 기록한 기준점과
후보를 재사용합니다. Windows 실행기의 공통 작업 루트는 `%LOCALAPPDATA%/ImageMonitorWatch`입니다.
목록을 새로 탐색하거나 기준점을 초기화하지 않습니다. 이번 실행은 아직 상세 시도가 없는 후보를
최대 두 개 선택하며, 대상이 없거나 DB·기준점이 없으면 새 탐색 없이 상태만 보고합니다.
사용자 v13의 후보 6개는 기존 로컬 DB에 있으며 원문 후보 정보를 새 ZIP에 넣지 않습니다.

전용 headless Chrome은 선택한 후보의 정규 URL로 한 번 탐색하고 `dcinside.inspect_post`로
기존 본문 DOM과 헤더를 읽습니다. 첨부 링크를 따라가거나 네이티브 저장 창을 조작하지 않습니다.
유일한 헤더와 제목·작성자·날짜 필드가 각각 하나이고 제목과 작성자가 비어 있지 않아야 시각을
판정합니다. `YYYY.MM.DD HH:MM:SS` 또는 같은 전체 날짜의 하이픈 형식을 Asia/Seoul로 해석한
값이 파싱 결과와 일치해야 합니다. 상대 시각·목록 표시 시각·최초 발견 시각으로 대체하지 않습니다.

최초 기준점의 timezone-aware 시각을 마이크로초까지 보존하고 UTC에서 비교합니다. 상세 관찰은
기준 시각보다 이르면 안 되고 작성 시각은 관찰 시각보다 미래이면 안 됩니다. 판정은
`at_or_after_baseline`·`before_baseline`·`unknown`으로 구분합니다. 상세 작성 시각이 기준 시각
이후여도 `save_approved`와 `queue_eligible`은 모두 false입니다. 기존 검증 게시글 외의 본문
프로필은 계속 미검증으로 남으며 시간 판정을 본문·이미지 저장 승인으로 사용하지 않습니다.

두 번째 상세 확인은 앞 관찰 종료 후 최소 60초와 같은 DB의 서비스 공통 대기를 지킵니다.
목록 시험과 같은 범위의 OS 잠금을 공유하고 탐색 전·종료 처리에서 대기를 기록합니다.
401·403은 같은 DB의 후속 상세 확인과 목록 탐색을 막는 검토 상태로 남깁니다. 상세의 404·410은
해당 후보를 사용할 수 없다는 기록만 남기며 다른 후보의 확인은 계속할 수 있습니다.
429·503은 `Retry-After`와 최소 간격을 보존하고 대기로 끝냅니다. 알 수 없는 시각이나 다른
관찰 오류가 생기면 결과를 남기고 이번 시험을 중단합니다.

탐색 전에 DB v5의 `candidate_details`에 시작 기록을 먼저 커밋합니다. 범위의 다섯 필드·
글번호·최초 발견 관찰 ID·기준 시각이 고정되며 관찰 결과는 비공개 JSON으로 완료 기록에 남습니다.
완료·오류·프로세스 중단을 포함해 시도 기록이 있는 후보는 다음 실행에서 자동 재시도하지 않습니다.
미완료 기록은 지우거나 목록을 초기화하지 않고 수동 검토 대상으로 남깁니다.
공유 TXT에는 원문 제목·작성자·글번호·경로 대신 판정과 제한된 구조·개수만 보고합니다.
`posts`·이미지 작업·최종 폴더 계획은 만들지 않습니다.

## 완료 상세 관찰 한 개의 네이티브 저장 시험

`candidate-save-test`는 새 목록이나 새 후보 상세를 수집하지 않고 기존 완료 관찰에서 대상을
선택합니다. v14 사용자 결과의 두 후보는 모두 기준점 이후였으며 첫 후보는 본문 이미지가
없었습니다. 두 번째 후보는 본문 이미지 두 개·첨부 한 개·원본명 대응 `ambiguous` 두 개였습니다.
본문 이미지가 없거나 기준점 이전인 후보는 건너뛰고, 미해결 이미지 없이 1~2개를 관찰한
완료 결과에만 명시적인 `CandidateSavePermit`을 만들 수 있습니다.

허가는 동일한 다섯 범위 필드와 후보 고유키·최초 발견 ID·기준 시각·상세 시도·원문 관찰에 묶입니다.
발견 루트의 `candidate-save-selection.json`이 한 번 선택한 후보와 근거 지문을 고정하므로
재실행으로 다른 게시글을 선택하지 않습니다. 현재 헤더와 정확한 이미지 URL·자연 크기·본문 출현
위치·제외 근거를 최초 검사와 사용자 시작·전경 재개 후마다 대조합니다. 달라지면 저장을 중단하고
검토 상태로 남깁니다. 원본명 대응이 불확실한 이미지는 원본명을 null로 유지합니다.

`candidate_reviewed` 상태는 이 한 후보의 허가를 받는 별도 대기열 연결에만 사용합니다.
`dcinside.SITE_VERIFIED_POST`나 일반 `enqueue_snapshot`의 검증 범위를 넓히지 않습니다.
발견 `watch.sqlite`의 기준점·후보·상세 결과와 이미지 작업 0개 상태를 유지하며, 최초 후보 발견
시각을 보존한 게시글·이미지 작업과 파일은 별도 `ImageMonitorCandidateSave` 작업 루트에 기록합니다.
기존 네이티브 작업자의 실제 우클릭·Windows Save As·완료 판독·검증·확정과 중복 방지를 사용합니다.

같은 OS 감시 범위 잠금을 유지하고 게시글 탐색 전·종료 후에 서비스 대기를 보존합니다.
401·403은 선택 기록의 차단 상태로 후속 목록·상세·후보 저장을 막습니다. 429·503은
`Retry-After`를 따르며, 404·410으로 선택한 글이 없어졌다면 다른 후보로 자동 전환하지 않습니다.
공통 미해결 네이티브 저장이 있으면 새 저장을 시작하지 않으며 후보 모드에 기존 예제의 입력 전
재개 옵션을 적용하지 않습니다. 사용자 절차는 ZIP 안의 TXT 하나로 제공하고 이 모드는 한 게시글
시험으로 종료합니다. v15에서 두 파일 저장·확정을, v16에서 기존 파일 재검증과 이미 종료된
브라우저 확인·미해결 표시 해제를 사용자 환경에서 완료했습니다. 정기 감시가 이 허가를 자동으로
적용하거나 다른 후보를 저장하지는 않습니다.

## v19 목록 감시의 완료 관찰 한 개와 네이티브 저장 연결

사용자 v18 TXT에서 `목록 감시`의 기존 후보 3개가 유지되고 두 후보의 상세 확인이 완료된 것을
확인했습니다. 두 결과 모두 기준점 이후 작성 시각과 본문 이미지 1개·로딩 미완료 0개를
보고했습니다. 이 결과만으로 본문 전체를 전역 검증하거나 저장 승인을 만들지는 않습니다.

별도 `monitor-save-test`와 `RUN_MONITOR_SAVE.cmd`는 같은 DB의 `목록 감시` 범위에서 완료된
상세 관찰 하나를 고정하고, 그 근거와 현재 게시글이 일치하는 한 후보에만 저장 허가를 적용합니다.
후보·상세 시도의 다섯 범위 필드가 정확히 같아야 하며 로딩된 이미지 1~2개·미해결 0개·확인된
기준점 이후 작성 시각과 유일한 헤더·본문이 필요합니다. 현재 헤더와 이미지 URL·자연 크기·출현
위치·제외 근거를 처음 검사와 사용자 시작·전경 재개마다 다시 대조합니다.

발견 루트의 `monitor-save-selection.json`이 선택과 근거를 고정하며 기존
`candidate-save-selection.json`을 재사용하거나 바꾸지 않습니다. 이미지 작업과 파일은 별도
`%LOCALAPPDATA%/ImageMonitorMonitorSave`에 기록하고 이전 `ImageMonitorCandidateSave`의
파일·메타데이터를 유지합니다. 발견 DB의 기준점·후보·상세 기록과 이미지 작업 0개도 유지합니다.
후보가 삭제되거나 근거가 달라지면 다른 후보로 자동 전환하지 않습니다.

실행기는 주 스레드에서 기존 Windows 네이티브 작업자를 사용하며 로컬 감시 화면의 백그라운드
스레드가 저장 창을 조작하지 않습니다. 사용자는 전용 Chrome에서 `저장 시작`을 누르고 완료될
때까지 그 창을 앞에 유지합니다. 기존 우클릭·Save As·완료 판독·Pillow 검증·저널 확정과
세션 공통 미해결 표시·전경 보호를 재사용합니다. 서비스 대기와 접근 차단은 두 후보 선택 경로와
목록·상세 확인에 함께 적용합니다. 목록이나 상세 관찰을 새로 수집하거나 전체 후보의 자동 저장을
시작하지 않습니다.

지원용 `monitor-finish`와 `RUN_MONITOR_FINISH.cmd`는 같은 새 선택·출력 루트에서 완료된
파일과 메타데이터, 전용 브라우저 종료의 근거만 재확인합니다. 새 게시글 탐색·네이티브 입력·
이미지 재저장이 없으며 일반적인 미완료 작업 복구로 확대하지 않습니다. 기본 사용자 시험은
저장 실행기 한 번으로 결과 TXT를 받는 절차이고 완료 정리 실행기를 추가로 요구하지 않습니다.

## v20 기존 저장 결과의 로컬 확인

`RUN_MONITOR.cmd`는 기존 `ImageMonitorMonitorSave`를 저장 결과 루트로 전달합니다. 화면을
열면 정지 상태에서 백그라운드 로컬 확인을 한 번 시작하며, 감시 제어 아래·후보 내용 확인 위의
저장 결과 영역에 검증한 파일과 미리보기를 표시합니다. 아래로 스크롤해야 보일 수 있습니다.
별도 감시 시작·후보 내용 확인·네이티브 저장 시작은 필요하지 않으며 다른 작업을 계속할 수
있습니다. 정지 상태의 `저장 결과 새로 확인`은 기존 결과를 명시적으로 다시 읽습니다.

열람 대상은 `monitor-save-selection.json`의 한 고정 후보와 현재 Windows 세션의 기존
`queue.sqlite`에 묶입니다. 발견 DB와 네이티브 DB를 읽기 전용으로 열고, 선택·허가·완료 작업·
확정 저널·고정 폴더 계획·메타데이터·Pillow 결과·배타적 SHA-256을 대조합니다. 같은 공통
탐색 잠금과 네이티브 저장 잠금을 사용하며 미해결 저장이 있으면 표시하지 않습니다. 누락된
선택·DB·저장 파일을 만들거나 다른 범위·세션·임의 과거 폴더로 대체하지 않습니다.

로컬 파일 확인은 사이트 대기나 접근 차단 중에도 실행할 수 있습니다. 원본 사이트 요청이나
이미지 재다운로드·네이티브 입력·재인코딩·보류 표시 변경·자동 복구는 하지 않습니다. 기존
완료 정리는 같은 파일 검증기를 재사용하지만 이전 완료 보고서와 미해결 표시의 엄격한 확인
조건을 유지합니다. 열람만으로 종료 정리를 대신하거나 표시를 해제하지 않습니다.

검증된 원본 바이트를 파일당 16MiB·전체 32MiB 이내에서 최대 두 개 메모리에 보관합니다.
JPEG·PNG·WEBP·GIF·BMP는 이 범위에서 미리보기를 제공하고 TIFF·한도 초과는 파일 정보만
표시합니다. 로컬 HTTP 서버는 같은 비밀 경로 아래의 임의 32자리 식별자로 메모리 바이트만
전달하며 사용자 경로를 받아 파일을 열지 않습니다. 공유 TXT에는 미리보기 식별자·로컬 경로·
원본 URL·해시를 넣지 않습니다.

개발용 `monitor --save-root`는 선택 옵션입니다. 생략하면 기존 감시 화면 동작을 유지합니다.
이번 사용자 확인은 실행기를 열고 저장 결과 이미지를 본 뒤 `프로그램 종료`를 눌러 열린 TXT를
전달하는 절차이며, 사용자 환경의 새 열람 결과는 별도로 확인합니다.

## v21 완료 상세 관찰의 후보별 연속 저장

`monitor-save-batch`와 `RUN_MONITOR_BATCH.cmd`는 이미 보존된 `목록 감시` 범위의 완료
상세 관찰만 사용합니다. 새 목록·후보 상세를 읽거나 기준점을 초기화하지 않습니다. 후보마다
같은 다섯 범위 필드·최초 발견과 기준점·기준점 이후 작성 시각·유일한 헤더/본문·로딩된 이미지
1~2개와 미해결 0개를 검증해 불변 허가를 만들며, 실제 저장 전 현재 헤더와 원본 URL·크기·
출현·제외 근거를 다시 대조합니다. 전체 갤러리의 저장 프로필을 승격하지 않습니다.

발견 루트의 새 `monitor-save-ledger.sqlite`는 별도 스키마 1입니다. `watch.sqlite`의 스키마 5,
기준점·목록·후보·상세와 이미지 작업 0개는 유지합니다. 기존 v19의 단일 선택과 완료 파일은
읽기 전용으로 재검증한 뒤 새 이력에 원자적으로 완료 등록하며, 그 이전 출력 루트에 저장
작업자를 다시 실행하지 않습니다. 새 시도마다 `ImageMonitorBatch/tasks/<작업ID>/session-<세션>`
아래 한 게시글 전용 DB와 출력을 사용합니다.

이력의 `planned` 작업은 네이티브 작업자를 부르기 전에 `started`로 커밋합니다. 한 실행의 새
네이티브 시도는 최대 두 번입니다. 중단된 `started`나 `needs_review`는 근거 대조 없이 다시
실행하지 않으며 미해결 작업이 있으면 새 네이티브 시도도 멈춥니다. 서비스 최소 대기·서버의
`Retry-After`·접근 차단과 탐색 진행이 불명확한 상태는 같은 버전의 목록·상세·단일 저장에도
적용합니다. 404/410은 입력 전 중단·빈 네이티브 DB·브라우저 종료·보류 없음이 모두 입증됐을
때에만 해당 후보의 종료로 기록하고 다음 후보를 처리합니다.

기본 사용자 절차는 `RUN_MONITOR_BATCH.cmd`를 열고 새 전용 Chrome의 `저장 시작`을 누른 뒤
저장 완료까지 그 창을 앞에 유지해 자동으로 열린 결과 TXT를 전달하는 것입니다. 현재 사용자
자료에서는 이전 완료 한 건을 건너뛰고 남은 완료 상세 관찰 한 건을 저장하므로 목록·상세
확인을 반복할 필요가 없습니다. 지원용 `RUN_MONITOR_BATCH_FINISH.cmd`는 이미 완료된 파일의
읽기 전용 재검증·정확한 전용 브라우저 정상 종료·보류 근거 대조만 수행합니다. 다른 Windows
세션의 미해결 작업을 정리하거나 미완료 이미지를 다시 저장하지 않습니다.

기존 `RUN_MONITOR_SAVE.cmd`의 한 후보 고정과 v20의 이전 완료 파일 미리보기는 유지합니다.
새 배치 저장 결과는 아직 그 미리보기에 표시하지 않습니다. 이 한정 배치는 정기 목록 감시가
모든 새 후보의 이미지를 계속 저장하는 기능과 구분하며 실제 사용자 인수는 새 TXT로 확인합니다.

## 영구 기록과 개발 명령

별도 `watch.sqlite`의 `watch_*` 테이블에 기준점·후보·관찰·미확인 이력을
저장합니다. 세대 번호를 비교하는 하나의 트랜잭션으로 기록하므로 오래된 작업이 완료 지점을
덮지 못합니다. 재시작 후에도 후보와 기존 기준점은 유지됩니다. 이 시험은 `posts`나 이미지
작업을 생성하지 않으며 본문 저장 작업자·네이티브 저장·폴더 계획과 연결하지 않습니다.
목록의 불완전한 작성자·시각으로 최종 저장 경로를 미리 고정하지 않습니다.

개발자는 Windows에서 다음 명령으로 한정 시험을 실행할 수 있습니다.

```powershell
uv run --locked --extra windows image-monitor watch-test --work-root C:/IMWatch --browser chrome
uv run --locked --extra windows image-monitor monitor --work-root C:/IMWatch
uv run --locked --extra windows image-monitor monitor --work-root C:/IMWatch --save-root C:/IMMonitorSave
uv run --locked --extra windows image-monitor candidate-test --work-root C:/IMWatch --browser chrome
uv run --locked --extra windows image-monitor candidate-save-test --watch-root C:/IMWatch --work-root C:/IMCandidateSave --browser chrome
uv run --locked --extra windows image-monitor monitor-save-test --watch-root C:/IMWatch --work-root C:/IMMonitorSave --browser chrome
uv run --locked --extra windows image-monitor monitor-save-batch --watch-root C:/IMWatch --legacy-root C:/IMMonitorSave --work-root C:/IMMonitorBatch
```

최근 후보 저장 시험은 `watch-images`로 실행합니다. 예시의 `--legacy-root`는 같은 후보를
다시 저장하지 않도록 이전 후보 시험의 작업 폴더를 가리킵니다. 저장이 끝난 뒤 결과 기록만
중단됐을 때는 같은 세 경로로 `watch-images-finish`를 실행해 기존 파일과 기록을 대조할 수 있습니다.

```powershell
uv run --locked --extra windows image-monitor watch-images --watch-root C:/IMWatch --legacy-root C:/IMCandidateSave --work-root C:/IMWatchImages
```

저장 완료 후 프로그램을 새로 열어 마지막 게시글의 파일을 재검증하려면 같은 경로로
`watch-images-check`를 실행합니다. `watch_images_verified`는 현재 파일을 저장 당시의 기록과
대조한 결과입니다. `watch_images_no_saved_files`는 확인할 완료 기록이 없을 때,
`watch_images_review`는 파일이나 기록에 확인할 사항이 있을 때 표시됩니다.

한정 `watch-test` CLI는 주기 수나 대기 간격을 바꾸는 옵션을 제공하지 않습니다. `monitor`의
간격은 정지한 로컬 화면에서만 설정합니다. 사용자용 실행기와 결과 확인은
위 TXT 안내에만 정리합니다. 실제 사이트를 읽지 않는 새 DB 합성 통합 시험도 유지합니다.

```powershell
uv run --locked image-monitor watch-demo --db ./reports/watch-demo.sqlite
```

합성 시험은 첫 기준점 → 페이지 상한 중단 → DB 재연결 → 정확한 기준점과 겹침 확인을
검사하며 후보 2개·관찰 3개·과거 미확인 이력 1개를 남기고 이미지 작업은 만들지 않습니다.
DB v1/v2/v3/v4의 정확한 알려진 스키마만 원자적으로 v5에 추가 마이그레이션하며 읽기 전용
조회는 기존 버전을 바꾸지 않습니다. v5는 상세 시도 기록을 추가하며 기존 목록·후보·이미지
확정 기록과 사용자 파일도 유지합니다. 이전 v13 실행 파일은 v5 DB를 거부하므로 같은 DB에
버전이 다른 실행기를 섞지 않습니다. v14의 실제 브라우저 자동화와 사용자 상세 관찰은
[검증 기록](validation.md)에 남겼습니다. v15 저장·v16 완료 정리의 사용자 인수와 v17 주기
목록 감시의 자동화·사용자 검증은 구분합니다. v18의 같은 화면에서 실행하는 내용 확인도
기존 개별 CLI와 구분해 검증했습니다. v19의 별도 후보 저장 연결도 모든 새 후보의 이미지
자동 저장으로 확대하지 않습니다.
