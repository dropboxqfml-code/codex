# 실제 사이트 DOM 확인 기록

본문과 네이티브 저장의 실사이트 검증 대상은 일반 갤러리 `comic_new6`의 게시글
`7036949` 한 개입니다. 별도로 사용자 v12 결과에서 같은 갤러리의 `ai` 제목+내용 검색
목록 두 페이지 구조를 확인했습니다. 본문 검증과 목록 구조 검증의 범위는 구분합니다.
검사한 게시글 URL은 설계안의 공개 예제이며, 새로 관찰한 글번호·원문 제목·작성자·IP
표시값·커서·해시·로컬 경로와 사용자 결과 로그는 저장소에 넣지 않습니다.

## 2026-11-15: 클라우드 탐색 연결 실패

대상 검색 URL:

`https://gall.dcinside.com/board/lists/?id=comic_new6&s_type=search_subject_memo&s_keyword=ai`

프로젝트의 잠금 의존성에 포함된 Playwright와 설치된 `/usr/bin/chromium`을 사용해,
새 임시 브라우저 컨텍스트에서 일반 페이지 탐색을 한 번 시도했습니다.

결과는 `Page.goto: net::ERR_TUNNEL_CONNECTION_FAILED`입니다. HTTP 응답과 사이트 DOM을
받기 전의 연결 실패이므로 HTTP 403/429, 사이트 접근 차단 또는 DOM 변경으로 판정하지 않습니다.
다른 프로토콜·프록시·접근 경로나 정책 변경으로 재시도하지 않았습니다.

이 클라우드 실행에서는 본문 선택자·헤더·첨부 목록이나 파일 식별자를 확인하지 못했습니다.
아래 실사이트 근거는 이후 사용자 Windows에서 생성한 읽기 전용 검사 결과에서 확보했습니다.

## 사용자 Windows v7: 본문과 첨부 대응 근거

사용자 TXT에서 Chrome 155.0.8059.84의 예제 게시글
`https://gall.dcinside.com/board/view/?id=comic_new6&no=7036949` 탐색이 HTTP 200으로
완료되고 검사 브라우저가 종료된 것을 확인했습니다. 이미지 저장과 대기열 변경은 없었습니다.

- `.write_div` 한 개에서 일반 이미지 4개를 로딩·decode했고 `.written_dccon` 이미지 1개를 제외했습니다.
- `.appending_file`에 공개 첨부 목록 4개와 완전한 표시 파일명이 있었습니다.
- `.view_head`는 없고 `.gallview_head`가 한 개였습니다. 그 안의 `.title_subject`,
  `.gall_writer`, `.gall_date`도 각각 한 개여서 헤더 선택자를 수정했습니다.
- 본문 `https://dcimg3.dcinside.co.kr/viewimage.php`의 `id`, `no`와 첨부
  `https://image.dcinside.com/download.php`의 `no`, `f_no`를 구분했습니다.
  두 엔드포인트의 `no` 값 해시가 네 경우 모두 유일하게 일치했습니다.
- `data-fileno`나 `f_no` 값으로 본문과 첨부를 대응하지 않습니다. 파일명·개수·순서도
  원본명 대응의 근거로 사용하지 않습니다.

## 사용자 Windows v8: 헤더와 원본명 대응 확인

수정 후 사용자 결과에서 제목·작성자·공개된 부분 IP 표시·작성 시각이 읽히는 것을 확인했습니다.
헤더는 유일한 `.gallview_head` 안에서 읽었고, 작성 시각은 Asia/Seoul 기준 2026-11-11로
해석됐습니다. IP는 보이는 `.ip` 요소의 표시값만 사용하며 `data-ip`로 대체하지 않습니다.

본문 일반 이미지 4개가 모두 공개 첨부 목록의 이름과 `matched`로 대응됐고,
원본명 출처는 `attachment_list_dom`입니다. 본문 디시콘 1개는 제외되고 미해결 로딩은 0개였습니다.
관찰된 표시 URL 해시·공통 `no` 식별자 해시·식별자 속성 힌트는 v7과 v8 사이에서 유지됐습니다.
속성 힌트의 동일성은 기록으로 보존하며 별도의 매칭 규칙으로 사용하지 않습니다.

이 검사는 DOM과 이미지 로딩을 확인한 읽기 전용 관찰입니다. 실제 게시글 이미지를 네이티브
저장 창으로 저장하는 연결의 사용자 인수 시험이나 정기 감시 실행을 입증하지는 않습니다.

## 사용자 Windows v10: 단일 게시글 전체 저장 인수 완료

v9에서는 첫 WEBP 파일이 확정된 뒤 두 번째 작업이 첫 조작 전 전경 검사에서 중단됐습니다.
후속 v10 사용자 TXT에서 Chrome 155.0.8059.84의 입력 전 복구가 정확한 이전 작업을 재개하고
기존 파일을 보존한 것을 확인했습니다. 이미 확정된 파일 한 개는 로컬 복구가 건너뛰었으며,
기존 `001.webp`를 다시 저장하지 않고 `002.webp`·`003.webp`·`004.webp`를 저장·검증·확정했습니다.

보고서 스키마 2의 `post_completed`·`complete`·종료 코드 0, 관찰 4개·완료 4개·미해결 0개를
확인했습니다. 미해결 표시가 해제됐고 브라우저 종료 뒤 공통 미해결 표시와 오류 유형도 없었습니다.
따라서 이 게시글의 전체 네이티브 저장 연결과 입력 전 재개는 사용자 인수 완료로 기록합니다.
다른 일반·마이너·미니 갤러리와 게시글, 검색 목록이나 정기 감시의 검증 근거로 확대하지 않습니다.
원문 로그·로컬 경로·실제 파일 해시·작성자와 이미지 크기는 이 기록에 포함하지 않습니다.

## 사용자 Windows v11: 검색 목록의 중복 컨테이너

Chrome 155.0.8059.84로 기본 검색 첫 페이지를 한 번 읽어 HTTP 200과 브라우저 종료를
확인했습니다. 관찰 보고서는 생성됐지만 `.gall_list`가 두 개여서 목록 상태는
`ambiguous_list`였으며 추출한 게시글과 대기열 변경은 없었습니다.

두 후보 모두 TABLE이고 한 후보에만 id 속성이 있었습니다. 넓은 선택자 범위에서
`.ub-content` 행과 작성자 필드는 각각 22개, 번호·제목 링크·날짜 필드는 각각 42개였습니다.
별도 목록을 함께 선택했을 가능성을 확인하고, 직접 소유한 본문 행 구조로 유일한 테이블을
고르도록 수정했습니다. 원문 id 값이나 테이블 순서를 선택 근거로 사용하지 않습니다.

페이지 이동 링크 33개 중 32개는 URL 검증에서 거부됐습니다. 기존 보고서의 URL 모양에는
`id/page/search_pos/s_type/s_keyword` 키만 있어 잘못된 값은 특정하지 못했습니다.
빈 커서 정규화와 값 없는 거부 유형 진단을 추가했으며 원인이나 수정 효과는 다음 관찰로 확인합니다.
원문 로그·로컬 경로·실제 글 제목·작성자·쿼리 값은 이 기록에 넣지 않습니다.

## 사용자 Windows v12: 목록 선택과 두 페이지 이동 확인

Chrome 155.0.8059.84에서 같은 검색 범위의 최신 첫 페이지와 실제로 관찰한 다음 페이지
링크를 따라 두 번째 페이지까지 읽었습니다. 두 탐색 모두 HTTP 200이었으며 브라우저는
정상 종료했습니다. 이미지 저장과 DB 쓰기는 없었습니다.

- 두 페이지 모두 id 속성이 없는 본문 TABLE을 유일하게 선택했습니다. 직접 소유한
  `.ub-content` 22행과 번호·제목·작성자·날짜 필드는 각각 22개였습니다.
- id 속성이 있는 부가 TABLE에는 일반 테이블 행 19개와 번호·제목·날짜 필드가 있었지만,
  `.ub-content`와 작성자 필드는 없었습니다. 원문 id나 테이블 순서를 선택 근거로 사용하지 않습니다.
- 각 페이지에서 일반 게시글 20개를 읽고 첫 행 `non_numeric`, 둘째 행 `pinned`를 제외했습니다.
  두 페이지의 40개 게시글은 중복 없이 내림차순이었으며 제목·작성자·표시 시각이 모두 있었습니다.
- 페이지마다 같은 범위의 유효 이동 후보 17개를 읽었고 `javascript:` 링크 16개를 거부했습니다.
  첫 페이지에서 선택한 실제 인접 링크와 두 번째 관찰의 페이지가 일치했습니다.

따라서 v12의 본문 목록 선택과 같은 범위의 두 페이지 이동은 실사이트 근거를 확보했습니다.
그러나 `non_numeric`만으로 첫 행을 안전하게 제외할 수는 없으며 이 보고서를 완전한 행
관찰이나 감시 기준점으로 소급 승인하지 않습니다. v13은 새 관찰에서 번호가 정확히 `설문`이고
제목과 행 전체가 직접 소유한 링크 하나가 동일한 `javascript:` 링크일 때만 `survey`로
분류합니다. 다른 비숫자 행은 계속 불완전한 행으로 남깁니다.

v12 공유 보고서에는 쿼리 값 유형의 `search_pos` 분류값까지 해시한 진단 오류가 있습니다.
그 해시는 실제 커서나 과거 검색 위치를 입증하지 않습니다. 원문 값을 추측하거나 이 진단으로
범위가 바뀌었다고 판정하지 않습니다.
v13은 지정한 진단 위치에서 허용된 분류값만 보존하도록 수정했으며 실제 커서는 계속 해시로 가립니다.

## 현재 코드에 반영한 검증 범위

본문의 `site_verified`와 이미지 저장 대기열 등록을 허용하는 실사이트 대상은
`normal / comic_new6 / 7036949` 하나입니다. 다음 조건도 모두 충족해야 합니다.

- 본문과 `.gallview_head`가 각각 한 개이고 제목·작성자·날짜 요소의 개수도 각각 한 개.
- 제목과 작성자가 비어 있지 않고 작성 시각을 유효한 Asia/Seoul 시각으로 해석할 수 있음.
- 본문 관찰 중 이미지 노드·순서·개수가 바뀌지 않았으며 미해결 이미지가 없음.

다른 게시글·갤러리는 `unverified`로 남으며 대기열 등록을 허용하지 않습니다.
본문을 찾지 못하거나 중복되면 페이지 전체 이미지 수집으로 대체하지 않습니다.

목록의 `site_verified`는 추가 필터 없는
`normal / comic_new6 / ai / search_subject_memo`의 검토한 구조에 한정합니다.
새 관찰에서 두 테이블의 직접 소유 관계·유일한 본문 선택·필드 개수·일반 게시글 필수 값이
맞아야 하며, 행 수 자체를 22개로 고정하지 않습니다. 구조 승격과 행 완전성은 별도 조건입니다.
행이 불완전하면 한정 감시 시험도 기준점을 생성하거나 완료 지점을 전진하지 않습니다.
목록 검증은 게시글 본문이나 이미지 저장 대상을 넓히지 않습니다.

검증된 엔드포인트의 `no`는 네임스페이스가 있는 SHA-256 식별자로 보존합니다.
해당 게시글이 `site_verified`일 때는 그 식별자를 작업 키로 사용하고, 같은 리소스의 URL 변형은
모든 본문 위치·표시 URL·매칭 근거를 함께 남기며 한 작업으로 묶습니다. 확인되지 않은 리소스나
합성 fixture는 정확한 표시 URL의 해시를 사용하는 기존 규칙을 유지합니다.
원본명 대응이 불확실하다는 이유만으로 정상 본문 이미지 작업을 차단하지 않습니다.

이 작업 키는 네이티브 선택 조건을 완화하지 않습니다. 저장 연결은 본문 소속, 준비한 이미지의
정확한 `currentSrc`, 예상 헤더와 게시글 정체성을 다시 확인해야 합니다.
위 한 게시글의 저장은 사용자 인수 시험을 통과했습니다. v13의 두 주기 한정 목록 시험은
별도 DB의 기준점·후보·미확인 구간만 기록하며, 사용자 실사이트 실행과 새 자동화 검증 결과는
별도로 확인해야 합니다. 계속 실행하는 정기 스케줄러와 새 글 이미지 자동 저장은 아직 없습니다.
