# 실제 사이트 DOM 확인 기록

전역 본문 저장 프로필과 기본 `save-post`의 실사이트 검증 대상은 일반 갤러리 `comic_new6`의
게시글 `7036949` 한 개입니다. 별도로 사용자 v12 결과에서 같은 갤러리의 `ai` 제목+내용 검색
목록 두 페이지 구조를 확인했고, v13 결과에서 기준점 저장과 두 번째 주기의 새 후보 6개 기록을
확인했습니다. v14에서는 저장된 후보 두 개의 작성 시각과 본문을 읽기 전용으로 관찰했고,
v15의 한 후보 전용 허가 경로에서는 JPEG·PNG 두 파일의 저장·검증·최종 확정을 보고했습니다.
마지막 종료 확인은 중단됐지만 v16에서 기존 두 파일을 재검증하고 브라우저 종료와 미해결 표시
해제를 확인했습니다. v17에서는 로컬 목록 감시의 두 주기·새 후보 3개와 정상 종료를,
v18에서는 같은 화면에서 기존 후보 두 개의 작성 시각·본문 이미지 관찰과 정상 종료를
확인했습니다. 전역 저장 프로필 검증과 목록 발견·후보 상세 관찰·개별 후보 허가의 범위는 구분합니다.
검사한 게시글 URL은 설계안의 공개 예제이며, 새로 관찰한 글번호·원문 제목·작성자·IP
표시값·커서·해시·로컬 경로와 사용자 결과 로그는 저장소에 넣지 않습니다.

## 2026-11-15: 클라우드 탐색 연결 실패

대상 검색 URL:

`https://gall.dcinside.com/board/lists/?id=comic_new6&s_type=search_subject_memo&s_keyword=ai`

프로젝트의 잠금 의존성에 포함된 Playwright와 설치된 `/usr/bin/chromium`을 사용해,
새 임시 브라우저 컨텍스트에서 일반 페이지 탐색을 한 번 시도했습니다.

결과는 `Page.goto: net::ERR_TUNNEL_CONNECTION_FAILED`입니다. HTTP 응답과 사이트 DOM을
받기 전의 연결 실패이므로 HTTP 403/429, 사이트 접근 차단 또는 DOM 변경으로 판정하지 않습니다.
다른 프로토콜·프록시·접근 경로나 정책 변경으로 재시도하지 않았습니다.

이 클라우드 실행에서는 본문 선택자·헤더·첨부 목록이나 파일 식별자를 확인하지 못했습니다.
아래 실사이트 근거는 이후 사용자 Windows에서 생성한 읽기 전용 검사 결과에서 확보했습니다.

이 검사는 DOM과 이미지 로딩을 확인한 읽기 전용 관찰입니다. 실제 게시글 이미지를 네이티브
저장 창으로 저장하는 연결의 사용자 인수 시험이나 정기 감시 실행을 입증하지는 않습니다.

원문 로그·로컬 경로·실제 파일 해시·작성자와 이미지 크기는 이 기록에 포함하지 않습니다.

별도 목록을 함께 선택했을 가능성을 확인하고, 직접 소유한 본문 행 구조로 유일한 테이블을

페이지 이동 링크 33개 중 32개는 URL 검증에서 거부됐습니다. 기존 보고서의 URL 모양에는

빈 커서 정규화와 값 없는 거부 유형 진단을 추가했으며 원인이나 수정 효과는 다음 관찰로 확인합니다.
원문 로그·로컬 경로·실제 글 제목·작성자·쿼리 값은 이 기록에 넣지 않습니다.

## 사용자 Windows v12: 목록 선택과 두 페이지 이동 확인

Chrome 155.0.8059.84에서 같은 검색 범위의 최신 첫 페이지와 실제로 관찰한 다음 페이지
링크를 따라 두 번째 페이지까지 읽었습니다. 두 탐색 모두 HTTP 200이었으며 브라우저는
정상 종료했습니다. 이미지 저장과 DB 쓰기는 없었습니다.

- 두 페이지 모두 id 속성이 없는 본문 TABLE을 유일하게 선택했습니다. 직접 소유한
  `.ub-content` 22행과 번호·제목·작성자·날짜 필드는 각각 22개였습니다.
- id 속성이 있는 부가 TABLE에는 일반 테이블 행 19개와 번호·제목·날짜 필드가 있었지만,
  `.ub-content`와 작성자 필드는 없었습니다. 원문 id나 테이블 순서를 선택 근거로 사용하지 않습니다.
- 각 페이지에서 일반 게시글 20개를 읽고 첫 행 `non_numeric`, 둘째 행 `pinned`를 제외했습니다.
  두 페이지의 40개 게시글은 중복 없이 내림차순이었으며 제목·작성자·표시 시각이 모두 있었습니다.
- 페이지마다 같은 범위의 유효 이동 후보 17개를 읽었고 `javascript:` 링크 16개를 거부했습니다.
  첫 페이지에서 선택한 실제 인접 링크와 두 번째 관찰의 페이지가 일치했습니다.

따라서 v12의 본문 목록 선택과 같은 범위의 두 페이지 이동은 실사이트 근거를 확보했습니다.
그러나 `non_numeric`만으로 첫 행을 안전하게 제외할 수는 없으며 이 보고서를 완전한 행
관찰이나 감시 기준점으로 소급 승인하지 않습니다. v13은 새 관찰에서 번호가 정확히 `설문`이고
제목과 행 전체가 직접 소유한 링크 하나가 동일한 `javascript:` 링크일 때만 `survey`로
분류합니다. 다른 비숫자 행은 계속 불완전한 행으로 남깁니다.

v12 공유 보고서에는 쿼리 값 유형의 `search_pos` 분류값까지 해시한 진단 오류가 있습니다.
그 해시는 실제 커서나 과거 검색 위치를 입증하지 않습니다. 원문 값을 추측하거나 이 진단으로
범위가 바뀌었다고 판정하지 않습니다.
v13은 지정한 진단 위치에서 허용된 분류값만 보존하도록 수정했으며 실제 커서는 계속 해시로 가립니다.

사용자 환경의 재시작 보존 시험, 후보의 상세 작성 시각 필터·본문 분석과 새 글 이미지 저장은

## 사용자 Windows v14: 기존 후보의 작성 시각과 본문 관찰 완료

Chrome 155.0.8059.84의 후보 상세 시험이 `candidate_test_completed`·`complete`·종료 코드 0으로

설정 간격은 60초였고 오류 유형은 없었으며 소유한 브라우저가 종료됐습니다.
이전 v13 실행에서 저장한 기준점과 후보를 다음 실행에서 다시 사용한 연결도 확인했습니다.

이미지 저장과 이미지 작업 생성은 0개입니다. 따라서 이 결과로 다른 게시글의 저장 프로필을
승격하거나 후보 이미지의 네이티브 저장을 승인하지 않습니다. 실제 후보의 글번호·제목·작성자·
URL·커서·해시·로컬 경로와 사용자 원문 로그는 옮기지 않습니다.

## 사용자 Windows v15: 후보 이미지 두 개 확정과 종료 확인 중단

Chrome 155.0.8059.84의 한 후보 전용 저장 시험은 HTTP 200으로 탐색했고 이미지 작업
