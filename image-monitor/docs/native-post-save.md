# Chrome 단일 게시글 네이티브 저장 작업자

사용자 실행 절차는 ZIP 안의 `WINDOWS_TEST_GUIDE.txt`에만 정리합니다.
`RUN_POST_SAVE_TEST.cmd`는 검증한 공개 예제 게시글 한 개를 전용 Chrome으로 열고,
사용자가 게시글·이미지 수·저장 위치를 확인해 `저장 시작`을 누른 뒤 저장합니다.
개인 프로필에 연결하지 않으며 검색·정기 감시나 다른 게시글 저장을 시작하지 않습니다.

## v15의 완료 관찰에 묶인 후보 한 게시글

별도 `candidate-save-test`는 v14가 기록한 완료 상세 관찰에서 후보 한 개를 선택합니다.
`CandidateSavePermit`은 같은 검색 범위·후보 고유키·최초 발견 관찰 ID·불변 기준 시각·
완료 상세 시도와 그 비공개 스냅샷을 함께 검증합니다. 작성 시각이 기준점 이후이고 헤더·본문이
각각 하나이며 미해결 이미지 없이 로딩된 이미지가 1~2개인 경우만 이 시험에 포함합니다.
사용자 v14의 이미지 없는 첫 후보는 건너뛰며 이미지 두 개를 관찰한 후보가 이 조건의 대상입니다.

발견 루트의 `candidate-save-selection.json`은 선택한 후보·상세 시도·근거 지문을 고정합니다.
다시 실행해도 다른 게시글로 넘어가지 않으며, 파일이 손상됐거나 기존 근거와 충돌하면 보존하고
검토 상태로 멈춥니다. 최초 발견 시각은 v14 관찰 시각으로 바꾸지 않고 기존 후보의 값을 사용합니다.

현재 게시글은 처음 관찰할 때, 사용자 시작 뒤, 전경 이탈에서 사용자가 재개할 때마다 허가와
다시 대조합니다. 제목·작성자·공개 IP·작성 시각, 정확한 이미지 URL과 자연 크기·본문 출현 위치·
제외 이미지 근거가 고정 관찰과 일치해야 합니다. 현재 스냅샷의 `candidate_reviewed` 승격과
대기열 등록은 이 허가를 받는 별도 API에서만 수행합니다. 기본 `save-post`의 예제 게시글 제한과
전역 `SITE_VERIFIED_POST`는 그대로이며 전체 갤러리의 본문 저장 프로필로 확대하지 않습니다.

원본 첨부명 대응이 `ambiguous`·`unavailable`이면 원본명은 null로 유지합니다. 개수·순서나
저장 창 제안명으로 원본명을 추정하지 않습니다. 이 불확실성은 정확한 본문 이미지의 네이티브
저장·파일 검증과 별도로 기록합니다.

발견 DB와 기준점·후보·완료 상세 기록은 `%LOCALAPPDATA%/ImageMonitorWatch`에 남깁니다.
이미지 작업과 파일은 별도의 `%LOCALAPPDATA%/ImageMonitorCandidateSave` 아래 세션 DB와
출력 경로에서 처리합니다. 발견 DB에는 게시글·이미지 작업을 추가하지 않습니다. 아래의 공통
세션 잠금·미해결 표시·전경 검사·실제 Save As·Chrome 완료 판독·Pillow 검증·확정 저널을 재사용하며,
이미 확정한 작업은 다시 저장하지 않습니다.

같은 감시 범위 잠금 안에서 정상 게시글 탐색 전과 종료 후에 서비스 대기를 남깁니다.
401·403은 선택 기록에 접근 차단을 보존해 후속 목록·상세·후보 저장을 막습니다. 429·503은
`Retry-After`와 최소 대기를 적용합니다. 404·410으로 선택한 글을 사용할 수 없으면 다른 후보로
대체하지 않고 검토 상태로 남깁니다. 후보 모드는 v9 예제용 입력 전 재개를 사용하지 않습니다.

Windows 실행기는 `RUN_CANDIDATE_SAVE_TEST.cmd`이며 사용자 절차는 ZIP 안의 TXT 하나에
정리합니다. 이 모드는 Chrome에서 한 게시글만 처리하는
네이티브 시험이며 계속 실행하는 정기 감시나 전체 후보 자동 저장은 아직 연결하지 않았습니다.
v15 자동화 검사는 통과했고 사용자 결과에서는 JPEG·PNG 두 파일의 저장·검증·최종 확정을
확인했습니다. 전체 시험은 마지막 브라우저 종료 확인에서 중단됐으며 상세 근거는
[검증 기록](validation.md)에 구분해 남깁니다.

## v16의 완료 파일 확인과 종료 정리

사용자 v15 TXT는 완료 2개·미완료 0개와 `001.jpg`·`002.png`의 검증 결과를 보고했지만,
`browser_shutdown`에서 `NativeUIError`가 나고 세션 공통 미해결 표시가 남았습니다.
`candidate_save_manual_review`·종료 코드 2이므로 전체 시험 완료로 기록하지 않습니다.
대상 창이 사라졌다는 진단만으로 프로세스 종료를 입증할 수 없으며 이 TXT만으로 지연 원인을
특정하지 않습니다. 함께 출력된 pywinauto `SyntaxWarning` 이후에도 두 파일이 확정됐으므로
이 경고를 해당 종료 실패의 원인으로 판정하지 않습니다.

새 `candidate-finish`는 기존 두 작업 루트와 고정 선택을 재사용합니다. 같은 감시 범위 잠금과
네이티브 세션 잠금 안에서 이전 실행의 정확한 세션 폴더·프로필·PID와 유한한 생성 시각을
스키마 2 비공개 보고서와 대조합니다. 지원하는 보고서는 후보 모드의 종료 확인 실패이고,
활성 시도가 없으며 고정 후보의 모든 이미지가 완료됐어야 합니다.

네이티브 DB는 읽기 전용으로 열어 작업 수·소유 토큰 없음·완료 상태·`finalized` 저널·불변
관찰 ID·후보 허가를 대조합니다. 각 최종 파일을 다시 Pillow로 확인하고 배타적 SHA-256이
저널과 같은지 검사하며 `metadata.json` 전체가 고정 저널에서 계산한 내용과 일치해야 합니다.
이 명시적 확인은 `finalized` 상태인 최종 파일도 다시 읽습니다.
작업을 재대기시키거나 다운로드·파일 재작성·메타데이터 재생성을 하지 않습니다.

프로필이 아직 사용 중이면 등록된 Chrome의 정확한 PID·생성 시각·현재 Windows 세션·프로필
인자와 해당 프로세스가 소유한 루프백 디버깅 포트를 먼저 확인합니다. 이 근거가 모두 맞을 때만
기존 전용 브라우저에 정상 종료를 요청하며 새 브라우저나 게시글을 열지 않습니다. 다른 브라우저에
연결하거나 프로세스를 강제 종료하지 않습니다. 종료 소유권이나 파일 근거를 확인할 수 없으면
파일과 미해결 표시를 보존하고 검토 상태로 끝냅니다.

실제 프로세스·프로필 종료와 검사 도중 공유 표시가 바뀌지 않은 것을 확인한 뒤에만 표시를
해제합니다. 별도의 완료 확인 보고서를 남기며 이전 작업자 보고서는 그대로 보존합니다.
Windows 실행기는 `RUN_CANDIDATE_FINISH.cmd`이고 사용자 절차는 ZIP 안의 안내 TXT 하나에
정리합니다. 시작 버튼이나 네이티브 입력 없이 기존 완료 상태만 확인하는 한정 시험입니다.

일반 종료 도우미도 CDP `Browser.close` 뒤 10초를 기다리고, 지연되면 소유한 CDP 연결을
해제한 뒤 20초를 더 기다립니다. 연결 해제나 창 소멸만으로 성공 처리하지 않으며 실제 프로세스
종료가 필요합니다. 전용 실행에는 백그라운드 모드 비활성화 인자를 추가하고, 실패 진단은 단계·
예외 유형만 남깁니다. v16의 새 자동화 결과와 사용자 완료 확인 결과는 확인 후 별도로 기록합니다.

## v19 목록 감시에서 확인한 후보 한 게시글

사용자 v18 결과에서 `목록 감시`에 남긴 두 후보의 상세 확인과 정상 종료를 확인했습니다.
두 결과 모두 기준점 이후 작성 시각·로딩된 본문 이미지 1개·미해결 이미지 0개였습니다.
새 `monitor-save-test`는 이 범위의 기존 완료 상세 관찰에서 후보 하나를 고정해 같은 네이티브
작업자에 연결합니다. 목록을 다시 탐색하거나 후보 상세를 새로 수집하지 않습니다.

허가는 `목록 감시 / normal / comic_new6 / ai / search_subject_memo`의 다섯 필드가 후보와
상세 시도에서 모두 정확히 같아야 합니다. v15의 `검색 감시 시험` 근거를 새 범위에 섞지 않으며,
기준점 이후 작성 시각·유일한 헤더와 본문·로딩된 이미지 1~2개·미해결 0개를 요구합니다.
현재 게시글의 헤더와 정확한 이미지 URL·자연 크기·본문 출현 위치·제외 근거도 저장 시작과
전경 재개 때마다 불변 관찰과 다시 대조합니다. 원본명 대응을 추정하거나 전역 `site_verified`
대상을 넓히지 않습니다.

선택은 발견 루트의 `monitor-save-selection.json`에 고정합니다. 기존
`candidate-save-selection.json`과 이전 저장 허가·완료 파일을 바꾸지 않습니다. 발견 DB의
목록·기준점·후보·상세 기록과 이미지 작업 0개는 유지하고 새 이미지 작업·파일·보고서는 별도
`%LOCALAPPDATA%/ImageMonitorMonitorSave`의 세션 DB와 출력 폴더에 기록합니다. 반복 실행이
다른 후보로 넘어가거나 완료 파일을 다시 저장하는 동작은 없습니다.

`RUN_MONITOR_SAVE.cmd`는 실행기의 주 스레드에서 저장 작업자를 실행합니다. 로컬 감시 화면의
작업 스레드에 Windows 네이티브 입력을 넣지 않습니다. 사용자는 열린 전용 Chrome에서
`저장 시작`을 한 번 누른 뒤 저장이 끝날 때까지 그 창을 앞에 유지해야 합니다. 창 활성화를
강제하지 않으며 실제 우클릭·네이티브 Save As·Chrome 완료 판독·Pillow 검증·최종 확정과
세션 공통 미해결 표시를 기존 경로로 처리합니다. 시험 종료 시 결과 TXT 하나를 엽니다.
목록 감시나 후보 내용 확인을 다시 실행할 필요가 없으며 사용자 절차는 ZIP 안의 TXT 하나에
정리합니다.

공통 감시 잠금과 서비스 대기·접근 차단을 지키며, 선택한 글이 삭제되거나 근거가 달라지면
다른 글로 자동 전환하지 않습니다. 이미지를 HTTP로 직접 저장하거나 전체 후보를 자동으로
저장하지 않습니다. 불확실한 저장은 기존 보류 상태와 파일을 유지하며 자동 재시도하지 않습니다.

지원용 `monitor-finish`와 `RUN_MONITOR_FINISH.cmd`는 새 선택·출력 루트에 묶인 완료 파일의
근거와 브라우저 종료만 재확인합니다. 모든 이미지 작업의 완료·확정 저널·배타적 파일 검증과
메타데이터 일치, 정확한 전용 프로필 종료를 입증한 뒤에만 미해결 표시를 정리합니다.
새 게시글 탐색·네이티브 입력·파일 재저장이 없으며 이전 후보 시험의 선택·파일을 대신 처리하지
않습니다. 기본 시험에서 이 실행기를 추가로 실행할 필요는 없습니다. 사용자 PC의 새 저장 연결은
새 결과 TXT로 확인하며 v18의 읽기 전용 관찰만으로 저장 인수 완료를 선언하지 않습니다.

## 완료를 확정하는 순서

1. Windows 세션 공통 mutex와 미해결 상태를 확인하고, 같은 세션 전용 DB/출력 루트를 사용합니다.
   이전 미해결 브라우저가 있으면 작업 루트를 바꿔도 새 네이티브 저장을 차단합니다.
2. 작업자가 모두 멈춘 상태에서 확정 저널만 로컬 복구합니다. 불확실한 중단 작업은 보류합니다.
3. 게시글 관찰 결과와 작업을 원자적으로 저장하고, 사용자 시작 후 이미지 집합을 재검사합니다.
   이번 게시글의 작업 ID로만 선점을 제한하며 선점 시 불변 관찰 결과를 고정합니다.
   이미지 사이에 전경을 잃으면 다음 작업을 선점하기 전에 멈추고 새 nonce의 `계속 저장`을
   기다립니다. 전경이 돌아오는 것만으로 재개하지 않으며 사용자가 누른 뒤 게시글·헤더·이미지
   집합과 각 스크롤의 전경 조건을 다시 검사합니다.
4. 제목·작성자·날짜·공개 IP와 정확한 `currentSrc`, 본문 소속·자연 크기를 재검사합니다.
   확인한 이미지 핸들 하나를 유지하므로 DOM 교체 시 다른 이미지로 재지정하지 않습니다.
5. 실제 우클릭과 네이티브 메뉴·저장 창을 조작합니다. 매 이미지마다 새로운
   `_staging/<작업ID>/<시도ID>/`를 사용하며 기존 파일을 저장 대상으로 사용하지 않습니다.
   제안명에 확장자가 없으면 선택한 파일 형식의 명시적 필터 또는 Windows의 읽기 전용
   확장자→ProgID→형식 설명 연결로 한 가지 이미지 형식임을 확인합니다.
   언어별 문자열을 추측하거나 여러 형식을 가리키는 이름을 허용하지 않습니다.
6. 첫 저장 전에 소유한 Chrome에 백그라운드 `chrome://downloads/` 탭을 열어 읽기만 합니다.
   원래 페이지·창 제목·전경·문서 포커스가 유지돼야 합니다. 정확한 저장 경로와 전체 원본 URL이
   일치하는 유일한 행의 숫자 상태 `2`와 위험/삭제 플래그를 검사합니다.
   다른 상태·모호한 행·알 수 없는 모델은 성공으로 간주하지 않습니다.
7. 쓰기 종료 근거를 확보한 뒤 배타적 파일 읽기와 SHA-256, Pillow verify/reopen/load,
   전체 프레임과 선택 이미지의 자연 크기를 확인합니다. 크기 안정화만으로 완료 처리하지 않습니다.
8. 불변 관찰 ID·검증 결과·완료 근거·목표 경로를 `prepared` 저널로 커밋합니다.
   같은 볼륨 안에서 덮어쓰기 없는 최종 발행 후 DB를 완료 처리하고,
   소유한 `metadata.json`을 원자적으로 갱신해 저널을 `finalized`로 확정합니다.

최종 확장자는 저장 창 제안명이나 URL이 아닌 검증된 실제 이미지 형식으로 정합니다.
파일 바이트는 이동 외에 변경하지 않습니다. 원본 첨부명·브라우저 제안명·최종명은
각각 보존합니다. 메타데이터에는 고정한 게시글 관찰과 검증·재시도 이력을 함께 기록합니다.

## 중단과 복구

작업자 보고서 v2는 `preparing_no_input → input_armed → writer_verified`를 보존합니다.
실제 첫 스크롤 직전 콜백에서 `input_armed`를 디스크에 기록하고 `loading → saving`을
커밋한 뒤에만 조작합니다. 기록에 실패하면 조작하지 않습니다.
콜백 전에 전경 검사가 실패한 현재 `loading` 선점은 토큰을 확인해 해제하고,
빈 시도 폴더를 보존한 채 새 사용자 재개를 기다립니다.

브라우저 쓰기가 불확실하면 전용 브라우저·세션 공통 미해결 표시·staging을 유지합니다.
작업은 `paused_ui` 또는 `paused_local`로 보존하며 자동 재저장하지 않습니다.
완료가 입증된 파일의 로컬 확정 실패는 브라우저를 닫을 수 있지만 파일과 저널은 유지합니다.

`prepared` 이후 중단은 staging/최종 파일과 기록한 해시를 대조해 로컬에서만 복구합니다.
DB 완료 뒤 메타데이터만 미완료이면 메타데이터를 다시 생성합니다.
알 수 없는 파일·덮어쓰기 충돌·해시 불일치·소유권이 다른 메타데이터는 그대로 보존하고 보류합니다.
이미 `finalized`인 파일의 나중 외부 변경을 검사하는 상시 무결성 감시 기능은 아직 없습니다.
v16의 `candidate-finish`는 종료 확인만 실패한 고정 후보에 대해 파일·메타데이터를 다시 검사하는
명시적 한 번 확인이며 상시 감시나 범용 보류 작업 복구로 확대하지 않습니다.

`RETRY_POST_SAVE_TEST.cmd`는 개발자 안내 후에만 사용합니다. 이전 전용 브라우저를 사용자가
닫은 다음 `save-post --resume-preinput`으로 이전 실패를 검사합니다. 이번 v9의
`image_load` 최초 전경 검사 실패만 지원하며 다음 근거가 모두 일치해야 합니다.

- 세션 공통 표시가 가리키는 정확한 전용 실행 폴더·프로필과 종료된 브라우저.
- v1 비공개 보고서의 모드·단계·정확한 오류 사유와 작업/관찰/시도 경로.
- 현재 DB의 `paused_ui`·마지막 실패 이력·불변 원본 관찰과 소유권 없는 작업.
- 해당 작업의 모든 시도 폴더가 비어 있고 최종 슬롯과 확정 저널이 없음.

검사를 통과한 작업 하나만 이력을 남겨 다시 대기열에 넣고 미해결 표시를 해제합니다.
DB 커밋 후 표시 제거 전에 중단되면 다음 명시적 실행은 근거를 다시 확인해 표시만 정리합니다.
기존 완료 파일·슬롯·관찰·재시도 횟수·대기 시각을 유지하며 새 저장은 사용자 시작 후 수행합니다.
이 조건에 맞지 않는 보류 작업은 검토 상태를 유지합니다.

기본 작업자의 성공은 종료 코드 0과 `status: post_completed`입니다. 후보 시험의 외부 보고서는
`candidate_save_completed`로 구분하며 대기·대상 없음·수동 검토도 별도 상태로 보고합니다.
완료 수는 각 확정 후와 오류 처리 후 DB에서 다시 읽으므로 부분 성공도 반영합니다. 기본 작업자의
결과 TXT에는 단계·오류 유형·저장 수·안전한 전경 진단·파일 형식/해시·출력 위치를 남기며 원본
제목·작성자·첨부명·전체 이미지 URL은 공유하지 않습니다. 후보 공유 TXT는 형식·크기·개수 등
제한된 결과를 남기며 이미지 지문과 로컬 경로도 제외합니다.
상세 보고서·DB·메타데이터는 사용자 PC에 보존하며 공개 저장소에 올리지 않습니다.

## 검증 경계

Chrome의 영어·한국어 기본 저장 시험은 실제 Windows CI에서 생산 완료 판독기로 확인했습니다.
[Windows CI #26](https://github.com/dropboxqfml-code/codex/actions/runs/43678523305)에서
영어·한국어 Chrome 각각 PNG·JPEG·애니메이션 GIF의 연속 저장·확정과 재실행 중복 방지를
확인했습니다. 확장자 없는 실제 저장 창 제안명 여섯 건도 현재 PC의 형식 연결 근거로 처리했습니다.
fixture의 원본 해시는 시험 최종 검증에만 사용하고 생산 저장 완료의 입력으로 사용하지 않습니다.
Edge의 기본 우클릭 저장은 성공했지만 통합 완료 판독은 아직 검증하지 않아 이 작업자에서는 거부합니다.
[Windows CI #28](https://github.com/dropboxqfml-code/codex/actions/runs/43688776541)에서
영어 Chrome의 첫 파일 확정 후 별도 시험 창으로 전경을 옮겨 일시정지·새 승인·나머지 저장까지
검증했습니다. 새 승인을 기다리는 동안 기존 완료 파일·저널·메타데이터가 유지되고 남은 두 작업의
선점 토큰이 없음을 확인했습니다. 영어·한국어 모두 세 형식 저장·검증·중복 방지를 통과했습니다.

v9 사용자 TXT에서 실제 WEBP 한 개의 저장·검증·확정을 확인했습니다. 두 번째 파일은
첫 스크롤 전에 전경 검사에서 중단됐습니다. v10 사용자 TXT에서는 Chrome 155.0.8059.84로
정확한 이전 작업의 입력 전 재개·기존 파일 보존·미해결 표시 해제를 확인했습니다.
이미 확정된 파일 한 개는 로컬 복구가 건너뛰고, `001.webp`의 네이티브 저장을 반복하지 않은 채
`002.webp`·`003.webp`·`004.webp`를 저장·검증·확정했습니다.
보고서 스키마 2의 `post_completed`·`complete`·종료 코드 0, 관찰 4개·완료 4개·미해결 0개와
브라우저 종료·공통 미해결 표시 없음·오류 유형 없음을 확인했습니다.
검증한 예제 게시글 하나의 전체 저장과 입력 전 재개는 사용자 인수 시험을 통과했습니다.
다른 일반·마이너·미니 갤러리와 게시글, 검색 목록·정기 감시는 별도 검증 대상입니다.
