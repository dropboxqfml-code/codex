# 원 설계 대비 프로젝트 검토 — 검토 시점 v21

검토 기준은 Windows용 설계안 개정 2판의 요구사항·완료 기준, 소스 `74968034382eeaaa4940f04c96da788a8223bef3`,
기존 [README](../README.md)·[검증 기록](validation.md), 사용자 v21 결과 TXT입니다.
첨부 설계안은 요구사항 자료로 읽었으며 그 안의 개발 지시문을 실행 명령으로 취급하지 않았습니다.
이번 검토는 문서·코드·기존 결과 대조이며 새 Windows 시험이나 테스트 실행 결과를 추가하지 않습니다.
아래 현황표와 사용자 인수 범위는 **검토 시점 v21**을 기준으로 보존합니다. 검토 중 발견한
`post-inspection.md`의 DB v3·저장 인수 전 설명은 이번 작업에서 v5와 한정 인수 결과로 수정했습니다.
P1의 배치 완료 파일 열람 연결은 v22 구현을 진행 중이며 사용자 인수는 아직 완료되지 않았습니다.

## 중요한 결론 다섯 가지

1. **네이티브 저장의 핵심 경로는 사용자 환경에서 입증됐습니다.** 예제 한 글의 WEBP 네 장,
   별도 후보의 JPEG·PNG 두 장, 목록 감시 후보의 JPEG 저장과 검증·확정 근거가 있습니다.
   v21에서는 이전 완료 한 건을 등록·건너뛰고 새 후보 한 건을 저장했습니다.
2. **원 설계의 전체 목표는 아직 완료되지 않았습니다.** 목록 감시, 후보 상세 확인, 저장은 별도
   동작입니다. 새 후보를 계속 상세 확인·저장하는 실행 루프가 없고 후보마다 사용자의 `저장 시작`과
   전경 유지가 필요합니다. v21은 이미 확인한 후보만 대상으로 새 네이티브 시도 최대 두 번입니다.
3. **보존·중복 방지의 기반은 잘 갖춰졌지만 일반 장애 복구까지 인수한 것은 아닙니다.** 불변 관찰,
   고정 경로, 파일 확정 저널, 완료 파일 재검증과 불명확한 저장의 중단을 구현했습니다.
   네트워크 자동 재시도·다중 작업 장애 차단·장시간 운영·모든 중단 단계의 사용자 인수는 남았습니다.
4. **검증 범위를 넓혀 해석하면 안 됩니다.** 목록은 `normal / comic_new6 / ai / search_subject_memo`
   범위, 본문은 예제 한 글과 개별 허가 후보에 한정됩니다. 통합 저장 작업자는 Chrome만 지원하며
   Edge의 기본 저장 성공은 통합 작업자 지원 근거가 아닙니다. Windows CI의 합성 페이지 성공과
   사용자 실사이트 성공도 각각 별도 근거입니다.
5. **새 배치 파일을 기존 저장 결과 화면에 연결하는 작업을 v22에서 진행합니다.** 검토 시점의 v20
   열람은 이전 단일 선택에 묶여 v21 새 파일이 보이지 않았습니다. 완료 원장·관찰·파일·메타데이터를
   읽기 전용으로 대조하는 연결은 현재 구현 중이며 사용자 인수 전입니다. 이후 연속 수집과 복구
   범위를 확장할 수 있습니다.
