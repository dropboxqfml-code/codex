# SQLite 영구 대기열 — 독립 개발 단계

이 단계는 브라우저나 사이트에 연결하지 않고 발견 기록과 이미지 작업을 보존합니다.
Windows 네이티브 저장·자동 감시·실사이트 파싱은 아직 연결하지 않았습니다.

## 로컬 시험

`image-monitor` 폴더에서 실행합니다. Python 3.12와 SQLite 3.50.2 이상이 필요합니다.
SQLite가 오래된 Python이라면 `uv python install 3.12.14` 후
`uv sync --locked --python 3.12.14`로 검증한 관리형 런타임을 사용하세요.

```powershell
uv run --locked image-monitor queue-demo --db ./reports/queue-demo.sqlite3
uv run --locked image-monitor queue-status --db ./reports/queue-demo.sqlite3
```

`queue-demo`는 **새 DB에만** 합성 게시글 1개·이미지 작업 2개를 만들고, 하나의
네트워크 실패와 600초 서비스 대기를 기록합니다. 원격 요청이나 파일 다운로드는
하지 않습니다. 이미 있는 DB나 파일을 덮어쓰지 않습니다. 같은 경로에서 다시 시험하려면
기존 DB를 삭제하지 말고 다른 새 경로를 지정하세요.

`queue-status`는 읽기 전용 연결로 게시글·작업 수, 상태별 작업 수, 미확인 구간 수와
가장 오래된 발견 시각을 표시합니다. 존재하지 않는 DB를 새로 만들지 않습니다.

## 보존하는 규칙

- 게시글 키는 `(갤러리 종류, 실제 ID, 글번호)`입니다. 검색어별 발견 이력은 별도로
  남기며 같은 게시글 작업을 중복 생성하지 않습니다.
- 발견 기록, 검색어 일치 기록, 확인 지점과 미확인 구간은 하나의 트랜잭션에서
  커밋됩니다. 중간 오류가 나면 확인 지점도 함께 롤백합니다. 오래된 탐색 결과가
  더 최근 확인 지점을 뒤로 돌리지 못합니다.
- 최초 발견 시 날짜·작성자·감시명으로 배정한 `folder_plan`은 DB에 고정합니다.
  나중에 작성 시각을 보완하거나 다른 검색어로 다시 발견해도 기존 경로를 이동하지
  않습니다. 날짜 정책 변경은 새 게시글에만 적용됩니다.
- 본문 순서와 별도의 `stable_key`가 필요합니다. 이 키는 검증된 본문 어댑터가
  제공해야 하며 대기열에서 순서나 URL로 추정하지 않습니다. 재발견 시 작업 ID와
  파일 슬롯은 유지하고 표시 순서만 갱신합니다. 새 이미지가 옛 순번에 나타나도
  기존 파일 슬롯을 재사용하지 않습니다.
- SQLite `BEGIN IMMEDIATE`로 작업 선점을 직렬화하고, 선점 토큰이 일치하는
  작업자만 상태를 변경할 수 있습니다. 이것은 DB 작업 소유권이며 Windows 저장
  전역 잠금과는 별도입니다. 두 장치를 연결하는 실제 저장 작업자는 아직 없습니다.
- 네트워크 실패 횟수·최초 실패 시각·재시도·서버/서비스 공통 대기는 재시작 후에도
  유지합니다. Retry-After는 해당 서비스 범위에도 적용하며 더 짧은 대기로 줄이지
  않습니다. 단기/장기 총 8회 및 최초 실패 24시간 한도를 선점 시에도 확인합니다.
- UI·로컬 오류·접근 거부는 각각 `paused_ui`·`paused_local`·`blocked`로 보존하며
  네트워크 시도 횟수를 늘리지 않습니다. 실패 이력은 작업별로 남깁니다.
- 오래된 재시도와 새 작업은 실행 가능 시각을 기준으로 섞어 처리합니다. 지속적으로
  새 글이 들어와도 이미 실행 시각이 지난 재시도가 새 작업 뒤로 무조건 밀리지 않습니다.
- 모든 작업자가 멈췄다고 명시한 뒤에만 중단 작업의 복구를 요청할 수 있습니다.
  `loading/saving/verifying`는 `manual_review`로 보존하고 자동 재다운로드하지 않습니다.
  이 API는 작업자 종료를 직접 확인하지 않습니다. 실제 작업자/프로세스 확인과 연결하기
  전에는 운영 자동 복구에서 호출하면 안 됩니다.

## 개발 API

`QueueStore`는 컨텍스트 관리자로 사용합니다. `discover_batch` → `queue_images` →
`claim_next` 순으로 처리합니다. `transition`은 `loading → saving → verifying`만
허용합니다. 실패는 `record_failure`, 공통 대기는 `defer_service`에 기록합니다.
`get_post`, `get_job`, `get_checkpoint`, `list_jobs`, `history`, `summary`로 확인합니다.

`record_failure(kind="network")`는 실제 실패한 네트워크 시도 하나를 기록하는 API입니다.
아직 성공 시도와 최종 저장을 확정하는 API는 없습니다. 따라서 `attempt_count`는 현재
단계에서 기록된 실패 시도의 누계이며, 향후 성공 시도 기록과 연결해야 합니다.
원시 예외·쿠키·인증 헤더 대신 정리된 실패 사유 코드를 전달하세요.

## 아직 완료되지 않은 항목

`verifying`는 저장 완료가 아닙니다. 최종 파일·SHA-256·DB·metadata.json을 대조해
완료를 확정하는 API와 강제 종료 복구는 다음 단계입니다. 삭제 확인, 임시 파일 격리,
확정 파일 재검증과 수동 보류 작업 재개도 아직 연결하지 않았습니다.

실제 목록 탐색·최초 실행 기준점·겹친 구간 재확인·갤러리 전환·회로 차단·용량 관리와
정기 스케줄러는 별도 구현이 필요합니다. 미확인 구간은 현재 저장만 하며 실제 후속
탐색 및 해결 처리기는 없습니다. 대기열 DB에는 표시 이름·제목·URL이 포함될 수 있으므로
외부에 공개하지 마세요. 알 수 없는 DB 형식은 자동 수정하지 않고 거부합니다.
