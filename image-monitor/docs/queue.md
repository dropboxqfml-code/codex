# SQLite 영구 대기열과 파일 확정 기록 — DB v4

대기열은 검색 목록 관찰·후보, 게시글 발견, 본문 관찰, 이미지 작업, 재시도 상태와 파일 확정
기록을 보존합니다. 목록 후보는 본문을 확인한 게시글·이미지 작업과 별도 테이블에 저장합니다.
`QueueStore` 자체는 브라우저를 조작하거나 파일을 이동하지 않습니다. 네이티브 저장 작업자와
로컬 파일 확정기가 이 API를 사용해 저장 결과를 연결합니다. 실제 사용자 게시글 저장과
정기 감시의 검증 범위는 [검증 기록](validation.md), 본문 선별과 이름 대응은
[본문 분석 안내](post-inspection.md)를 참고하세요.

사용자 v10 시험에서는 검증 대상 게시글 한 개의 입력 전 중단을 재개해 기존 `001.webp`를
보존하고 나머지 세 이미지를 확정했습니다. 이 결과와 검색 목록의 정기 감시 검증은 별개입니다.
입력 전 중단을 안전하게 재개하는 경로와 파일 확정 복구도 구분합니다.

## 로컬 개발 시험

Python 3.12와 SQLite 3.50.2 이상이 필요합니다. 검증한 관리형 런타임은 Python 3.12.14입니다.
다음 명령은 개발용 합성 대기열 시험과 상태 조회입니다. 사용자 인수 시험 작업은 ZIP에 동봉한
TXT 안내에 따로 정리합니다.

```powershell
uv run --locked image-monitor queue-demo --db ./reports/queue-demo.sqlite3
uv run --locked image-monitor queue-status --db ./reports/queue-demo.sqlite3
```

`queue-demo`는 새 DB에만 합성 게시글 1개·이미지 작업 2개, 네트워크 실패 하나와
600초 서비스 대기를 기록합니다. 원격 탐색이나 이미지 저장을 수행하지 않으며 기존 DB를
덮어쓰지 않습니다. `queue-status`는 읽기 전용으로 상태를 조회하고 없는 DB를 만들지 않습니다.

## 검색 목록 관찰과 후보

`WatchStore(QueueStore(...))`는 `(watch_name, gallery_type, gallery_id, keyword, search_type)`를
한 감시 범위로 사용합니다. `persist_scan`은 호출자가 검증한 목록 계획을 받아 목록 관찰,
후보 갱신, 감시 상태와 부분 탐색의 미확인 구간을 한 트랜잭션으로 저장합니다. 이 API 자체는
사이트 DOM이나 탐색 범위의 정확성을 입증하지 않습니다. 현재 계획기는 명시적인 합성 fixture만
허용하며, 실제 DOM 검증을 마치기 전에는 실제 목록의 정기 탐색·저장 루프를 활성화하지 않습니다.

| 테이블 | 보존하는 내용 |
| --- | --- |
| `watch_state` | 범위별 세대 번호, 최초 기준점, 마지막 완전 탐색 체크포인트와 최신 관찰 ID |
| `watch_scans` | 매번의 목록 결과 JSON, 해당 탐색의 체크포인트, 완료 여부와 부분 탐색 사유 |
| `watch_candidates` | 범위·글번호별 후보, 목록 표시 정보, 변경하지 않는 최초 발견 시각과 최신 관찰 |
| `watch_gaps` | 부분 탐색을 남긴 관찰 ID와 사유의 이력 |

기본 `new` 시작 계획은 처음 본 기존 행을 후보로 적재하지 않고 정확한 글번호 목록을 최초
기준점에 보존합니다. 이 기준점은 한 번 정하면 바꾸지 않습니다. 이후 탐색은 최신 목록부터
시작하고 알려진 정확한 글번호를 만난 뒤 한 페이지를 더 겹쳐 확인하거나 명시적인 끝 근거로
범위를 확인합니다. 최대 글번호만으로 빠짐없는 탐색을 선언하지 않습니다.

호출자는 계획을 만들 때 읽은 `expected_generation`을 커밋에 전달합니다. 저장소는 쓰기 잠금
안에서 세대 번호를 대조하므로 같은 상태에서 만든 겹친 계획이 모두 커밋될 수 없습니다.
오래된 세대·관찰 시각 또는 변경된 최초 기준점을 거부하면 후보·관찰·체크포인트도 함께
롤백됩니다. 같은 후보를 다시 관찰해도 행이나 최초 발견 시각을 중복 생성하지 않습니다.

부분 탐색은 후보와 최신 관찰, 후속 탐색 위치를 남기되 마지막 **완전 탐색** 체크포인트를
옮기지 않습니다. 후속 위치는 최신 `watch_scans`의 결과·체크포인트에서 읽습니다.
`watch_gaps`는 과거의 미확인 구간 이력이므로 나중에 완전 탐색을 마쳐도 자동 삭제하거나
해결 상태로 바꾸지 않습니다. 기존 `checkpoints`·`gaps`와도 별개입니다.

목록의 표시 작성자·날짜는 `shown_metadata`에만 보존합니다. 목록 후보를 저장하면서 `posts`,
이미지 작업이나 `folder_plan`을 만들지 않습니다. 기본 `new` 정책의 후보는 실제 저장 전에
본문에서 확인한 `published_at`으로 최초 기준 시각 이후 글인지 필터링해야 합니다. 목록 날짜나
최초 발견 시각으로 이 검사를 대신할 수 없습니다. 상세 확인과 날짜 필터를 통과한 뒤에만
아래 본문 관찰 API로 저장 경로와 이미지 작업을 만듭니다.

## 기존 발견 API와 본문 관찰

게시글 키는 `(갤러리 종류, 실제 ID, 글번호)`입니다. 기존 `discover_batch` API는 게시글,
감시 범위별 발견 이력, 이전 형식의 목록 체크포인트와 미확인 구간을 한 트랜잭션으로 저장합니다.
이 API와 기존 데이터는 유지하지만 새 검색 목록 계획은 위의 별도 `WatchStore`를 사용합니다.
중간 실패는 함께 롤백하며 오래된 결과가 더 최근 체크포인트를 되돌리지 못합니다.

`persist_post_snapshot`은 본문 관찰 결과·게시글·감시 범위·이미지 작업·작업 대응 관계를
원자적으로 저장합니다. 이 작업은 목록 체크포인트를 변경하지 않습니다. 감시 범위는 호출자가
전달한 값으로, 검색 목록이 해당 글을 반환했다는 증거와 구분합니다. 이전 관찰 JSON은 수정하지
않으며 새 관찰이 추가됩니다. 오래된 관찰이 최신 작업 상태를 되돌리는 경우는 거부합니다.

최초 배정한 날짜·작성자·감시명 경로인 `folder_plan`은 고정합니다. 작성 시각을 보완하거나
날짜 정책을 바꿔도 이미 배정한 파일을 다른 날짜 폴더로 옮기지 않습니다.

이미지의 `stable_key`는 본문 순서와 별개입니다. 대기열은 키를 추정하지 않고 어댑터가 제공한
키를 사용합니다. 재관찰에서 작업 ID와 파일 슬롯은 유지하며 본문 표시 순서만 갱신합니다.
새 이미지가 이전 순번에 나타나도 기존 파일 슬롯을 재사용하지 않습니다. 원본 파일명 대응,
리소스 식별자와 정확한 URL 기반 작업 키의 검증 경계는 본문 분석 안내에 기록합니다.

## 작업 선점과 고정된 저장 근거

`claim_next(worker_id, now, job_ids=...)`는 `BEGIN IMMEDIATE` 안에서 작업을 선점하고
작업자 ID와 선점 토큰을 기록합니다. 실행 가능 시각·서비스 대기·재시도 한도를 만족하는 작업만
선택하며, 반환값의 `source`에는 해당 작업과 연결된 관찰 ID·관찰 JSON·이미지 정보를 담습니다.
선택한 근거는 현재 작업의 정확한 표시 URL과 `stable_key`에 일치해야 합니다.

실제 게시글 저장 컨트롤러는 새로 확인하고 허용한 관찰 결과의 작업 ID 목록을 전달합니다.
목록은 최대 500개이며 빈 목록은 아무 작업도 선점하지 않습니다. 다른 게시글이나 이번 본문에서
제외된 과거 작업으로 범위를 넓히지 않습니다. 만료 처리도 지정한 작업 범위에 한정합니다.
`job_ids=None`은 기존 개발 API의 전체 대기열 선택 동작을 유지합니다.

활성 작업의 표시 URL은 재관찰로 교체하지 않습니다. 같은 URL의 첨부명이나 게시글 정보가
새 관찰에서 바뀌어도, 진행 중인 저장은 선점 시 받은 관찰 ID를 명시적으로 사용합니다.
`get_job_source`는 현재 작업 URL에 맞는 연결 근거를 조회하고, `get_observation`은 완료 후 URL이
갱신돼도 이전 관찰 자체를 읽을 수 있습니다. 관찰 근거가 없는 이전 작업의 `source`는 null이며,
이를 검증된 본문 저장 대상으로 임의 취급하지 않습니다.

DB 선점 토큰과 Windows 세션의 `NativeSaveLock`은 별도 장치입니다. 실제 작업자는 두 장치를
연결해 네이티브 저장을 한 번에 하나만 수행합니다. 파일 확정과 로컬 복구도 이 잠금을 유지하는
호출자의 책임입니다.

## 파일 확정 단계

일반 작업 상태는 `queued → loading → saving → verifying → completed`입니다.
`verifying`만으로 파일 저장 완료를 선언하지 않습니다. 네이티브 저장 완료와 본문 대응 근거,
배타적 읽기 및 로컬 검증 결과를 확보한 뒤 파일 확정 기록을 준비합니다.

`artifact_finalizations`는 작업당 하나의 불변 기록을 저장합니다. 관찰 ID, 저장 루트,
작업별 staging 상대 경로, 고정된 최종 상대 경로, 검증 결과, 이미지 메타데이터와 저장 시각을
보존합니다. 최종 파일명은 고정 파일 슬롯과 감지된 실제 형식으로 결정합니다.
다른 작업이 같은 최종 경로를 예약할 수 없으며 경로 이탈과 잘못된 상대 경로를 거부합니다.

| 확정 단계 | DB 작업 상태와 의미 | 다음 동작 |
| --- | --- | --- |
| `prepared` | 검증한 staging 파일의 근거를 기록한 상태이며 작업은 아직 `verifying` | 기존 파일을 덮어쓰지 않는 최종 이동과 최종 파일 재검증 |
| `metadata_pending` | 최종 파일 확인 후 작업을 `completed`로 커밋하고 선점 토큰 해제 | 소유권을 확인한 `metadata.json` 갱신 |
| `finalized` | 메타데이터 기록까지 반영 | 정상 확정 완료 |

`prepare_artifact`는 유효한 `verifying` 선점 토큰과 연결된 관찰 근거를 요구합니다.
입력 경로·실제 형식·크기·SHA-256 및 파일명 일치 여부를 검사하지만 실제 파일을 읽지는 않습니다.
바이트 검증과 작성 종료·본문 대응 증거는 저장 작업자와 파일 확정기가 제공해야 합니다.
`complete_artifact`는 최종 파일 검증 후 DB 완료와 `metadata_pending`을 원자적으로 반영하며,
`mark_metadata_written`은 메타데이터 기록 후 `finalized`로 변경합니다.

파일 확정기는 기존 최종 이미지가 있으면 덮어쓰지 않습니다. staging과 최종 경로는 같은 로컬
볼륨 안에 있어야 하며 심볼릭 링크·재분석 지점과 저장 루트 이탈을 검사합니다. 기존
`metadata.json`은 프로그램 표식·게시글 키·고정 경로가 일치하는 경우에만 안전하게 갱신합니다.
파일·DB·JSON을 하나의 파일시스템 트랜잭션으로 처리한다고 가정하지 않고 위 기록으로 사이의
종료 지점을 구분합니다.

## 로컬 복구와 수동 확인

파일 확정 기록이 하나라도 있는 작업은 단계와 관계없이 새 네이티브 저장 선점에서 제외합니다.
기록 준비 후 오류 처리기가 선점 토큰을 해제했더라도 GUI 저장을 자동으로 반복하지 않습니다.

`recover_finalizations`는 이전 작업자가 모두 종료됐음을 확인하고 전역 잠금을 유지한 뒤
로컬 파일과 기록을 대조합니다. staging 또는 최종 파일의 형식·크기·해시와 저장 근거를 다시
확인한 경우에만 미완료 이동·DB 완료·메타데이터 기록을 이어갑니다. 브라우저를 열거나 이미지
요청을 보내지 않습니다. 충돌·누락·검증 실패는 파일을 보존하고 수동 확인으로 남깁니다.
이미 `finalized`인 항목의 정기 무결성 검사는 이 복구 절차의 범위에 포함하지 않습니다.

`recover_artifact_complete`는 명시적인 작업자 종료 확인과 외부 파일 검증을 전제로,
`prepared` 기록에 연결된 `verifying`·`manual_review`·`paused_local` 작업의 DB 완료를 반영합니다.
QueueStore API의 확인 인자 자체가 OS 프로세스 종료나 파일 검증을 대신하지는 않습니다.
`mark_artifact_manual_review`는 같은 종료 확인을 요구합니다. 준비 단계의 충돌은 작업을
`manual_review`로 보존하고, 이미 완료된 파일의 메타데이터 문제는 `completed`를 유지하면서
`last_error`와 확정 단계에 남깁니다.

`recover_interrupted`는 모든 작업자 종료가 확인된 뒤 남은 `loading/saving/verifying`를
`manual_review`로 보존하고 이전 선점 토큰을 무효화합니다. 자동 재다운로드나 일반적인 보류
해제 기능이 아닙니다. 입력 시작 여부가 불명확한 작업, `manual_review`·`paused_local` 작업은
네이티브 저장 대상으로 자동 재개하지 않습니다. 파일 확정 기록이 있는 경우에만 위의 로컬
파일 검증·완료 복구 경로를 사용할 수 있습니다.

### 입력 전 중단의 제한된 재개

다음 두 API는 DB 스키마 변경 없이 기존 작업과 시도 이력을 사용합니다. 기존 네트워크
실패 누계·최초 실패 시각·재시도 시각·서버 대기를 유지하고 이전 이력을 지우지 않습니다.
재개 시 작업자·선점 토큰·현재 오류만 정리하며 별도 비네트워크 감사 이력을 추가합니다.

`release_unstarted_claim(job_id, token, now=..., reason="pre_input_focus_pause")`는 현재 토큰이
일치하는 `loading` 작업에만 적용합니다. 파일 확정 기록이 없어야 하며 호출자는 네이티브 입력이
전혀 시작되지 않았음을 보장해야 합니다. 작업을 `queued`로 돌리고 `ui_pause` 이력을 남깁니다.
이미 `saving/verifying`로 넘어간 작업이나 오래된 토큰으로는 호출할 수 없습니다.
작업자는 입력을 시작하기 전에 비공개 실행 보고서에 `input_armed` 단계를 먼저 기록합니다.
이 단계에 도달했거나 입력 여부가 불명확하면 입력 전 해제 경로로 되돌리지 않습니다.

`resume_preinput_failure(job_id, observation_id=..., expected_history_id=..., now=...,
confirm_workers_stopped=True, confirmed_no_input=True)`는 지원하는 이전 UI 실패 한 건에만
적용합니다. 현재 상태가 `paused_ui`, 현재 오류가 `NativeUIError`이고 활성 작업자·토큰과
파일 확정 기록이 없어야 합니다. 전달한 실패 이력 ID가 최신 행과 정확히 일치하고, 그 행도
`ui / NativeUIError / paused_ui`여야 합니다. 지정한 불변 관찰의 작업 키와 정확한 표시 URL이
현재 이미지 작업에 대응하는지도 확인합니다. 조건을 통과한 한 작업만 `queued`로 재개하고
`pre_input_resume / verified_no_input` 이력을 추가합니다.

두 확인 인자는 정확한 True를 요구하지만 그 값 자체가 프로세스 종료·입력 부재·파일 부재의
증거는 아닙니다. 복구 컨트롤러는 세션 전역 잠금 아래에서 소유한 기존 비공개 실행 보고서, 실행·프로필·
작업·관찰·시도 경로의 대응, 이전 브라우저/프로필 종료와 작업별 빈 staging을 검증합니다.
기존 최종 파일 슬롯이나 다른 시도에 파일이 있으면 이 경로를 허용하지 않습니다.
알 수 없는 상태·다른 오류·다른 최신 이력·일치하지 않는 관찰은 거부합니다.

동일 실패 ID로 큐 재개 API를 다시 호출하면 거부합니다. 재개 커밋 후 세션 표시 정리 전에
중단된 경우에는 복구 컨트롤러가 일치하는 재개 감사 이력을 확인해 표시 정리만 마칠 수 있습니다.
다른 작업이나 새로운 실패에 이전 보고서를 그대로 재사용해 재개하는 기능은 아닙니다.

`RETRY_POST_SAVE_TEST.cmd`는 명시적인 `--resume-preinput` 경로를 사용합니다. 지원하는
v9 비공개 실행 보고서의 `image_load` 전경 실패와 입력 전 상태를 입증한 경우에만 위의 제한된 재개를
수행합니다. 일반적인 `native-recover`로 보류 표시만 지우거나 대기열 상태를 일괄 초기화하지
않습니다. 알 수 없는 작업·수동 확인·로컬 오류·`input_armed` 이후 작업은 계속 보류합니다.

## 재시도 정책의 범위

`record_failure(kind="network")`는 확인한 네트워크 실패 하나를 기록합니다. `attempt_count`는
네트워크 실패 누계이며 성공 저장이나 모든 브라우저 동작 횟수가 아닙니다. 최초 실패 시각,
다음 시도, 서버/서비스 공통 대기는 재시작 후에도 유지합니다. 실패 누적 8회 또는 최초 실패
24시간 한도에 도달한 작업은 자동 선점하지 않습니다. Retry-After와 서비스 공통 대기는 더 짧은
시간으로 줄이지 않습니다. 실행 가능한 작업 사이에서는 오래된 재시도가 새 작업에 계속
밀리지 않도록 선택합니다.

UI·로컬·접근 오류는 각각 `paused_ui`·`paused_local`·`blocked`로 보존하며 네트워크 실패
횟수를 늘리지 않습니다. 로컬 확정 복구도 이 횟수를 증가시키지 않습니다. 사유는 정리된 코드로
기록하고 쿠키·인증 헤더·원시 예외 내용을 대기열 이력으로 넘기지 않습니다.
재시도 정책 API가 있다는 사실은 모든 실제 네트워크 응답·오류·Retry-After 관측과 자동 재시도가
연결됐다는 뜻이 아닙니다. 정기 스케줄러와 서비스 전체 회로 차단의 완성 검증도 남아 있습니다.

## 스키마와 조회 API

DB 버전 4는 v3의 파일 확정 기록에 위의 목록 관찰·후보·상태·미확인 구간 테이블을 추가합니다.
알려진 v1/v2/v3의 객체 정의가 정확히 일치할 때만 추가 마이그레이션하며, v1에서 v4까지의
변경도 한 트랜잭션으로 수행합니다. 실패 시 커밋된 스키마·행·버전이 원래 상태로 롤백됩니다.
기존 게시글·고정 경로·이미지 작업·시도 이력·본문 관찰·파일 확정 기록은 보존합니다.
알 수 없는 객체가 있는 DB는 수정하지 않고 거부합니다. 읽기 전용 v1/v2/v3 조회는 마이그레이션하지
않으며 실제 DB 버전을 보고합니다. 이전 DB의 `WatchStore` 조회는 초기 상태와 빈 목록을 반환합니다.
관찰 JSON과 메타데이터 JSON의 `schema_version`은 DB 버전과 별도로 관리합니다.

조회에는 `get_post`, `get_job`, `get_checkpoint`, `list_jobs`, `history`, `summary`,
`list_post_snapshots`, `get_observation`, `get_job_source`, `get_artifact`, `list_artifacts`를 사용합니다.
목록 저장소에는 `get_state`, `list_candidates`, `list_scans`, `list_gaps`가 있습니다. 목록 조회는
감시 범위를 요구하고 기본 최대 100개, 지정 시 1~1,000개를 반환합니다.
대기열에는 표시 이름·공개 부분 IP·제목·표시 URL 등이 포함될 수 있으며 기본 공유 자료로
취급하지 않습니다.

검증 대상 한 게시글의 전체 저장·입력 전 재개와 합성 목록 계획의 검사는 실제 정기 감시의
완료를 뜻하지 않습니다. 실제 검색 DOM과 페이지 이동·겹친 구간·끝 근거, 상세 작성 시각 필터,
화면 잠금·긴급 중단·다중 모니터 등의 보호 상황, 갤러리 전환, 회로 차단·용량 관리·정기
스케줄러는 추가 구현 또는 검증 대상입니다.
