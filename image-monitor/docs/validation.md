## 현재 검증 범위

로컬 경로·이미지 검증·SQLite 영구 대기열·본문 관찰·네이티브 저장·최종 파일 확정을 검사합니다.
사용자 v8 관찰로 예제 게시글 하나의 헤더와 원본명 대응을 확인했습니다.
Chrome 단일 게시글 작업자와 확정 저널·메타데이터 복구를 연결했으며,
v9 사용자 환경에서 WEBP 한 개의 실제 저장·검증·확정을 확인했습니다.
v10 사용자 결과로 기존 파일을 보존한 입력 전 재개와 해당 게시글의 전체 4개 저장 인수를
완료했습니다. 사용자 v12 결과에서는 한 검색 범위의 목록 구조와 두 페이지 이동을 확인했고,
v13 결과에서는 최초 기준점 저장과 다음 주기의 새 후보 6개 기록을 확인했습니다.
v14 결과에서는 기존 후보 두 개의 기준점 이후 작성 시각과 본문 이미지 개수를 확인했습니다.
v15 결과에서는 고정 후보 한 글의 JPEG·PNG 두 파일 저장·검증·최종 확정을 확인했지만 마지막
브라우저 종료 확인은 중단됐습니다. v16에서는 기존 파일 재검증과 이미 종료된 전용 브라우저
확인 후 미해결 표시 정리를 완료했습니다. 다른 게시글의 전역 저장 프로필·다른 검색 범위·목록
후보의 이미지 자동 저장은 아직 검증하지 않았습니다.
버전별 자동화 수치는 해당 버전의 기록에 보존하며 사용자 실사이트 시험과 구분합니다.
v17 사용자 결과로 로컬 목록 감시의 두 주기·새 후보 3개 기록과 정상 종료를 확인했습니다.
장시간 동작·일시정지/재개 수동 조작·재시작 후 상태 보존은 이 결과의 검증 범위에 포함하지 않습니다.
v18 사용자 결과로 같은 화면의 정지 상태에서 기존 후보 두 개의 작성 시각·본문 이미지 관찰과

## Windows 사용자 결과와 개선

사용자가 보내 준 TXT에서 다음을 순서대로 확인했습니다.

- 최초 시도: `uv` 명령이 없어 실행 준비 단계에서 중단.
- WinGet 설치 성공 뒤 기존 CMD가 갱신된 PATH를 찾지 못함. 자식 PowerShell에서
  영구 Machine/User PATH를 읽어 검색하도록 수정했습니다. 일반 실행기는 레지스트리나
  실행 정책을 변경하지 않습니다.
- 의존성 설치와 브라우저 연결 뒤 전경 보호 검사로 중단. `시험 시작` 버튼을 누른 뒤
  대상 창 전경 조건을 기다리게 했습니다. 실제 입력이 시작된 뒤에는 즉시 중단 검사를 유지합니다.
- v4 사용자 결과: Windows 10.0.19045, Edge 157.0.4341.46, 한국어 UI, RDP에서
  우클릭 성공 후 `context_menu` 단계 시간 초과. 포커스와 대상 창 소유권은 정상이었습니다.
  이 시도에서는 저장 메뉴 단계에서 중단됐습니다.

전용 Windows CI에서 실제 메뉴를 열어 한국어 Edge의 메뉴가
`다른 이름으로 사진 저장(V)`임을 확인했습니다. 해당 이름을 명시적으로 추가했습니다.
Chromium의 가상 MenuItem은 HWND가 없고, UIA 부모 경로 중 실제 Window보다 먼저
별도 HWND를 가진 Pane을 거칩니다. 신뢰한 HWND에서 새 UIA 루트를 얻어 요소 동일성을
대조하도록 수정했습니다. 동일 PID만으로 허용하거나 요소의 HWND를 덮어쓰지 않습니다.

저장 창은 UIA 최상위 창 열거에 빠질 수 있어 실제 전경 HWND로 직접 연결합니다.
네이티브 PID·클래스·창 소유 관계와 UIA 공급자의 HWND/PID를 확인한 후 조작합니다.
창 종료도 UIA 목록 누락이 아닌 네이티브 HWND의 파괴/숨김으로 확인합니다.

추가 Windows 시험에서 값 읽기는 입력 경로를 반환했지만 실제 파일은 기존 제안 이름으로
저장된 것을 전용 프로필 이력으로 확인했습니다. 포커스 이동만으로는 해결되지 않았습니다.
실제 UIA 경로가 `FileNameControlHost` → Edit(`1001`)인 것을 확인하고 이 구조로 한정했습니다.
경로 입력에는 pywinauto의 Win32 Edit와 같은 `EM_SETSEL`·`EM_REPLACESEL`을 사용해
Windows 편집 알림을 전달합니다. 메시지마다 HWND·PID·네이티브 부모와 UIA 부모를 확인하고,
2초 제한 후 실패하면 재시도 없이 중단합니다. 입력 후 정확한 경로를 다시 확인합니다.
이 조작은 이미 전경인 저장 창 안에서만 수행하며 외부 창 활성화·키보드·좌표 입력은 없습니다.
[최종 Windows 검사 #17](https://github.com/dropboxqfml-code/codex/actions/runs/43654232686)는
전체 검사에 성공했습니다. Windows 러너 build 26100 / Edge 156.0.4314.58에서
영어·한국어 브라우저 메뉴를 각각 열고 실제 Save As 창으로 지정한 staging 경로에 저장했습니다.
두 경우 모두 배타적 파일 읽기·Pillow 검증과 원본 바이트 일치를 확인했습니다.
합성 PNG는 96×64, 372바이트이며 SHA-256은
`66c51d37abf6966a24da94dce88e06961c610ac0c933ed9df1dad10a73079da4`입니다.

이 증거는 시험이 사용한 네이티브 저장 경로에 한정합니다. 사용자 시작 버튼은 별도 브라우저
시험으로, 세션 공통 미해결 상태·잠금·중단 복구는 모의/로컬 시험으로 검사했습니다.
2026-11-15 사용자 v5 TXT에서 `probe_passed`, `last_stage: complete`, 종료 코드 0을 확인했습니다.
Windows build 19045 / Edge 157.0.4341.46 / Windows UI ko-KR / RDP / DPI 96 / 모니터 1대에서
시작 버튼부터 실제 저장·원본 SHA-256 일치·브라우저 종료까지 성공했습니다.
제안 파일명은 `fixture-original.png`, 저장명은 `native-image.png`입니다.
이는 합성 이미지 한 장의 정상 저장에 대한 사용자 환경 검증이며 실사이트 감시나 다른 환경의 검증은 아닙니다.

## Chrome과 배포 안내

[Windows CI #18](https://github.com/dropboxqfml-code/codex/actions/runs/43659493217)에서
Chrome 156.0.8078.80의 영어·한국어 메뉴를 각각 실제로 열고 네이티브 Save As로 저장했습니다.
Edge 2개 조합도 함께 다시 통과했습니다. 4개 모두 같은 합성 PNG의 원본 SHA-256과 일치했습니다.
브라우저 엔진이 같아도 메뉴/UIA/프로세스 관계와 버전 차이가 있어 별도 검증합니다.
2026-11-15 v6 ZIP 전달 후 사용자가 채팅으로 `Chrome 성공`을 보고했습니다.
사용자 환경의 Chrome 기본 저장 시험도 성공으로 기록합니다. 이 보고에는 결과 TXT가 첨부되지
않았으므로 Chrome 버전·세부 환경·해시 값을 추가로 단정하지 않습니다. Edge 결과 TXT 및
Windows CI의 상세 검증 증거와 구분합니다.

Chrome 실행기와 재시험 실행기를 추가했습니다. 자동 대체나 자동 복구는 없으며,
알 수 없는 실행기 인자는 설치·로그·UI 실행 전에 거부합니다.
[Windows CI #19](https://github.com/dropboxqfml-code/codex/actions/runs/43659745007)에서
실제 CMD로 옵션 순서·잘못된 인자·래퍼 전달/종료 코드를 확인하는 7개 회귀 검사도 통과했습니다.
사용자 안내는 UTF-8 BOM/CRLF TXT로 만들고 v8부터 ZIP의 프로젝트 폴더에 하나만 동봉합니다.
재사용 가능한 패키징 스크립트가 안내 TXT의 위치·유일성·내용을 검사하고 기존 버전 덮어쓰기를 거부합니다.

## 회귀 검사

- 잠긴/보안 데스크톱, 다른 앱과 같은 PID의 다른 창, 잘못된 소유 관계, 중복 제목,
  포커스 변경은 조작 전에 중단합니다. 좌표·메뉴 순서·전역 키보드 입력 대체는 없습니다.
- 실제 Chromium 부모 경로의 중간 Pane, 다른 Window, 웹 Document 아래의 가짜 메뉴,
  외부 PID 조상과 순환 경로를 검사합니다. 조작 직전에 HWND·PID·소유 관계·전경을 다시 확인합니다.
- 합성 이미지의 decode→실제 우클릭→메뉴→저장 창 순서, 제안 파일명 보존,
  입력 경로 재확인과 알려진 원본 SHA-256 대응을 검사합니다.
- 결과 TXT는 마지막 단계·브라우저 버전·환경·포커스와 제한된 메뉴 진단을 보존합니다.
  외부 앱 제목·입력값·명령줄은 수집하지 않습니다.
- 실제 Linux Chromium과 Windows Edge에서 시작 버튼의 클릭/미클릭 상태를 검사합니다.
  이 시작 버튼 시험의 OS 전경 판정은 모의 객체입니다. Linux 파일 URL 정책은 변경하지 않고
  시험용 합성 파일만 루프백 HTTP로 제공합니다.
- 세션 공통 미해결 상태·mutex가 다른 작업 루트와 중복 실행을 차단합니다. 브라우저 PID 재사용,
  사용 중인 프로필, 조회 불가, 손상 상태, 디스크 쓰기 실패에서도 차단을 유지합니다.
  명시적인 재시험은 브라우저 종료 확인 후 보류 표시만 해제하며 결과나 프로필을 삭제하지 않습니다.
- 열린 파일과 경로의 식별자 대조, 검사 중 교체/변경, PNG CRC 손상과 모든 프레임 디코딩을 검사합니다.
  Windows가 열린 파일 교체 자체를 막는 두 경쟁 상태 시험은 해당 플랫폼에서 건너뜁니다.
  경로/descriptor에는 공통 식별자·크기·수정 시각을, descriptor 전후에는 변경 시각까지 대조합니다.
- SQLite 재발견·재시작 후 경로와 작업 ID 고정, 발견/확인 지점 원자적 롤백, 동시 선점,
  중단 토큰 거부, Retry-After·공통 대기 보존, 24시간/8회 한도와 읽기 전용 조회를 검사합니다.

시험에는 임시 합성 데이터만 사용합니다. 저장은 실제 브라우저 메뉴와 Windows 창을 통하며,
HTTP 저장·응답 바이트 추출·download.save_as·스크린샷으로 대체하지 않습니다.
합성 원본의 알려진 해시는 이 시험에 한정한 대응 증거입니다.

## 본문 분석과 관찰 결과 저장

본문 영역·제외 사유·이미지 로딩·첨부 파일명 대응과 반복 출현을 기록하는 분석기를 추가했습니다.
합성 페이지에서 검증한 프로필과 실사이트 관찰 근거를 구분합니다. 초기 실사이트 프로필은
대기열 등록을 차단했으며, 아래 사용자 v8 결과를 검토한 뒤 검증한 게시글 하나만 허용합니다.
클라우드 연결 시도는 터널 연결 오류로 종료됐으며 HTTP 차단이나 사이트 구조 변경으로
해석하지 않습니다. [관측 기록](live-dom-observations.md)을 참고하세요.

## 검색 목록과 감시 기준점 기반

엄격한 검색 URL 범위와 게시글 번호/링크 일치, 공지·광고·외부 행 분리, 표시된 작성자·날짜 원문,
페이지 이동 후보를 관찰하는 목록 분석기를 추가했습니다. 일반·마이너·미니 URL과 DOM은
합성 fixture로 검사했습니다. 도입 당시 실제 목록 프로필은 `unverified`였으며,
읽기 전용 검사 명령은 다운로드가 비활성화된 전용 headless 브라우저로 한 페이지를 탐색하고,
대기열·이미지 저장·네이티브 저장 상태를 변경하지 않습니다. 공유 보고서의 과거 커서는 해시 처리합니다.

합성 감시 계획은 첫 실행 기존 행 건너뛰기, 정확한 ID 기준점·겹친 페이지·최신 검색 재시작,

전용 브라우저에 정상 종료를 요청합니다. 새 브라우저·게시글 탐색·저장 창·네이티브 입력은 없고

## 0.5.0-alpha.13 자동 감시의 목록 검토 진단

자동 감시가 목록을 검토해야 하는 상태로 멈추면, 확인 가능한 제한된 진단 근거를
`last_list.review`에 남기도록 보완합니다. 같은 감시 범위의 최신 커밋 목록과 당시 최종
보고서를 대조한 최근 중단 근거를 `previous_list_review`로 읽습니다. 기록을 남기기 전에
발생한 새 실패의 원인까지 이 자료가 입증하지는 않습니다. 공통 사유만 있던 결과에서 실제
실패 페이지나 구조 조건을 추측해 채우지 않습니다.

`CHECK_LAST_LIST.cmd`는 기존 목록 구조 오류의 `list_diagnosis`와 이전 자동 감시의
`previous_list_review`를 함께 반환합니다. 검증 가능한 항목이 하나 이상 있으면
`diagnosis_found`, 둘 다 없으면 `no_saved_diagnosis`이며, 감시 DB가 없으면
`watch_database_missing`, 읽기 자체에 실패하면 `diagnosis_read_failed`를 기록합니다.
확인할 근거가 없던 항목은 null입니다. `previous_list_review.stage_ko`에는 확인한 검사
단계의 한국어 설명이 표시됩니다. 기존 구조 오류가 읽혔다는 사실만으로 이번
alpha.12의 마지막 중단 원인이 같은 오류라고 단정하지 않습니다.

이 진단은 같은 PC에 남은 기록을 읽으며 새 목록·게시글 접속이나 이미지 저장을 시작하지
않습니다. 원문 제목·작성자·URL·인증정보를 제외한 고정 사유·상태·페이지별 제한된 근거만
공유합니다. 사용자 확인은 새 ZIP의 같은 실행기 한 번과 생성된 TXT 한 개로 진행합니다.
실제 배포했던 alpha.12 소스 `f8b5d0a`로 별도의 모의 HTTP 500 목록 중단을 SQLite에
기록한 뒤 새 오프라인 진단으로 읽는 호환 검증을 수행했습니다. 네트워크와 프로세스 실행을
차단한 상태에서도 `list_diagnosis: null`, `previous_list_review.stage: watch_result`,
`http_status: 500`과 한국어 설명을 반환했습니다. 감시 DB·리스 파일·보고서의 내용 해시와
수정 시각은 확인 전후 같았습니다. 이 값은 모의 중단 시험의 결과이며 사용자 alpha.12의
실제 중단이 HTTP 500이었다는 근거는 아닙니다.

## 0.5.0-alpha.14 목록 문서 읽기와 제한된 복구

별도 재현에서 링크 하나의 주소에 잘못된 괄호가 있으면 목록 전체의 주소 검사가 중단되는

## 0.5.0-alpha.16 최근 목록과 보관한 복구 경로의 연결

실제 링크와 글 순서를 검증한 최근 네 문서의 끝에서 이전 첫 쪽의 글 세 건 이상이

`observed_frontier_shift`로 표시하며 현재 네 번째 방문 위치를 사용하고 원래 복구 경로와

추가 요청 없이 결과로 남깁니다. 기본 간격은 60초이며 처리 시간과 종료 조건에 따라
실행 시간이 달라지므로 항상 여덟 분 동안 실행하는 시험은 아닙니다. Windows 실행 창에서
Enter로 중단을 요청하면 현재 작업을 정리하고 완료한 목록 기록을 보존합니다.

`recovery_observation: disjoint_recent_rows`와 `recovery_observation_ko`는 재검증한
최근 네 문서의 일반 글 번호가 모두 이전 구간 첫 글보다 크고, 새 복구 기록이 실제 첫째·
넷째 문서와 일치하며 이전 복구 위치가 보관됐을 때만 표시합니다. 공개 보고에는 원문
글번호를 포함하지 않습니다. 이전 배포 기록은 당시 규칙으로 읽으며, 로컬 Chrome·SQLite
근거를 재검증해 표시한 관찰과 alpha.16 TXT에 없던 근거를 추정하는 일을 구분합니다.

실제 alpha.16 배포 소스 `cbd5c97`으로 만든 모의 `segment_queued` 기록에는 세부 사유를
저장하지 않은 채 새 오프라인 이력 판독으로 다시 읽었습니다. 네트워크와 프로세스 생성을
금지한 상태에서 근거에 맞는 관찰을 표시했고 파일 아홉 개의 내용 해시·수정 시각을
유지했습니다. 사용자 alpha.16의 29건이 같은 행 구성이나 분기였다는 근거는 아닙니다.

각 확인의 방문 쪽·새 후보·복구 상태와 최종 종료 사유를 보고합니다. 기본
`test-list-recovery` CLI의 한 번 확인과 `--follow-gap`의 조건부 두 번 확인도 계속
지원합니다. 종료 사유 `list_coverage_confirmed`는 전체 연결,
`recovery_followup_deferred`는 진행 근거 부족, `recovery_progress_stalled`는 진전 없는
반복, `cycle_limit_reached`는 횟수 한도 도달을 뜻하며 `list_test_summary_ko`로 설명합니다.
정상 종료만으로 미확인 구간이 모두 닫혔다고 해석하지 않습니다. 일반 연속 감시의 기존
간격은 유지합니다.

실제 Chromium에 시험 목록을 제공하고 같은 SQLite 기록으로 두 번 실행했습니다. 첫 실행은 새 후보 28건과 1건을 차례로 등록하고 8회 확인 후 11쪽에서 끝났습니다. 두 번째 실행은 11쪽부터 이어서 14쪽의 기준 글과 바로 다음 15쪽을 확인한 뒤 4회 만에 마쳤습니다. 후보 275건의 최초 발견 기록과 기존 완료 지점을 대조했고, 같은 글을 중복 등록하지 않았습니다. 이 수치는 오프라인 시험 목록의 결과입니다.

## 0.5.0-alpha.18 다시 읽은 복구 페이지의 제한된 앞부분 연결

최근 두 쪽과 이전 첫 쪽의 연결을 검증하고, 이전 복구 페이지의 같은 주소와 그곳의
유일한 다음 문서를 실제로 읽은 경우에만 새 경계 연결을 검증합니다. 같은 검색 범위의
정상 글 순서·구조가 전제이며, 다시 읽은 경계의 글은 모두 저장한 경계의 첫 글보다
새 글이어야 합니다. 이어 방문한 문서 끝에 저장된 경계 앞부분의 글이 세 건 이상 같은
순서로 연속하고, 그 끝 글까지의 이전 구간에서 미일치가 최대 두 건이며, 저장된 마지막
글에는 아직 도달하지 않아야 합니다. 겹침 앞에서 읽은 글은 모두 이전 경계 첫 글보다
새 글이어야 하며 다음으로 갈 유일한 유효 링크도 확인해야 합니다.

이 근거가 모두 확인되면 `frontier_relocated`·`frontier_prefix_overlap`로 실제 네 번째
문서에 복구 위치를 옮깁니다. 기존 탐색 경로를 사용하며 새 페이지 이동 규칙을 추가하지
않습니다. 이전 완료 지점·목표 글·보관한 미완료 구간은 유지하고, 위치 이동만으로 전체
누락 구간 완료나 과거 구간 재합류를 판정하지 않습니다. 새 경계 연결은 새 정책의
스키마 5에서만 허용하며 이전 배포 기록은 당시 판정으로 검증합니다.

`frontier_overlap`은 검증을 마친 시작 복구 기록과 완전하게 검증한 네 문서가 있을 때
`frontier_changed`·`frontier_relocated`에서만 표시합니다. `previous_rows`는 저장된
경계의 일반 글 수, `matched_rows`는 세 번째·네 번째 문서에서 다시 확인한 서로 다른
기존 글 수입니다. `shape`는 일치 없음 `none`, 현재 두 문서의 끝에서 이전 글의
전체보다 짧은 앞부분이 끊기지 않고 정확히 일치한 `prefix_at_end`, 그 밖의 양수 일치 `other`로
제한합니다. `frontier_overlap_ko`는 이 개수를 설명합니다. 미일치가 삭제를 뜻하지 않으며
근거가 부족하면 진단을 채우지 않습니다.

`candidate_eligible_visits`는 방문 순서의 처음부터 후보 판정에 사용할 수 있는 문서
수입니다. 예를 들어 1·2·5·6쪽을 방문하고 값이 2면 1·2쪽만 후보 판정 대상입니다.
새 경계 연결을 검증한 위치 이동에서는 값 4로 네 문서를 인정합니다. 방문 쪽·관찰·
후보 등록 범위를 구분하며 원문 글번호나 제목을 공개 진단에 넣지 않습니다.

사용자 확인은 같은 Windows PC의 새 ZIP에서 `TEST_LIST_RECOVERY.cmd`를 한 번
더블클릭하고 자동으로 열린 TXT 하나를 전달하는 절차입니다. 화면에 표시하지 않는
Chrome·실제 목록 확인 최대 8회·확인당 실제 문서 최대 4개·기존 요청 간격과 서버 대기
정책은 유지합니다. 본문 확인·이미지 저장은 실행하지 않습니다. 사용자 게시판에서 새 연결 조건이 성립하는지는 다음 실사이트 시험에서 확인합니다.
