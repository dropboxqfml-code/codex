## 검토에서 확인한 결함의 수정 검증

- 파일을 연 직후 및 최종 경로 확인 직전의 파일 교체를 재현해 검증을 거부했습니다.
  열린 파일의 `fstat` 결과와 경로의 파일 식별자를 대조합니다. Windows에서 열린 파일
  교체 자체를 허용하지 않는 파일시스템은 이 두 경쟁 상태 테스트를 건너뜁니다.
- 정상 PNG의 IDAT CRC를 손상시켜 라이브러리에서 검증 오류로 처리하고 CLI가
  traceback 없이 종료 코드 2를 반환하는지 확인했습니다.
- Windows 예약 갤러리 ID를 거부하고, 심볼릭 링크 권한·기능이 없는 환경에서는
  관련 테스트만 건너뛰도록 보완했습니다. Linux에서는 해당 테스트도 실행·통과했습니다.
- 같은 프로세스의 다른 창/저장 창, 잘못된 소유 관계·중복 제목·포커스 변경을
  모의 입력으로 검사했습니다. 현재 HWND/부모/소유 관계를 조작 직전에 재확인합니다.
- 지역 로캘과 Windows UI 언어가 다른 경우를 모의 검사했습니다. 브라우저 UI 언어는
  근거 없이 추정하지 않고 null로 남깁니다.
- 미완료 상태는 작업 루트와 무관한 세션 공통 파일에 보존합니다. 다른 루트에서
  네이티브 저장을 재실행해도 브라우저를 다시 시작하지 않는 통합 모의 테스트를 수행했습니다.
- 브라우저 PID 기록 전 종료, PID 재사용, 사용 중인 프로필, 프로세스 정보 확인 불가,
  상태 파일 손상 및 쓰기/fsync/교체 실패에서 차단이 유지되는지 검사했습니다.
  복구 성공 시에도 결과·프로필 파일이 보존되는지 확인했습니다.

## SQLite 대기열 검증

- 재발견·작성일 보완·날짜 정책 변경 후에도 최초 배정 경로와 최초 발견 시각 유지.
- 순서 변경 및 기존 순번의 새 이미지 추가 후에도 작업 ID·파일 슬롯 보존.
- 중간 INSERT 실패 시 발견 기록과 확인 지점 함께 롤백.
- 다른 연결의 작업 선점 중복 방지와 중단 복구 후 이전 토큰 거부.
- Retry-After·공통 대기의 재시작 보존·단축 방지 및 장시간 종료 후 24시간 한도 적용.
- 새 작업이 계속 들어와도 실행 시각이 더 오래된 재시도가 먼저 선택됨.
- UI/로컬/접근 오류가 네트워크 시도 횟수를 늘리지 않음.
- 읽기 전용 조회가 없는 DB를 생성하지 않고, 시험 명령이 기존 파일을 덮어쓰지 않음.
- 무관한 DB와 뷰만 있는 DB도 수정하지 않고 거부.

Windows 시험용으로 먼저 만든 ZIP은 대기열 추가 전의 고정 스냅샷입니다. 19개 파일을
독립 폴더에 풀어 잠금 설치·테스트(110개)·Ruff·Linux 플랫폼 거부를 다시 검증했습니다.
현재 저장소의 대기열 추가 판(133개 테스트)과 구분합니다. ZIP의 SHA-256은
`f3194170e95ce644620171f873a9afdc0cd6aba2782c7128b659c3eb990112d7`입니다.

테스트는 임시 생성 파일과 합성 데이터만 사용합니다. 실사이트 요청이나 이미지
다운로드는 실행하지 않았습니다. Windows UI 테스트를 모의 통과로 대체하지 않았습니다.

## 남은 필수 항목

- Windows 대화형 세션의 전용 브라우저 프로필·프로세스/창 소유권·메뉴와 저장 창
  식별, 실제 이미지 1장 저장, 기본 파일명 읽기, 화면 잠금·긴급 정지 동작.
- 실사이트 본문/첨부 DOM 검증과 로딩 확인, 원본 파일명 대응, 수집 없는 시험 모드.
- 구현된 SQLite 영구 대기열을 실제 목록/본문 파싱·저장 작업자에 연결.
- 서비스 공통 제한/회로 차단, 단일 UI 작업자, 파일 완료 신호와 본문 대응 확인.
- staging/최종 파일/DB/metadata.json 사이 종료·재시작 복구.
- 정기 감시·갤러리별 설정·누락 구간 보고·주소 변경 증거 처리.

현재 테스트는 정책 함수·로컬 검증·모의 UI 흐름을 검사하며 완성된 감시·저장 워크플로를
입증하지 않습니다. Linux에서는 Windows 네이티브 저장 선행 검증을 진행할 수 없습니다.
파일 검증의 시간 제한은 Pillow 호출 사이에서 확인하는 방식입니다. 단일 디코딩이나
`n_frames` 탐색을 강제로 중단하는 프로세스 격리는 아직 구현하지 않았습니다.

## Windows 시험 준비 안내 보완

첫 실제 Windows 시도에서 `uv`가 명령으로 인식되지 않아 실행 전 단계에서 실패했다는
사용자 보고를 받았습니다. 네이티브 저장 실패로 분류하지 않습니다.

`RUN_WINDOWS_TEST.cmd`는 uv 조회/필요 시 WinGet 설치 → 관리형 Python 3.12.14 준비 →
잠금 의존성 설치 → 단일 이미지 시험을 순서대로 실행합니다. 각 단계가 실패하면 중단하고
고유한 TXT 결과를 메모장으로 엽니다. 설치 실패 후 발견된 실행 파일도 실행하지 않으며,
네이티브 실패 뒤 자동 복구·재시도나 데이터 삭제를 수행하지 않습니다.

CMD의 오류 코드·경로 인용·설치 후 uv 조회 흐름을 독립 검토하고, ASCII/CRLF 및 사용자
안내 TXT의 UTF-8 BOM/CRLF를 확인했습니다. Linux 테스트는 133개 통과를 유지했습니다.
실제 Windows에서 CMD 설치와 저장을 끝까지 실행한 결과는 아직 없습니다.

후속 사용자 로그에서 uv 0.13.8의 설치 관리자 해시 검증·WinGet 설치 성공·종료 코드 0을
확인했습니다. 같은 CMD 프로세스가 새 uv 경로를 찾지 못해 `install_uv` 단계에서 종료됐으며,
Python 준비와 네이티브 저장은 아직 시작되지 않았습니다. 현재 프로세스 PATH와 고정된 설치 경로를 찾던 방식에
영구 Machine/User PATH를 읽어 확장하는 조회를 추가했습니다. 자식 PowerShell의 PATH만
설정하며 레지스트리·실행 정책·패키지 검증은 변경하지 않습니다. 최초 조회에도 적용해
이미 설치된 uv를 재사용합니다. 사용자 안내는 짧은 TXT 3단계로 유지합니다.

Windows CI에서 파일 생성 시각과 descriptor의 변경 시각을 같은 값으로 비교해 정상 이미지가
거부되는 문제도 확인했습니다. 경로/descriptor 사이에는 공통 식별자·크기·수정 시각을 비교하고,
descriptor 전후에는 변경 시각까지 계속 확인하도록 수정했습니다.

[Windows 자동검사](https://github.com/dropboxqfml-code/codex/actions/runs/43634792507)는
총 137개 중 135개 통과·2개 건너뜀, failure/error 0으로 완료됐습니다. 실제 CMD에서 한글·공백·
앰퍼샌드가 있는 uv 위치와 새로 등록된 사용자 PATH 검색을 시험했습니다. 해당 레지스트리
fixture는 명시적으로 허용된 GitHub Windows 러너에서만 잠시 설정 후 원래 값으로 복원하며,
일반 사용자 시험과 실제 실행기는 레지스트리를 수정하지 않습니다.
이 결과는 경로 검색·단위 테스트의 Windows 호환성을 확인한 것이며 브라우저 저장 UI를
성공으로 검증한 결과는 아닙니다.
